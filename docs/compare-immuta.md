# Governing at the query path: Provisa and platform-native policy tools (Immuta)

In Provisa, every read goes through one governed path, over every source you admit. A rule you write is applied on that path, so it means the same thing on a Snowflake table as on a Salesforce object. Much of the rest of Provisa is built on that one path, from data residency to synthetic test data.

Immuta is the best-known example of another approach. It writes your policies into each data platform's own policy objects, and each platform enforces them. Every Immuta statement below quotes and links Immuta's own documentation.

## Two places to enforce a rule

**In each platform.** On Snowflake, "Immuta manages and applies Snowflake governance column and row access policies to Snowflake tables" ([Snowflake integration](https://documentation.immuta.com/SaaS/configuration/integrations/snowflake/reference-guides/snowflake-overview)). Databricks Unity Catalog is similar. "Immuta generates and applies SQL user-defined functions", and "Row-level security is enforced by applying SQL UDFs" ([Unity Catalog integration](https://documentation.immuta.com/SaaS/configuration/integrations/databricks/databricks-unity-catalog/databricks-unity-catalog-integration-reference-guide)). On Redshift, Immuta writes views, through what it calls "a policy push integration" that will "apply policies directly on Immuta-created views in Redshift" ([Redshift integration](https://documentation.immuta.com/SaaS/configuration/integrations/redshift/amazon-redshift-view-based-integration/reference-guides/redshift)).

Starburst and Trino don't take policy objects. Immuta's plugin runs inside the cluster, and "The masking and row-level security methods apply the actual policy expressions" ([Trino integration](https://documentation.immuta.com/saas/configuration/integrations/starburst-trino/trino-connection-reference-guide)).

**On the query path.** Provisa adds every rule to the statement before it runs. A row rule is a `WHERE` predicate "added after compilation and before execution", and a mask is pushed into the `SELECT` projection, so a masked role never receives the real value ([Security model](security.md#row-level-security-rls)). A statement that touches one direct-capable source runs whole in that source, with its filters pushed down. When a statement joins sources, Provisa's federation engine reads each source at its floor, and the rules run in that engine over those reads ([Sources](sources.md)).

## Expanding coverage

A platform-native rule reaches as far as the platforms the tool integrates with. Immuta's integrations overview lists Amazon Redshift, Amazon S3, Azure Synapse Analytics, Databricks Spark, Databricks Unity Catalog, Google BigQuery, Snowflake and Starburst (Trino) ([integrations overview](https://documentation.immuta.com/latest/configuration/integrations/integrations-overview)). The support matrix adds Apache Impala, CDH Spark, Netezza, Oracle, PostgreSQL and Teradata as legacy databases, "currently supported for existing customers" ([support matrix](https://documentation.immuta.com/latest/releases/support-matrix)). Support also varies inside a platform. On Azure Synapse, "Immuta only supports Dedicated SQL pools, not Serverless SQL pools" ([support matrix](https://documentation.immuta.com/latest/releases/support-matrix)).

Each platform also has to host the tool's account and objects. Snowflake setup needs "A set of Snowflake credentials to a system account", plus "A new system Snowflake role to orchestrate policies in Snowflake". That account holds privileges such as `APPLY MASKING POLICY` and `APPLY ROW ACCESS POLICY` ([Snowflake integration](https://documentation.immuta.com/SaaS/configuration/integrations/snowflake/reference-guides/snowflake-overview)). For Unity Catalog, "The Immuta service principal must own the catalog Immuta creates during setup" ([Unity Catalog integration](https://documentation.immuta.com/SaaS/configuration/integrations/databricks/databricks-unity-catalog/databricks-unity-catalog-integration-reference-guide)). For open-source Trino, "you must download the Immuta Trino plugin and add it to your Trino cluster", installing "the plugin archive on all nodes in your cluster" ([register a Trino connection](https://documentation.immuta.com/SaaS/configuration/integrations/starburst-trino/register-a-trino-connection)). Starburst users skip that step, since "The Immuta Trino plugin comes pre-installed on Starburst clusters" ([Trino integration](https://documentation.immuta.com/saas/configuration/integrations/starburst-trino/trino-connection-reference-guide)). A SaaS application or a third-party API that you don't administer has no place for any of this.

On the query path, coverage grows with every source you register. You can admit relational databases and warehouses, Elasticsearch and other analytics stores, MongoDB, Cassandra and Redis, files (CSV, Parquet, Excel and more), SaaS applications such as Salesforce, ServiceNow, Jira, Microsoft 365 and Google Workspace, and APIs described by OpenAPI, GraphQL or gRPC ([Sources](sources.md)). Provisa leaves the source as it is. You give Provisa a connection and credentials that allow the reads and writes you want it to serve. A source with no security model of its own, such as a CSV file or a public API, gets the same row rules and masks as a warehouse table.

## Consistency of application

When each platform enforces a policy, what the policy can do depends on the platform. Immuta's integrations overview publishes a table of data policy types by platform and says "If a data platform isn't included in the table, that integration does not support any data policies." In that table, format-preserving masking and randomized response are marked for Snowflake only, and reversible masking is not marked for Azure Synapse, Databricks Unity Catalog or Google BigQuery. A footnote adds that "Databricks Unity Catalog ARRAY, MAP, or STRUCT type columns only support masking with NULL" ([integrations overview](https://documentation.immuta.com/latest/configuration/integrations/integrations-overview)).

Platform limits carry through too. "Immuta also inherits some Snowflake limitations", the Snowflake guide says ([Snowflake integration](https://documentation.immuta.com/SaaS/configuration/integrations/snowflake/reference-guides/snowflake-overview)). Unity Catalog row filters and column masks aren't supported on views, and "Row access policies with more than 1023 columns are unsupported." Immuta calls the latter "an underlying limitation of UDFs in Databricks" ([Unity Catalog integration](https://documentation.immuta.com/SaaS/configuration/integrations/databricks/databricks-unity-catalog/databricks-unity-catalog-integration-reference-guide)). A rule is only as complex as the platform's policy object can hold.

In Provisa a rule's reach doesn't depend on the source. A row rule is a SQL predicate, and it can read the caller's session settings, such as `current_setting('provisa.user_region')`. A mask is an ordered list per column, where the first entry the reader holds decides what it sees ([Security model](security.md#column-level-masking)). The same row rule, mask and column grant hold on a PostgreSQL table, a Salesforce object, a CSV file and a MongoDB collection. Masked columns are refused in `WHERE` and `HAVING` on every source too, which stops a caller from recovering a value by filtering ([Security model](security.md#layer-5-predicate-guard)).

## Portability and lock-in

Immuta answers part of the lock-in question. You author a policy once, in Immuta, and Immuta applies it on each platform it supports. How far does it carry? Only to those platforms, and only as far as each platform's native policy objects can express it. Queries stay behind. So do views, written in each platform's own SQL dialect.

Provisa holds the query layer as well. Clients reach Provisa over protocols they already speak. SQL tools use the PostgreSQL wire protocol, JDBC or Arrow Flight SQL, graph tools use Bolt, and applications use GraphQL, gRPC or REST ([Integrations](integrations.md), [Security model](security.md)). Your rules name Provisa's tables, and so do your clients' queries. Swap the source beneath a table, and both keep working. For a tool that already speaks one of these protocols, adopting Provisa is a change of connection details, and your queries stay as they are.

## Direct access to a source

On a platform-native tool, users query the platform itself. A Snowflake user "queries the corresponding table directly in Snowflake" and a Databricks user "queries the corresponding table directly in Databricks". On Redshift, users "query Redshift views directly instead of going through a proxy" ([Snowflake](https://documentation.immuta.com/SaaS/configuration/integrations/snowflake/reference-guides/snowflake-overview), [Unity Catalog](https://documentation.immuta.com/SaaS/configuration/integrations/databricks/databricks-unity-catalog/databricks-unity-catalog-integration-reference-guide), [Redshift](https://documentation.immuta.com/SaaS/configuration/integrations/redshift/amazon-redshift-view-based-integration/reference-guides/redshift)).

With Provisa, who can reach a source directly is yours to decide as the operator. Lock each source so that only Provisa's service account reads it. You already apply this discipline to a warehouse superuser's credentials, which you keep out of everyday hands. Once the lock is in place, every read of that source takes the governed path.

## What one governed path makes possible

Because every read passes through the same place, features that need to see every read can be built once and hold on every source.

- **Regions and residency.** A table can name a home region, where its personal data is stored and processed. Other regions read it there under the reader's row and column rules, so only what the reader may see leaves the region ([Regions](regions.md), [Data residency](security.md#data-residency)).
- **A semantic layer.** An [ontology](ontology.md) gives every column a term, with definitions and relationships, and [data products](data-products.md) publish owned bundles of tables. Both span every source you register.
- **Fakes and synthetic data.** A sensitive column has four levels of protection. In any environment a role can be denied it or shown a mask. A test environment fakes it for every role, and a synthetic environment holds no real rows at all ([Building test environments](test-data.md), [Environments](environments.md)).
- **Reviewed judgments.** Each governance decision, such as a mask or a row rule, can carry the reason for it and a date by which to review it. Provisa records who decided it and the profile evidence behind the decision. A periodic review queues the judgments that have gone stale. A steward reaffirms a judgment against today's evidence ([Judgments under review](security.md#judgments-under-review)).
- **Rules traced to policy.** A judgment can cite named bases, such as a regulation or an internal policy. When you declare a basis changed, every earlier judgment that cites it is flagged for review at once ([Judgments under review](security.md#judgments-under-review)).

## What governing costs

Governance is never free. In Provisa it is its own timed stage of every request. Each request records how long governing took, and the CPU it used, beside the other stages. At debug trace detail the stage is a span of its own, `pipeline.governance`. You can read these in **Admin > Observability**, or export them over OpenTelemetry to your own collector ([Observability](features.md#observability-otel), [Configuration](configuration.md#observability)). Rules vary too much from one organization to the next for a general benchmark to tell you much. Measure what your own rules cost on your own queries.

## Other Immuta features

- **Access requests.** A consumer requests a data product. If no approval is needed, access "is automatically granted once the user acknowledges the data use agreement"; otherwise "the request will enter the approval flow and appear as Pending". "Immuta automatically provisions access through policies in the data platform" ([requesting access](https://documentation.immuta.com/saas/request/access-data-products/how-to-guides/requesting-access-to-a-data-product)). "Data stewards are able to make determinations on access requests", and can approve one "for a specific period of time" ([responding to requests](https://documentation.immuta.com/saas/marketplace/review-access-requests/how-to-guides/view-and-respond-to-access-requests)).
- **Sensitive data discovery.** "Identification runs identifiers to discover data", using "built-in identifiers to discover common categories of data". Identifiers can match on column names, on regular expressions or on dictionaries. A competitive identifier "must match at least 90% of the data sampled". Regex and dictionary matching are listed for Redshift, Databricks, Snowflake and Starburst, and column-name matching for all eight integrations ([data discovery](https://documentation.immuta.com/latest/discover-your-data/data-discovery)).
- **Purposes.** "Purposes allow governors to define exceptions to policies", and "Each purpose has its own acknowledgement statement" ([projects and purposes](https://documentation.immuta.com/latest/governance/author-policies-for-data-access-control/projects-and-purpose-based-access-control/projects-and-purpose-controls/reference-guides/projects)). The SaaS documentation marks this feature deprecated: "Support for projects and purposes has been deprecated" ([projects and purposes, SaaS](https://documentation.immuta.com/saas/govern/secure-your-data/projects-and-purpose-based-access-control/purpose-index/reference-guides/projects)).

## When policies in each platform suit you

Writing policies into each platform is a good match when your data already lives in the platforms Immuta supports and people connect to those platforms with their own tools. It also suits you when you want consumers to request access and stewards to approve it, with access provisioned on approval. Provisa has no request and approval workflow.
