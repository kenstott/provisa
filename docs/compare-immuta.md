# Governing at the query path: Provisa and platform-native policy tools (Immuta)

In Provisa, every read goes through one governed path, over every source you admit. A rule you write is applied on that path, so it means the same thing on a Snowflake table as on a Salesforce object. Much of the rest of Provisa is built on that one path, from data residency to synthetic test data.

Immuta is the best-known example of another approach. It writes your policies into each data platform, as the platform's own policy objects or as views and grants that Immuta creates there, and each platform enforces them. Every Immuta statement below quotes and links Immuta's own documentation.

## Two places to enforce a rule

**In each platform.** On Snowflake, "Immuta manages and applies Snowflake governance column and row access policies to Snowflake tables" ([Snowflake integration](https://documentation.immuta.com/SaaS/configuration/integrations/snowflake/snowflake-overview)). Access itself goes through grants. Immuta's low row access policy mode works "by using table grants to manage user access" and is "enabled by default" ([low row access policy mode](https://documentation.immuta.com/SaaS/configuration/integrations/snowflake/snowflake-overview/integration-settings/snowflake-low-row-access-policy-mode)). Immuta's deprecations page lists running "Snowflake without table grants" with an end of life in July 2026 ([deprecations](https://documentation.immuta.com/SaaS/releases/deprecations)).

Databricks Unity Catalog is similar. "Immuta generates and applies SQL user-defined functions", and "Row-level security is enforced by applying SQL UDFs" ([Unity Catalog integration](https://documentation.immuta.com/SaaS/configuration/integrations/databricks/databricks-unity-catalog/databricks-unity-catalog-integration-reference-guide)). Amazon Redshift has two integrations. In one, "Immuta generates a masking or row-level policy in Amazon Redshift" ([Amazon Redshift integration](https://documentation.immuta.com/SaaS/configuration/integrations/redshift/amazon-redshift-integration/reference-guides/amazon-redshift-integration-reference-guide)). The other, for Redshift Spectrum, is "a policy push integration" that will "apply policies directly on Immuta-created views in Redshift" ([Redshift Spectrum integration](https://documentation.immuta.com/SaaS/configuration/integrations/redshift/amazon-redshift-view-based-integration/redshift)).

Views carry the policy on other platforms too. On Azure Synapse, Immuta creates schemas that "contain policy-enforced views that users query" ([Synapse integration](https://documentation.immuta.com/SaaS/configuration/integrations/azure-synapse-analytics/azure-synapse-analytics)). In Google BigQuery's view-based integration, "Immuta creates views that contain all policy logic" ([BigQuery view-based integration](https://documentation.immuta.com/SaaS/configuration/integrations/google-bigquery/google-bigquery-view-based-integration)).

Starburst and Trino don't take policy objects. Immuta's plugin runs inside the cluster, and "The masking and row-level security methods apply the actual policy expressions" ([Trino integration](https://documentation.immuta.com/saas/configuration/integrations/starburst-trino/trino-connection-reference-guide)).

**On the query path.** Provisa adds every rule to the statement before it runs. A row rule is a `WHERE` predicate "added after compilation and before execution", and a mask is pushed into the `SELECT` projection, so a masked role never receives the real value ([Security model](security.md#row-level-security-rls)). A statement that touches one direct-capable source runs whole in that source, with its filters pushed down. When a statement joins sources, Provisa's federation engine reads each source at its floor, and the rules run in that engine over those reads ([Sources](sources.md)).

## Expanding coverage

A platform-native rule reaches as far as the platforms the tool integrates with. Immuta's SaaS integrations page lists Amazon Redshift, Amazon Redshift Spectrum, Amazon S3, AWS Lake Formation, Azure Synapse Analytics, Databricks Spark, Databricks Unity Catalog, Google BigQuery (view-based and viewless), MariaDB, MySQL, Oracle, Snowflake, SQL Server, Starburst (Trino) and Teradata ([integrations](https://documentation.immuta.com/SaaS/configuration/integrations)). The self-managed release lists eight of these ([self-managed integrations overview](https://documentation.immuta.com/latest/configuration/integrations/integrations-overview)).

Some listed integrations enforce nothing. On MySQL, MariaDB, Oracle and SQL Server you can author policies in Immuta, but "these policies will not be enforced natively" ([MySQL](https://documentation.immuta.com/SaaS/configuration/integrations/mysql/mysql-integration-reference-guide), [MariaDB](https://documentation.immuta.com/SaaS/configuration/integrations/mariadb/mariadb-connection-reference-guide), [Oracle](https://documentation.immuta.com/SaaS/configuration/integrations/oracle/oracle-connection-reference-guide), [SQL Server](https://documentation.immuta.com/SaaS/configuration/integrations/sql-server/sql-server-connection-reference-guide)). Amazon S3 and AWS Lake Formation take subscription policies, which govern access, and no data policies, so they get no row or column rules ([integrations](https://documentation.immuta.com/SaaS/configuration/integrations)). Support also varies inside a platform. On Azure Synapse, "Immuta only supports Dedicated SQL pools, not Serverless SQL pools" ([support matrix](https://documentation.immuta.com/SaaS/releases/support-matrix)).

Each platform also has to host the tool's account and objects. Snowflake setup needs "A set of Snowflake credentials to a system account", plus "A new system Snowflake role to orchestrate policies in Snowflake". That account holds privileges such as `APPLY MASKING POLICY`, `APPLY ROW ACCESS POLICY` and `MANAGE GRANTS` ([Snowflake integration](https://documentation.immuta.com/SaaS/configuration/integrations/snowflake/snowflake-overview)). For Unity Catalog, "The Immuta service principal must own the catalog Immuta creates during setup" ([Unity Catalog integration](https://documentation.immuta.com/SaaS/configuration/integrations/databricks/databricks-unity-catalog/databricks-unity-catalog-integration-reference-guide)). For open-source Trino, "you must download the Immuta Trino plugin and add it to your Trino cluster", installing "the plugin archive on all nodes in your cluster" ([register a Trino connection](https://documentation.immuta.com/SaaS/configuration/integrations/starburst-trino/register-a-trino-connection)). Starburst users skip the download, since "The Immuta Trino plugin comes pre-installed on Starburst clusters" ([Trino integration](https://documentation.immuta.com/saas/configuration/integrations/starburst-trino/trino-connection-reference-guide)). On both, you still write Immuta's `immuta-access-control.properties` file and "add it to your Trino cluster's `etc` folder" ([register a Trino connection](https://documentation.immuta.com/SaaS/configuration/integrations/starburst-trino/register-a-trino-connection)). On Databricks Spark, "Immuta installs an Immuta-maintained Spark plugin on your Databricks cluster". You apply a cluster policy that Immuta generates, and an Immuta init script downloads the plugin each time the cluster starts ([Databricks Spark installation](https://documentation.immuta.com/SaaS/configuration/integrations/databricks/databricks-spark/reference-guides/databricks/installation-and-compliance)).

A SaaS application or a third-party API that you don't administer has no place for any of this. Immuta's custom securables let it decide access to such objects. You can register subscription policies "for any object, such as a SaaS application or API". Even so, "Immuta does not enforce those access controls on them", and "Data policies are unsupported". Your own tooling carries out each decision ([custom securables](https://documentation.immuta.com/SaaS/configuration/integrations/custom-integrations/custom-securables-reference-guide)). Immuta's docs list no MongoDB or Elasticsearch integration ([integrations](https://documentation.immuta.com/SaaS/configuration/integrations)).

On the query path, coverage grows with every source you register. You can admit relational databases and warehouses, Elasticsearch and other analytics stores, MongoDB, Cassandra and Redis, files (CSV, Parquet, Excel and more), SaaS applications such as Salesforce, ServiceNow, Jira, Microsoft 365 and Google Workspace, and APIs described by OpenAPI, GraphQL or gRPC ([Sources](sources.md)). Provisa leaves the source as it is. You give Provisa a connection and credentials that allow the reads and writes you want it to serve. A source with no security model of its own, such as a CSV file or a public API, gets the same row rules and masks as a warehouse table.

## Consistency of application

When each platform enforces a policy, what the policy can do depends on the platform. Immuta's integrations page publishes a table of data policy types by platform. A platform missing from the table "does not support any data policies." In that table, reversible masking is marked for Redshift Spectrum, Databricks Spark, Snowflake and Starburst (Trino). Amazon Redshift, Azure Synapse, Databricks Unity Catalog, both BigQuery integrations and Teradata lack it. BigQuery's viewless integration filters rows but is marked for none of hashing, replace with NULL or replace with constant. A footnote adds that "Databricks Unity Catalog ARRAY, MAP, or STRUCT type columns only support masking with NULL" ([integrations](https://documentation.immuta.com/SaaS/configuration/integrations)).

A mask the platform can't run may become a different mask. On Azure Synapse, a column given an unsupported type, such as reversible or regex masking, "will be masked to NULL" ([Synapse integration](https://documentation.immuta.com/SaaS/configuration/integrations/azure-synapse-analytics/azure-synapse-analytics)).

Platform limits carry through too. On correlated subqueries in custom `WHERE` policies, "Immuta also inherits some Snowflake limitations" ([Snowflake integration](https://documentation.immuta.com/SaaS/configuration/integrations/snowflake/snowflake-overview)). Unity Catalog row filters and column masks aren't supported on views, and "Row access policies with more than 1023 columns are unsupported." Immuta calls the latter "an underlying limitation of UDFs in Databricks" ([Unity Catalog integration](https://documentation.immuta.com/SaaS/configuration/integrations/databricks/databricks-unity-catalog/databricks-unity-catalog-integration-reference-guide)). A rule is only as complex as the platform's policy object can hold.

In Provisa a rule's reach doesn't depend on the source. A row rule is a SQL predicate, and it can read the caller's session settings, such as `current_setting('provisa.user_region')`. A mask is an ordered list per column, where the first entry the reader holds decides what it sees ([Security model](security.md#column-level-masking)). The same row rule, mask and column grant hold on a PostgreSQL table, a Salesforce object, a CSV file and a MongoDB collection. Masked columns are refused in `WHERE` and `HAVING` on every source too, which stops a caller from recovering a value by filtering ([Security model](security.md#layer-5-predicate-guard)).

## Portability and lock-in

Immuta answers part of the lock-in question. You author a policy once, in Immuta, and Immuta applies it on each platform it supports. How far does it carry? Only to those platforms, and only as far as each platform's native policy objects can express it. Queries stay behind. So do views, written in each platform's own SQL dialect.

Provisa holds the query layer as well. Clients reach Provisa over protocols they already speak. SQL tools use the PostgreSQL wire protocol, JDBC or Arrow Flight SQL, graph tools use Bolt, and applications use GraphQL, gRPC or REST ([Integrations](integrations.md), [Security model](security.md)). Your rules name Provisa's tables, and so do your clients' queries. Swap the source beneath a table, and both keep working. For a tool that already speaks one of these protocols, adopting Provisa is a change of connection details, and your queries stay as they are.

## Direct access to a source

On a platform-native tool, users query the platform itself. A Snowflake user "queries the corresponding table directly in Snowflake" and a Databricks user "queries the corresponding table directly in Databricks" ([Snowflake](https://documentation.immuta.com/SaaS/configuration/integrations/snowflake/snowflake-overview), [Unity Catalog](https://documentation.immuta.com/SaaS/configuration/integrations/databricks/databricks-unity-catalog/databricks-unity-catalog-integration-reference-guide)). The platform's own policies govern those reads, apart from the accounts Immuta exempts. On Snowflake, roles and users on Immuta's excepted list "will be exempt from policies" ([Snowflake](https://documentation.immuta.com/SaaS/configuration/integrations/snowflake/snowflake-overview)). On Unity Catalog, members of a policy exemption group are "exempt from Immuta data policy enforcement" ([Unity Catalog](https://documentation.immuta.com/SaaS/configuration/integrations/databricks/databricks-unity-catalog/databricks-unity-catalog-integration-reference-guide)).

In a view-based integration, the policy lives in the view. On Redshift Spectrum, users "query Redshift views directly instead of going through a proxy" ([Redshift Spectrum](https://documentation.immuta.com/SaaS/configuration/integrations/redshift/amazon-redshift-view-based-integration/redshift)). The base tables under those views carry no Immuta policy. For BigQuery, Immuta tells governors to "limit user access to original datasets" so that users read through the views ([BigQuery view-based integration](https://documentation.immuta.com/SaaS/configuration/integrations/google-bigquery/google-bigquery-view-based-integration)). Closing the path around the governed layer is an operator's task in both approaches.

With Provisa, who can reach a source directly is yours to decide as the operator. Lock each source so that only Provisa's service account reads it. You already apply this discipline to a warehouse superuser's credentials, which you keep out of everyday hands. Once the lock is in place, every read of that source takes the governed path.

## What one governed path makes possible

Because every read passes through the same place, features that need to see every read can be built once and hold on every source.

- **Regions and residency.** A table can name a home region, where its personal data is stored and processed. Other regions read it there under the reader's row and column rules, so only what the reader may see leaves the region ([Regions](regions.md), [Data residency](security.md#data-residency)).
- **A semantic layer.** An [ontology](ontology.md) gives every column a term, with definitions and relationships, and [data products](data-products.md) publish owned bundles of tables. Both span every source you register.
- **Fakes and synthetic data.** A sensitive column has four levels of protection. In any environment a role can be denied it or shown a mask. A test environment fakes it for every role, and a synthetic environment holds no real rows at all ([Building test environments](test-data.md), [Environments](environments.md)).
- **Reviewed judgments.** Each governance decision, such as a mask or a row rule, can carry the reason for it and a date by which to review it. Provisa records who decided it and the profile evidence behind the decision. A periodic review queues the judgments that have gone stale. A steward reaffirms a judgment against today's evidence ([Judgments under review](security.md#judgments-under-review)).
- **Rules traced to policy.** A judgment can cite named bases, such as a regulation or an internal policy. When you declare a basis changed, every earlier judgment that cites it is flagged for review at once ([Judgments under review](security.md#judgments-under-review)).

## What governing costs

Governance is never free. In Provisa it is its own timed stage of every request. Each request records how long governing took, and the CPU it used, beside the other stages. At debug trace detail the stage is a span of its own, `pipeline.governance`. You can read these in **Admin > Observability**, or export them over OpenTelemetry to your own collector ([Observability](features.md#observability-otel), [Configuration](configuration.md#observability)). Rules vary too much from one organization to the next for a general benchmark to tell you much. Measure what your own rules cost on your own queries.

## Other Immuta features

- **Access requests.** A consumer requests a data product. If no approval is needed, access "is automatically granted once the user acknowledges the data use agreement"; otherwise "the request will enter the approval flow and appear as Pending". "Immuta automatically provisions access through policies in the data platform" ([requesting access](https://documentation.immuta.com/saas/request/access-data-products/how-to-guides/requesting-access-to-a-data-product)). "Data stewards are able to make determinations on access requests", and can approve one "for a specific period of time" ([responding to requests](https://documentation.immuta.com/saas/request/review-access-requests/how-to-guides/view-and-respond-to-access-requests)).
- **Sensitive data discovery.** "Identification runs identifiers to discover data", using "built-in identifiers to discover common categories of data". Identifiers can match on column names, on regular expressions or on dictionaries. A competitive identifier "must match at least 90% of the data sampled" ([data discovery](https://documentation.immuta.com/latest/configuration/manage-data-metadata/data-discovery)). Regex and dictionary matching are listed for Redshift (including Spectrum), Databricks, Snowflake and Starburst. Column-name matching is listed for every integration except BigQuery viewless ([integrations](https://documentation.immuta.com/SaaS/configuration/integrations)).
- **Intents.** "Support for projects and purposes has been deprecated" ([projects and purposes](https://documentation.immuta.com/saas/govern/projects-and-purpose-based-access-control/purpose-index/reference-guides/projects)), and Immuta's deprecations page names intents as their replacement ([deprecations](https://documentation.immuta.com/SaaS/releases/deprecations)). "An intent is a form of identity that governors create." When a user assumes one, "the intent attributes replace any user attributes" ([intents](https://documentation.immuta.com/SaaS/govern/intents/intents-reference-guide)). Intents are "available in public preview for use with Databricks Unity Catalog" ([release notes](https://documentation.immuta.com/SaaS/releases/index)).

## When policies in each platform suit you

Writing policies into each platform is a good match when your data already lives in platforms where Immuta enforces policy, such as Snowflake, Databricks, Redshift or Starburst, and people connect to those platforms with their own tools. On Synapse and BigQuery the same holds for the views Immuta creates. It also suits you when you want consumers to request access and stewards to approve it, with access provisioned on approval on the platforms where Immuta enforces policy. Provisa has no request and approval workflow.
