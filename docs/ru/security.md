# Модель безопасности {: #security-model }

Provisa применяет многоуровневую модель безопасности ко всем языкам запросов (GraphQL, SQL, Cypher) и всем транспортам (REST, gRPC, Arrow Flight, JDBC, WebSocket). (REQ-001, REQ-266) Governance применяется единообразно — нет такого пути запроса, который бы её обходил. (REQ-002, REQ-266)

Уровни применяются по порядку. Запрос должен пройти каждый уровень, прежде чем будет оценён следующий.

## Многоуровневая модель {: #layered-model }

### Уровень 0 — Фильтрация интроспекции {: #layer-0-introspection-filtering }

Схема и каталог, представленные роли, содержат только таблицы из её списка `domain_access` и колонки, проходящие правила `visible_to` каждой колонки. (REQ-039) Объекты вне доступа роли невидимы при обнаружении — их нельзя запросить, автодополнить или сделать вывод об их существовании. (REQ-039) Это относится к схеме GraphQL, каталогу SQL и браузеру схемы в редакторе запросов. (REQ-039, REQ-363)

См. [Видимость схемы](#schema-visibility).

### Уровень 1 — Публичный доступ {: #layer-1-public-access }

Колонка, опубликованная с областью `public`, обслуживается каждой роли организации, включая роли, чей `domain_access` не достигает домена таблицы; такая роль видит таблицу только с её публичными колонками. Ничто не публично, пока регистрирующий таблицу этого не скажет. (REQ-1959) См. [Публичные колонки](#public-columns).

### Уровень 2 — Доступ к доменам {: #layer-2-domain-access }

Каждая роль несёт список `domain_access` из id доменов. Запрос, затрагивающий таблицу вне этих доменов, отклоняется до выполнения. (REQ-038, REQ-039) Это грубая граница владения — роль HR не достигает финансовых таблиц, как бы ни был написан SQL. (REQ-002)

См. [Модель прав](#rights-model).

### Уровень 3 — Безопасность на уровне строк {: #layer-3-row-level-security }

После подтверждения доступа к домену предикаты `WHERE` для каждой таблицы и роли внедряются в каждый `SELECT` во время выполнения. (REQ-041, REQ-263) Предикаты вычисляются по исходным данным. Региональный менеджер, запрашивающий общую таблицу заказов, видит только строки своего региона даже при `SELECT *`. (REQ-264)

См. [Безопасность на уровне строк (RLS)](#row-level-security-rls).

### Уровень 4 — Видимость и маскировка колонок {: #layer-4-column-visibility-and-masking }

Колонки со списком `visible_to`, который исключает запрашивающую роль, удаляются из вывода запроса. (REQ-040, REQ-263) Значения колонок с правилом маскировки заменяются — редактированием по regex, заменой на константу или усечением — до того, как результаты покидают сервер. (REQ-263) Маскировка применяется во всех языках запросов и форматах вывода. (REQ-263)

См. [Модель разрешений колонок](#column-permission-model) и [Маскировка на уровне колонок](#column-level-masking).

### Уровень 5 — Защита предикатов {: #layer-5-predicate-guard }

Маскированные колонки отклоняются в предложениях `WHERE` и `HAVING`. (REQ-263) Без этого вызывающий мог бы вывести немаскированное значение, подбирая его бинарным поиском в фильтре, хотя вывод маскирован. Отклонение выполняется при разборе запроса, до выполнения. (REQ-531)

### Governance связей (V002) {: #relationship-governance-v002 }

Условия JOIN в SQL должны соответствовать зарегистрированной и одобренной связи между таблицами. (REQ-001) Неодобренные соединения отклоняются. Каждая связь несёт понятные человеку причину и описание — ориентир для пользователей и автономных агентов о том, зачем существует путь обхода. Это политика governance, а не жёсткая граница безопасности: уровни 2–5 действуют независимо от структуры соединения, поэтому намеренный обход не раскрывает данных, которые роль не могла бы получить двумя отдельными запросами. Попытки обхода журналируются и поддаются аудиту.

**Механизмы обхода** — V002 можно обойти двумя способами. Первый — это возможность: роль, у которой есть `ignore_relationships`, соединяет отношения, которые каталог не покрывает. Из предустановленных системных ролей её имеет только `modeler` — роль исследования, задача которой — определить модель, а не применять её. (REQ-1297) У `analyst` её нет.

Второй — исключение с двумя условиями, оба из которых должны выполняться:

1. **Флаг роли** — `relationship_guard: false` в определении роли (по умолчанию: `true`).
2. **Исключение в запросе** — SQL содержит комментарий `--relationship-guard=false`.

Один только флаг роли не обходит V002; один только комментарий не обходит V002.

**Режим высокой безопасности фиксирует защиту.** При `security.mode: high` ни один обход не действует: `ignore_relationships` игнорируется, `relationship_guard: false` игнорируется, и каждое соединение должно существовать в каталоге одобренных связей. (REQ-693) Это намеренная избыточность — производственная роль, которой возможность выдана по ошибке, всё равно не может выйти из модели.

**Путь GraphQL** — V002 всегда пропускается для запросов GraphQL. Связи, определённые в SDL, одобрены заранее по своей природе; проверка избыточна и не применяется.

**Пути SQL и Cypher** — V002 активен по умолчанию. И `endpoint_dev.py`, и `cypher_router.py` применяют проверку с двумя условиями перед вызовом `validate_sql`.

**Путь pgwire** — та же проверка с двумя условиями, что и в SQL. Комментарий `--relationship-guard=false` удаляется из запроса перед выполнением; до базы данных он не доходит.

---

Эти уровни сочетаются. У роли с доступом к доменам, RLS и маскированными колонками все пять ограничений действуют одновременно. Добавление источника данных, колонки или связи не требует обновлять каждое правило — каждый уровень настраивается независимо и автоматически применяется к любому запросу, затрагивающему регулируемые объекты.

## Модель прав {: #rights-model }

Независимо назначаемые возможности с необязательной иерархией ролей через `parent_role_id`. `admin` даёт всё. (REQ-042)

| Возможность | Описание |
| ----------- | ------------- |
| `source_registration` | Регистрировать источники данных |
| `table_registration` | Регистрировать таблицы и колонки |
| `create_relationship` | Определять связи FK |
| `access_config` | Настраивать RLS и маскировку |
| `query_development` | Выполнять запросы |
| `write` | Вызывать зарегистрированные мутации (грубый контроль; см. Авторизация мутаций) |
| `full_results` | Обходить ограничения выборки |
| `ignore_relationships` | Обходить governance связей (V002). Из системных ролей есть только у `modeler`, а в режиме высокой безопасности полностью игнорируется |
| `admin` | Суперпользователь — даёт всё |

### Наследование ролей {: #role-inheritance }

Роли могут наследовать от одной родительской роли через `parent_role_id`, заданный в конфигурации или на странице Безопасность как «Наследует от». (REQ-215) Цепочка сворачивается при запуске: потомок получает объединение возможностей и доступа к доменам своих предков, каждое предоставление колонки, метрики, функции и webhook, называющее предка, и правила RLS предков для каждой таблицы с приоритетом потомка — ближайшая роль в цепочке с правилом для таблицы даёт предикат этой таблицы, а правило, сохранённое для потомка, заменяет правило родителя для этой таблицы. (REQ-1677)

```yaml
roles:
  - id: basic_user
    capabilities: [query_development]
    domain_access: [public]
  - id: analyst
    capabilities: [full_results]
    domain_access: [sales, analytics]
    parent_role_id: basic_user   # inherits query_development + public domain
```
## Роли: предоставленные, псевдо и мета {: #roles-granted-pseudo-and-meta }

В модели доступа Provisa работают вместе три вида ролей.

### Предоставленные роли {: #granted-roles }

Предоставленная роль назначается пользователю напрямую. Она несёт права: возможности, доступ к доменам, записи маскировки, фильтры строк. Наследование (`parent_role_id`) сворачивает права предка в потомка при запуске. Права только добавляются; вычитания нет. Чтобы ограничить читателя, предоставляйте составной записи, которая называет и роль, и условие, либо поставьте запись маски перед разрешающей. (REQ-215, REQ-1677)

### Псевдороли {: #pseudo-roles }

Псевдороль выводится из атрибутов пользователя. Организация объявляет, какие типы атрибутов становятся ролями (`claim_roles`). Для каждого объявленного типа `t`, значение `v` которого дают атрибуты пользователя, у пользователя есть родительская роль `t` и её подроль `t__v`. Нет значения — нет ни одной из этих ролей.

Разрешение атрибутов имеет значение. Собственная запись организации об участнике побеждает то, что даёт провайдер идентичности: если оба называют один атрибут, используется значение организации, а значение провайдера помечается как переопределённое.

Псевдороли не несут прав и никогда не назначаются вручную. Список предоставления называет их точно так же, как предоставленную роль; запрос называет их в `X-Provisa-Role` и действует от их имени. (REQ-2057)

Подумайте о JWT: его claims — это факты о человеке. Псевдороли превращают выбранные факты в роли, чтобы предоставление могло обращаться к ним без создания роли на каждую комбинацию.

### Метароли {: #meta-roles }

Когда запрос называет больше одной роли, Provisa строит эфемерную метароль с идентификатором `meta:<ids sorted, joined by +>`. Она — единственный потомок каждой роли названного набора. Весь конвейер затем выполняется с ней как с обычной одиночной ролью.

Права — это объединение прав каждого участника. Фильтры строк — это OR разрешённых фильтров каждого участника; если у какого-либо участника, читающего таблицу, нет фильтра, его нет и у метароли — отсутствие фильтра означает все строки. Метароль никогда не сохраняется, не перечисляется и не экспортируется. Она пересобирается из своих участников при изменении модели. (REQ-1620)

Запись аудита называет каждую действующую роль, а не id метароли.

### Как запрос называет роли {: #how-a-request-names-roles }

Клиент отправляет одну роль или набор через запятую в `X-Provisa-Role`. Каждая названная роль должна быть у пользователя. Роль, не назначенная идентичности, отклоняется по имени.

Права и данные следуют только за ролями, от которых действует запрос: иметь роль — не значит действовать от неё. Одна роль — это эта роль; две или больше действуют как их метароль. Действующая роль, которая приносила бы с собой права каждой имеющейся роли, ничего бы не значила, поэтому запрос получает наименьшие привилегии, а запись аудита называет ровно то, что действовало.

Названные псевдороли входят как квалификаторы. У квалификатора нет собственных прав, доступа к доменам, масок или фильтров строк, поэтому он не участник прав метароли: как участник без масок он снял бы маску с каждой колонки, а как не читающий ни одной таблицы — завершил бы любое OR фильтров строк. Он входит только в предоставления: предоставление или запись маски, называющая `region__eu`, достигает запроса, который называет этот квалификатор вместе с предоставленной ролью. (REQ-2057)

### Что означает `+` {: #what-means }

`+` встречается в двух местах, и в каждом значит своё.

**В записи предоставления.** `analyst+region__eu` в списке `visible_to` или `to` означает, что читатель имеет их все — `analyst` И `region__eu` одновременно. Запись, которая не является составной, — это одна роль. Между записями списка правило — любая: читатель имеет предоставление, если у него есть любая запись. И внутри, ИЛИ между.

**В id метароли.** `meta:analyst+engineer` — серверный идентификатор метароли набора {analyst, engineer}. Её права — объединение обоих. Клиент никогда не называет id метароли напрямую; он называет роли, которые имеет, а сервер строит метароль.

### Правила колонок ABAC как простой RBAC {: #abac-column-rules-as-plain-rbac }

Политика на основе атрибутов спрашивает: «может ли этот пользователь с этими атрибутами видеть эту колонку?» RBAC спрашивает: «какие роли могут видеть эту колонку?» Составные предоставления и псевдороли делают это одним вопросом.

«Снимать маску с этого email только для аналитика в ЕС» — это запись маски `{to: [analyst+region__eu], mask: null}`. Любой читатель, у которого есть и роль `analyst`, и псевдороль `region__eu`, читает колонку без маски. Никакого языка политик. Никакой роли на комбинацию.

Компромисс — вычисление вместо перечисления. Небольшой каталог ролей снижает затраты на сопровождение, но «кто может видеть этот email из ЕС?» становится вычисляемым ответом: составные записи оцениваются по назначениям и claims каждого пользователя. Provisa может ответить в обе стороны, потому что модель — одно определение. Проверка доступа в редакторе колонок (`POST /admin/masks/check`) выполняет эту оценку для выбранного набора ролей.

### Преимущества {: #benefits }

- Правило колонки ABAC становится записью предоставления RBAC.
- Небольшой каталог ролей вместо роли на каждую комбинацию.
- Одно определение, согласующее правила каждого региона.
- Наименьшие привилегии и точная запись аудита на каждый запрос.

### Рекомендации {: #best-practices }

- Держите каталог ролей настолько малым, насколько позволяет организация.
- Наследуйте внутри одной оси (старшинство, уровень допуска). Комбинируйте по независимым осям (роль + регион, роль + отдел).
- Ставьте самые специфичные записи маски первыми — более ранняя запись побеждает, даже если у читателя есть более поздняя.
- Проверяйте действующий доступ через `POST /admin/masks/check` перед выпуском комбинации в продакшен.

## Модель разрешений колонок {: #column-permission-model }

У каждой колонки есть модель разрешений, управляющая чтением, записью и маскировкой для каждой роли. (REQ-042, REQ-249)

### Видимость в три уровня {: #three-tier-visibility }

| Уровень | Условие | Результат |
| ------ | ----------- | -------- |
| **Скрыта** | Роли нет в `visible_to` | Колонки нет в схеме и каталоге |
| **Маскирована** | Роль в `visible_to`; у первой записи маски, которую она имеет, есть `mask` | Колонка видна, значение в выводе заменено |
| **Без маски** | Роль в `visible_to`; у первой записи маски, которую она имеет, нет `mask`, или у неё нет ни одной | Полный доступ на чтение |

### Публичные колонки {: #public-columns }

У каждой колонки есть `scope`, задаваемый в файле модели, через API администратора или на странице Таблицы. Три области упорядочены по тому, кого они обслуживают: `restricted`, затем `domain`, затем `public`. Редактор таблицы (`table_registration` в домене таблицы) может сузить область колонки. Её расширение — `restricted` в `domain` или `public`, `domain` в `public` — обслуживает колонку большему числу ролей и требует права, которого требует её предоставление: `column_grant` или `access_config` в домене таблицы. Регистрируемая колонка сравнивается с `domain`, поэтому её регистрация как `public` — это расширение. Для колонки с чувствительным тегом любое изменение области требует `sensitive_data`. Отклонённое изменение называет колонку и право. (REQ-1959, REQ-1943, REQ-1944)

| Область | Обслуживается |
| ------- | ----------- |
| `domain` (по умолчанию) | Ролям, которые достигают домена таблицы, как говорит `visible_to`. Пустой `visible_to` — это каждая такая роль. |
| `public` | Тем же ролям и также ролям, которые не достигают домена таблицы. |
| `restricted` | Только ролям, которые называет `visible_to`. Пустой `visible_to` — никто. |

Публикация колонки снимает условие домена для этой колонки и ничего больше:

- Роли вне домена таблица обслуживается только с её публичными колонками. Остальные колонки таблицы и таблицы, которые ничего не публикуют, остаются вне её схемы, каталога и SQL.
- Собственный `visible_to` колонки по-прежнему решает, кому: публичная колонка, предоставленная одной роли, публична только для этой роли.
- Маски, фильтры строк, лимиты строк и защита связей действуют так же, как внутри домена. Без фильтра строк для роли опубликованные колонки читаются без фильтра; фильтр строк на таблице или её домене по-прежнему действует.
- Связь обслуживается, когда обслуживаются колонки обоих её концов.
- Колонка-параметр таблицы API (аргумент пути или запроса) — это не данные, и она ничего не публикует.
- Домен `ops` требует явного предоставления для каждой колонки (REQ-1133); ничто в нём не обслуживается между доменами, какой бы ни была область.

Правило одинаково на каждой поверхности, потому что каждая читает скомпилированную схему роли: GraphQL, SQL (HTTP, pgwire, Flight, JDBC), Cypher и Bolt, gRPC, REST и JSON:API, каталоги Flight и MCP и списки администратора. Область, не являющаяся одним из трёх значений, отклоняется при сохранении колонки.

### Разрешения на запись {: #write-permissions }

| Поле | Пустое означает | Назначение |
| ------- | ------------ | --------- |
| `visible_to` | Все роли могут читать | Управляет тем, кто видит колонку (с маской или без) |
| `writable_by` | Ни одна роль не может писать | Управляет тем, кто может изменять (INSERT/UPDATE) |

Разрешение на запись применяется в конвейере мутаций. Роль, которой нет в `writable_by`, получает ошибку 403 при попытке записать в ограниченную колонку. (REQ-033, REQ-034)

### Пример {: #example }

```yaml
columns:
  - name: email
    visible_to: [admin, analyst, viewer]
    writable_by: [admin]
    masks:
      - to: [admin]                   # admin sees raw value (no mask)
      - to: ["*"]                     # everyone else sees it masked
        mask: {type: regex, pattern: "(.).*@", replace: "$1***@"}
  - name: salary
    visible_to: [admin, hr]
    writable_by: [hr]
    masks:
      - to: [admin, hr]               # admin and hr see real value
      - to: ["*"]                     # all other visible roles see 0
        mask: {type: constant, value: 0}
  - name: created_at
    visible_to: []                    # all can read
    writable_by: []                   # nobody can write (auto-set)
```
В этом примере:

- `email`: admin видит `alice@example.com` и может редактировать; analyst и viewer видят `a***@example.com`
- `salary`: admin и hr видят настоящее значение; hr может редактировать; любая другая видимая роль видит `0`
- `created_at`: все могут читать, никто не может писать, маскировки нет

## Авторизация мутаций {: #mutation-authorization }

Зарегистрированные мутации (удалённый GraphQL, OpenAPI, gRPC, Hasura) защищены двумя независимыми проверками. (REQ-867, REQ-868) Роль может вызвать мутацию, только если у неё есть глобальная возможность `write` И она указана в списке `writable_by` этой мутации. (REQ-868) Пустой `writable_by` по умолчанию запрещает — ни одна роль не может её вызвать. (REQ-867)

Мутации классифицируются как записи по контракту, а не по заявлению вызывающего. (REQ-869) `SELECT`, который ссылается на функцию вида мутация, повышается до записи и подлежит той же проверке с двумя воротами, поэтому вызывающий не может вызвать мутацию, выдав её за чтение. (REQ-869) Переклассификация мутации как безопасной для чтения требует возможности `access_config` и записывается как решение governance; исключения для отдельного запроса нет. (REQ-870)

## Видимость схемы {: #schema-visibility }

Схемы GraphQL для каждой роли скрывают неавторизованное содержимое: (REQ-039)

- **Доступ к доменам**: роль видит таблицы только в своих доменах `domain_access` (`"*"` = все) (REQ-039)
- **Видимость колонок**: колонки, которых нет в `visible_to` для роли, исключаются из SDL (REQ-039)
- Неавторизованные таблицы/колонки не появляются в схеме (REQ-039)

## Безопасность на уровне строк (RLS) {: #row-level-security-rls }

Внедрение SQL-предложений WHERE для каждой таблицы и роли. Применяется после компиляции, до выполнения. (REQ-041, REQ-263)

```yaml
rls_rules:
  - table_id: orders
    role_id: analyst
    filter: "region = current_setting('provisa.user_region')"
```
Фильтр добавляется через AND к предложению WHERE запроса. Работает и для запросов, и для мутаций (UPDATE/DELETE). (REQ-035, REQ-041)

Термин `current_setting('provisa.<name>')` разрешается по переменным сеанса, которые связывает запрос: `user_id` из аутентифицированной идентичности, `role` из действующей роли и каждый скалярный claim токена под его именем в нижнем регистре без префикса `x-hasura-`, так что импортированный фильтр Hasura по `X-Hasura-User-Id` читает `provisa.user_id`. Настроенные `session_vars` роли — это базовые константы; привязки запроса накладываются поверх них. В незащищённом режиме заголовок `x-provisa-session-<name>` связывает `<name>`. Переменная, нигде не связанная, разрешается в NULL и не совпадает ни с одной строкой. (REQ-1682)

## Маскировка на уровне колонок {: #column-level-masking }

Маскировка задаётся как упорядоченный список для каждой колонки. Первая запись, которую имеет читатель, решает, что он видит. (REQ-2059, REQ-263)

| Тип маски | Поддерживаемые типы колонок | SQL-выражение |
| ----------- | ----------------------- | --------------- |
| `regex` | Строка (varchar, char, text) | `REGEXP_REPLACE(col, pattern, replace)` |
| `constant` | Любой | Литеральное значение (`NULL`, `0`, своя строка) |
| `truncate` | Дата/метка времени | `DATE_TRUNC(precision, col)` |

У каждой записи есть список `to`, называющий читателей, на которых она направлена, и необязательная `mask`. Запись без `mask` означает «без маски» для этих читателей. `*` в `to` совпадает с любым читателем.

Выражение маски переносится в проекцию SQL SELECT. База данных возвращает маскированное значение; немаскированные данные никогда не передаются по сети для маскированных ролей. (REQ-263) Маскированные колонки также блокируются в предложениях `WHERE` и `HAVING` (защита предикатов уровня 5), чтобы не допустить вывода значений через фильтрацию. (REQ-263, REQ-531)

**Нет записи — нет маски.** Читатель, у которого нет ни одной записи, читает колонку без маски. Завершайте список записью `*`, когда к каждому читателю должна применяться какая-либо маска. Редактор колонок предупреждает, если в списке нет записи `*` (`unlisted_unmasked`).

**Запрет порядком.** Более ранняя запись побеждает, даже если у читателя есть и более поздняя, более разрешающая. Чтобы подрядчики всегда видели зарплату под маской, какие бы ещё роли у них ни были, поставьте запись подрядчиков перед записью без маски. Предоставленная роль никогда не теряет того, что даёт родитель через наследование, но запись маски, стоящая в списке раньше, применяется первой — так здесь работает ограничение.

**Метароли.** Цепочка метароли включает роли каждого участника, их предков и все названные псевдороли. Запись, предоставленная любому участнику, достигает метароли. Запись перед ней, которую имеет другой участник, всё равно применяется первой.

**Проверка доступа.** `POST /admin/masks/check` принимает список масок и необязательный набор ролей и возвращает, какая запись применяется для этих ролей, плюс записи, которых не может достичь ни один читатель. Защищено `masking_config`.

```yaml
# email column: analyst+region__eu sees raw; everyone else sees masked
masks:
  - to: [analyst+region__eu]          # composite: analyst AND in EU region
  - to: ["*"]                         # all others
    mask: {type: regex, pattern: "(.).*@", replace: "$1***@"}

# hire_date column: hr sees raw; all other visible roles see year only
masks:
  - to: [hr]
  - to: ["*"]
    mask: {type: truncate, precision: year}
```
## Governance ответов действий {: #governing-action-responses }

Ответ отслеживаемой функции или webhook регулируется как строки таблицы. (REQ-1679) Строки, которые возвращает действие, связываются как отношение, колонки которого — объявленный выходной контракт действия (`output_columns` для функции, `inline_return_type` для webhook или свойства объекта массивного `return_schema` функции), и это отношение проходит тот же этап governance, что и каждое чтение таблицы, через CTE VALUES со строками. (REQ-1679) Ничего из RLS, маскировки или видимости для действий заново не реализуется.

Применяются три вещи, в том же порядке, что и для таблицы. (REQ-1679)

- Фильтр строк: правило RLS роли, сохранённое для действия по имени (`upsertRlsRule` с `actionName`), или, если у действия нет собственного, правило домена домена действия. Предикат проверяется по контракту при сохранении так же, как правило таблицы. (REQ-1676)
- Видимость колонок: колонка контракта, объявляющая `visible_to`, удаляется для роли, которую список не называет; колонка, которая ничего не объявляет, — часть публичной формы действия и остаётся.
- Маски: колонка контракта несёт `masks`, тот же упорядоченный список масок, что и колонка таблицы. (REQ-2059)

Наследование ролей разрешает цепочку для всех трёх. (REQ-1677) Ответ, возвращающий колонку вне объявленного контракта, отклоняется с 502, а не пропускается без регулирования. Действие, которое не объявляет контракта колонок, возвращает скаляр, и связывать ему нечего; оно возвращается как есть. Тестовый вызов администратора сообщает применённые фильтры, исключения и маски, а регулируемая инструкция записывается в журнал аудита запросов.

## Журнал аудита {: #audit-logging }

Каждый запрос, затрагивающий актив домена, записывается в `query_audit_log`, предназначенный только для добавления. (REQ-596, REQ-613) Каждая строка фиксирует `tenant_id`, `user_id`, `role_id`, хеш SHA-256 текста запроса, `table_ids`, `source`, `status_code`, `duration_ms` и `logged_at`. (REQ-596) Текст запроса никогда не хранится дословно — только его хеш. (REQ-596)

Журнал на уровне базы данных только для добавления: правила PostgreSQL блокируют `DELETE` и `UPDATE`. (REQ-596, REQ-613) Два индекса — `(tenant_id, logged_at)` и `(user_id, logged_at)` — поддерживают запросы соответствия по арендатору и по пользователю за интервалы времени. (REQ-596, REQ-613)

При включённом шифровании колонка хеша текста запроса хранится зашифрованной и расшифровывается только при авторизованных чтениях администратора. (REQ-689)

## Ограничение частоты {: #rate-limiting }

Лимиты частоты для каждой роли настраиваются в `provisa.yaml`: максимум запросов в секунду, максимум одновременных подписок SSE и максимум одновременных потоков Arrow Flight. (REQ-369) Лимиты применяются на уровне API до компиляции или выполнения; запросы сверх лимита отклоняются с HTTP 429 и заголовком `Retry-After`. (REQ-369)

У сервиса NL-запросов (`POST /query/nl`) есть отдельный лимит через `nl.rate_limit` (запросов в минуту на роль). Запросы сверх лимита отклоняются до любого вызова LLM. (REQ-370)

Состояние лимитов частоты хранится в Redis (`cache.redis_url`) как счётчик скользящего окна — без состояния в отдельном экземпляре, — поэтому лимиты действуют на всех горизонтальных экземплярах Provisa. (REQ-371)

## Лимит сложности запроса {: #query-complexity-limit }

Лимит частоты ограничивает, сколько запросов отправляет роль. Лимит сложности ограничивает, что может запросить одна инструкция. (REQ-1174)

У каждой инструкции есть оценка сложности: отношения, которые она читает, её соединения, колонки, которые она выбирает (`*` считается как колонки, которые он обозначает), и вложенные в неё запросы. Отношение, прочитанное из удалённого API-источника (OpenAPI, удалённый GraphQL, удалённый gRPC), считается за 10, потому что каждое чтение расходует бюджет, который удалённая система задаёт для всех пользователей этого источника.

Лимит — это `max_query_complexity` в `rate_limit` роли. Общеорганизационная настройка `limits.max_query_complexity` — потолок для каждой роли: роль может задать более низкий лимит, а более высокий не действует. По умолчанию ни один не задан.

```yaml
roles:
  - id: analyst
    rate_limit:
      max_query_complexity: 200
```
Оценка измеряется после разбора запроса и до его регулирования или выполнения, поэтому один лимит действует на каждом интерфейсе, через который может прийти инструкция: GraphQL, SQL по HTTP, pgwire, Arrow Flight, gRPC, Cypher, JSON:API и MCP. Инструкция сверх лимита отклоняется с её оценкой, лимитом и тем, что она запрашивала. Интерфейсы HTTP отвечают 413. Отказ записывается как отказ политики.

## Аутентификация {: #authentication }

Подключаемые провайдеры аутентификации: (REQ-120)

| Провайдер | Тип токена | Сценарий |
| ---------- | ----------- | ---------- |
| `none` | Заголовок X-Provisa-Role | Разработка |
| `basic` | Локальные учётные записи bcrypt + JWT | Автономные развёртывания |
| `firebase` | ID-токен Firebase | Продакшен |
| `keycloak` | JWT Keycloak | Предприятие |
| `oauth` | JWT OIDC | PingFed, Okta, Azure AD, Auth0 |
| `simple` | bcrypt + JWT | Тестирование |

Отображение ролей: claims идентичности → роль Provisa через настраиваемые правила. (REQ-120) Поле `assignments_source` управляет тем, откуда берутся назначения ролей: `claims` читает их из claims токена JWT (по умолчанию), `provisa` — из внутреннего хранилища назначений Provisa. (REQ-551) Мультиарендное развёртывание (`multitenancy: true`) само назначает роли, по организациям, поэтому должно использовать `assignments_source: provisa`: с `claims` оно не запускается, а изменение настроек, которое привело бы к этому сочетанию, отклоняется. Одноарендное развёртывание может использовать любой вариант.

Суперпользователь, настроенный в `provisa.yaml` (имя пользователя плюс пароль из секрета окружения), всегда получает роль admin и все возможности независимо от настроенного провайдера — путь начальной загрузки для первоначальной настройки. (REQ-125)

### Поверхности и учётные данные {: #surfaces-and-credentials }

Каждая поверхность аутентифицируется через один и тот же контракт провайдера, поэтому учётные данные, работающие на одной, работают на всех, где их может передать протокол. (REQ-124, REQ-1263) Эта таблица — единственный справочник; документация отдельных поверхностей её не повторяет.

| Поверхность | Пароль | Токен провайдера | Персональный токен доступа | Клиентский сертификат (mTLS) |
| --------- | ---------- | ---------------- | ----------------------- | --------------------------- |
| HTTP (REST, JSON:API, GraphQL) | `Authorization: Basic` | `Authorization: Bearer` | `Authorization: Bearer` | через терминирующий прокси |
| pgwire | поле пароля (открытый текст или SCRAM) | поле пароля, развёртывания OIDC | поле пароля | да |
| Bolt | схема `basic` | схема `bearer` | схема `bearer` | да |
| Arrow Flight | — | `token` в рукопожатии или полезной нагрузке тикета; заголовок вызова `authorization: Bearer` для `list_flights`, `get_flight_info` и `get_schema` | то же | да |
| gRPC | — | метаданные `authorization` | метаданные `authorization` | да |
| Airport (расширение DuckDB `airport`, по выбору) | — | `authorization: Bearer` (`auth_token` секрета) | то же | — |
| MCP | — | `Authorization: Bearer` | `Authorization: Bearer` | через терминирующий прокси |

Единственный вариант аутентификации расширения DuckDB `airport` — bearer-`auth_token` его секрета, поэтому клиент DuckDB предъявляет там токен провайдера или персональный токен доступа и действует от роли, в которую разрешается его идентичность. Клиент, который может задавать заголовки вызова, может запросить одну имеющуюся роль или набор через запятую в `x-provisa-role`. (REQ-1120, REQ-1263)

Отказ сообщает свой вид на каждой из этих поверхностей. Отсутствующие, отклонённые или непригодные учётные данные — это отказ аутентификации: HTTP 401, gRPC `UNAUTHENTICATED`, Arrow Flight и Airport `Unauthenticated`. Действительные учётные данные, запрашивающие действие от роли, которой у идентичности нет, — это отказ авторизации, с названием роли: HTTP 403, gRPC `PERMISSION_DENIED`, Arrow Flight и Airport `Unauthorized`. (REQ-273, REQ-1263) Одно исключение находится в клиентской библиотеке Arrow, а не на сервере: отказ вызова Flight `get_schema` доходит до клиента Python как общая ошибка Arrow с причиной сервера, но без её вида; `list_flights`, `get_flight_info` и `do_get` передают вид.

Там, где в ячейке `—`, протокол не несёт поля имени пользователя, к которому можно было бы приложить пароль; это покрывают формы токенов. pgwire — зеркальный случай: в стартовом пакете одно поле секрета и нет схемы, поэтому метод выбирает то, чем секрет *является*: PAT распознаётся по префиксу, секрет читается как bearer-токен, если настроенный провайдер — провайдер токенов, а всё прочее — пароль. Выбор делается один раз — учётные данные, которые отклонил выбранный валидатор, не проверяются повторно другим.

Матрицу обеспечивает `tests/unit/test_auth_surface_conformance.py`, который вызывает настоящую точку входа проверки каждой поверхности и падает, если поверхность добавлена без строки.

### Персональные токены доступа {: #personal-access-tokens }

PAT — это долгоживущий bearer-секрет, который пользователь создаёт для клиента, не способного пройти интерактивный вход, — скрипта, BI-инструмента, драйвера. (REQ-1263) Он несёт собственные организацию и роль, и каждая поверхность разрешает его через тот же валидатор, поэтому ни одной поверхности не нужно знать, что такое PAT.

Форма передачи — `provisa_pat_`, за которым следуют 43 символа base64, безопасных для URL. Префикс — это то, что направляет предъявленный секрет в хранилище токенов, а не к провайдеру идентичности, и делает утёкший токен находимым в журналах и репозиториях.

- **Хранение** — хранится только SHA-256 секрета. Сам секрет показывается ровно один раз, при создании, и не может быть восстановлен. Перечень несёт отображаемый префикс и метки времени жизненного цикла, но никогда работающие учётные данные.
- **Выпуск и отзыв** — `POST /auth/tokens`, `GET /auth/tokens`, `DELETE /auth/tokens/{token_hash}`, а также раздел самообслуживания в собственном профиле пользователя в интерфейсе администратора. Создание и отзыв учётных данных — действие владельца токена.
- **Атрибуция** — проверенный PAT разрешается в учётную запись владельца: id пользователя, email и отображаемое имя. Поэтому строка аудита или отчёт об использовании, записанные под PAT, называют человека, а не учётные данные. Какой из токенов этого человека действовал, передаётся отдельно, в `raw_claims["token_name"]`.
- **Срок действия** — у токена может быть срок действия; просроченный токен отклоняется при проверке. Удаление членства пользователя отзывает вместе с ним его токены.

### SCRAM-SHA-256 в pgwire {: #scram-sha-256-on-pgwire }

С провайдером `basic` настройка `auth.scram: true` заставляет pgwire предлагать SASL (код аутентификации 10) с механизмом `SCRAM-SHA-256`, так что пароль доказывается, а не передаётся. (REQ-1394) Привязка канала (`SCRAM-SHA-256-PLUS`) не предлагается.

SCRAM нужен верификатор RFC 5802, который нельзя вывести из хеша bcrypt. Верификатор записывается всякий раз, когда пароль проходит в открытом виде — при регистрации, входе, смене пароля, сбросе администратором, — поэтому развёртывание, включившее SCRAM, собирает верификаторы по мере следующей аутентификации пользователей, и первое SCRAM-подключение каждого пользователя следует за его следующим вводом пароля. Пользователю, у которого ещё нет верификатора, отвечают имитационным обменом, неотличимым от настоящего, чтобы сеть не раскрывала, кто уже перешёл.

### Взаимный TLS {: #mutual-tls }

Проверка клиентского сертификата переносит первую проверку в рукопожатие TLS: вызывающий без сертификата, подписанного CA развёртывания, никогда не достигает уровня учётных данных. (REQ-1228) Она доступна в pgwire, Bolt, gRPC и Arrow Flight — четырёх транспортах, которые сами завершают свой TLS.

| Переменная | Значение |
| ---------- | --------- |
| `PROVISA_MTLS_CLIENT_CA` | PEM-пакет CA, которым разрешено подписывать клиентские сертификаты |
| `PROVISA_MTLS_MODE` | `required` (по умолчанию, как только задан CA) или `optional` |
| `PROVISA_MTLS_BIND_PRINCIPAL` | Если true, общее имя сертификата должно совпадать с именем пользователя, под которым затем аутентифицируется соединение |

Переопределения для отдельных протоколов следуют тому же именованию, что и настройки TLS. Ничего не выводится: режим, заданный без CA, отказывается запускаться, а нераспознанный режим отказывается запускаться, а не читается как самый безопасный соседний — развёртывание, которое считает, что требует клиентские сертификаты, но не требует, в худшем положении, чем то, которое не запускается.

### Ограничение попыток входа {: #login-throttling }

Подбор паролей не зависит от протокола: одну и ту же учётную запись можно атаковать по HTTP, pgwire и Bolt. Поэтому счётчик находится на уровне проверки учётных данных, а не на какой-либо одной поверхности, так что блокировка, полученная где угодно, действует везде. (REQ-1393)

Оно включено по умолчанию — пять неудач за пять минут блокируют субъекта на пятнадцать минут — и настраивается в `auth.login_throttle`. Заблокированный субъект отклоняется ещё до проверки учётных данных, а успешная аутентификация очищает историю этого субъекта.

Ключ — это принципал, которого несёт протокол. Поверхность только с bearer не несёт принципала, поэтому ключ — дайджест самих учётных данных; это не даёт повторять плохой токен без ограничений. Хранилище — в пределах процесса, поэтому развёртывание с несколькими воркерами API допускает до `max_attempts` на воркер — ограничение тормозит подбор, а не является распределённой квотой.

### Указание организации {: #naming-the-org }

В мультиарендном режиме каждый запрос называет организацию, для которой он предназначен. Принадлежность ровно к одной организации её не называет: запрос, который не называет никакой, отклоняется, и отказ говорит, что отправить. (REQ-1235) Каждая поверхность называет организацию так:

| Поверхность | Как клиент называет организацию |
| ------- | -------------------------- |
| HTTP (интерфейс, REST, GraphQL) | Собственное имя хоста организации, `acme.provisa.dev`, или заголовок `X-Org-Provisa` на хосте плоскости управления |
| pgwire | Имя базы данных (`psql -d acme`, поле базы данных BI-инструмента) или собственное имя хоста организации, набранное по TLS |
| Bolt | Имя базы данных, `<org>.provisa_<role>` (или `<org>.provisa_ops_<role>`), или собственное имя хоста организации, набранное по TLS |
| Arrow Flight | `"org"` в тикете |
| gRPC | Заголовок метаданных `x-provisa-org` |
| MCP (транспорт HTTP) | Собственное имя хоста организации или заголовок `X-Org-Provisa` |
| Клиент Python | `org=` в `ProvisaClient`, `connect()` и `adbc_connect()`; `?org=` в URL SQLAlchemy |

Клиент pgwire, который набирает имя хоста по TLS, отправляет его в TLS ClientHello, и Provisa читает организацию оттуда (REQ-1234). Когда имя хоста и имя базы данных оба называют организацию и различаются, соединение отклоняется; ни одно не имеет приоритета. Имя базы данных `provisa`, используемое по умолчанию, не называет организацию, и BI-инструмент, подключённый к организации, показывает
эту организацию как свою базу данных. В Bolt `SHOW DATABASES` перечисляет по одному `<org>.provisa_<role>` для каждой организации, к которой
принадлежит пользователь; просто `provisa_<role>` в мультиарендном режиме отклоняется, а сеанс остаётся в
организации, которую назвал первой.

Имя — это просьба, а не предоставление. Везде оно попадает в один и тот же резолвер, который отклоняет организацию, участником которой аутентифицированный принципал не является и на которую не имеет межорганизационного права.

Персональный токен доступа выпускается для одной организации и сам её называет. Он открывает только эту организацию: запрос, называющий другую, отклоняется, даже если владелец токена принадлежит обеим.

У одноарендного развёртывания нет организации, которую нужно называть. Ни одна поверхность там не читает для этого имя хоста, имя базы данных или заголовок.

## Секреты между организациями {: #secrets-across-organizations }

Секреты организации читает только эта организация. В собственном хранилище Provisa каждый секрет хранится под своей организацией. В центральном сервисе (Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault) развёртывания со многими организациями каждое чтение выполняется внутри префикса читающей организации, а ссылка, которая вышла бы за его пределы, отклоняется. (REQ-1557) Префиксы и шаги по переносу существующих секретов под них описаны в разделе [Секреты](secrets.md#one-organizations-secrets-in-a-central-service).

## Режим высокой безопасности {: #high-security-mode }

`security.mode: high` в `provisa.yaml` утверждает одну гарантию: бэкенд Provisa никогда не обрабатывает данные в открытом виде. (REQ-693) Каждая значимая колонка зашифрована в источнике, и прочитать её может только клиент, у которого есть ключ расшифровки. У этой гарантии есть последствия, которые развёртывание должно предусмотреть.

**Что делает режим:**

- **Endpoint-ы данных требуют доказательства расшифровки на стороне клиента.** Всё под `/data/` возвращает 403, если вызывающий не предъявляет заголовок `X-Provisa-KMS-Key` — признак клиента JDBC или Python, настроенного на локальную расшифровку. Браузер или REST-потребитель открытого текста такого ключа не несёт и отклоняется. Контроль — это запрет по умолчанию на всё дерево: маршрут, добавленный завтра, защищён в день выпуска, а исключение нужно обосновать.
- **Endpoint-ы метаданных схемы остаются открытыми.** `/data/sdl`, `/data/introspection`, `/data/schema-version`, `/data/domains`, `/data/proto` и `/data/compile` не возвращают данных строк, а клиент должен прочитать схему — в том числе какие поля `@encrypted` — прежде чем сможет подключиться.
- **gRPC и Arrow Flight продолжают обслуживать, с тем же доказательством.** Это транспорты, которыми на деле пользуются шифрующие клиенты; их закрытие оставило бы развёртывание высокой безопасности без протокола передачи. Вызов данных в любом из них должен нести тот же ключ KMS как метаданные вызова.
- **pgwire, Bolt и MCP не запускаются.** Ни у одного из трёх нет рукопожатия на соединение, способного нести контекст расшифровки: набор строк pgwire и результат Cypher передаются открытым текстом, а вызов инструмента MCP отдаёт свои результаты модели как текст. Настроенный порт любого из них отклоняется при запуске, а не обслуживается.
- **Защиту связей нельзя обойти.** И `ignore_relationships`, и `relationship_guard: false` игнорируются; см. [Governance связей](#relationship-governance-v002).

**Как проверить, что развёртывание в этом режиме:** журнал запуска называет его, запрос `/data/sql` без ключа KMS отвечает 403 с сообщением, называющим REQ-693, а порты pgwire, Bolt и MCP не слушают.

## Хук утверждения ABAC {: #abac-approval-hook }

Необязательный внешний хук политики, срабатывающий перед выполнением запроса. (REQ-203) Если он настроен, Provisa обращается к вашему движку политик с идентичностью пользователя, ролями, таблицами, колонками и операцией. Ответ определяет, продолжится ли запрос. (REQ-203) Команда, зарегистрированная с **Требует одобрения**, передаётся тому же хуку перед каждым вызовом; см. [Вызовы команд](#command-calls). (REQ-1924)

### Область действия {: #scoping }

Хук срабатывает только когда запрос затрагивает включённую таблицу или источник — никаких накладных расходов для всего остального. (REQ-204)

| Конфигурация | Эффект |
| -------- | -------- |
| `auth.approval_hook.scope: all` | Каждый запрос вызывает хук |
| `sources[].approval_hook: true` | Все таблицы этого источника вызывают хук |
| `tables[].approval_hook: true` | Эта таблица вызывает хук |

### Протоколы {: #protocols }

Поддерживаются три транспорта: (REQ-246)

| Тип | Сценарий | Поле конфигурации |
| ------ | ---------- | ------------- |
| `webhook` | Любой сервис политик с HTTP (OPA, собственный) | `url` |
| `unix_socket` | OPA или сайдкар политик на той же машине | `socket_path` + `url` |
| `grpc` | Высокопроизводительный сервис политик рядом | `url` (host:port) |

Транспорт gRPC использует контракт `provisa.auth.ApprovalService`, определённый в `provisa/auth/approval.proto`. Реализуйте этот сервис в своём движке политик: (REQ-246)

```proto
service ApprovalService {
  rpc Evaluate (ApprovalRequest) returns (ApprovalResponse);
}

message ApprovalRequest {
  string user = 1;
  repeated string roles = 2;
  repeated string tables = 3;
  repeated string columns = 4;
  string operation = 5;
  map<string, string> session_vars = 6;
  string command = 7;         // a command call's name; empty for a query
  string arguments_json = 8;  // a command call's arguments as a JSON object
}

message ApprovalResponse {
  bool approved = 1;
  string reason = 2;
}
```
Канал gRPC постоянный — один канал на экземпляр Provisa, повторно используемый для всех вызовов этого endpoint хука. (REQ-555)

### Запрос / ответ {: #request-response }

Все три транспорта несут одинаковую полезную нагрузку: (REQ-246)

| Поле | Тип | Описание |
| ------- | ------ | ------------- |
| `user` | string | Идентичность аутентифицированного пользователя |
| `roles` | string[] | Роли Provisa пользователя |
| `tables` | string[] | Id таблиц, на которые ссылается запрос |
| `columns` | string[] | Колонки, выбранные в запросе |
| `operation` | string | `"query"` или `"mutation"`; `"command"` для вызова команды |
| `command` | string | Имя команды при вызове команды; пусто для запроса |
| `arguments` | object | Аргументы, с которыми вызывается команда; пусто для запроса |

Транспорты webhook и Unix-сокет обмениваются JSON, с `command` и `arguments` в качестве ключей. В gRPC аргументы передаются как текст JSON `arguments_json`. Ответ должен содержать `approved` (bool) и, по желанию, `reason` (string). (REQ-246)

### Вызовы команд {: #command-calls }

Команда с установленным `requires_approval` (переключатель **Требует одобрения** в форме команды) перед каждым вызовом идёт к хуку, на любой поверхности. Она выполняется, только если хук одобряет. Запрос несёт `operation: "command"`, имя команды и её аргументы; `tables` и `columns` пусты. (REQ-1924) [tool-verified: `provisa/api/data/action_exec.py` `_require_approval` (`operation="command"`, `tables=[]`, `columns=[]`, `command=fn["name"]`, `arguments=args`)]

```json
{
  "user": "analyst",
  "roles": ["analyst"],
  "tables": [],
  "columns": [],
  "operation": "command",
  "command": "create_issue",
  "arguments": {"input": {"title": "Crash on save"}}
}
```
[inferred: the payload also carries `session_vars`; values shown are placeholders]

Два отказа, оба 403:

- `functions.approval_unavailable`: хук не настроен. В отличие от запроса, команда, которой нужно одобрение, без него никогда не пропускается.
- `functions.approval_denied`: хук ответил `approved: false`. Причина — в сообщении.

### Тайм-аут и запасной вариант {: #timeout-and-fallback }

```yaml
auth:
  approval_hook:
    type: grpc          # webhook | grpc | unix_socket
    url: "localhost:50051"
    timeout_ms: 500     # default 5000
    fallback: deny      # allow | deny — applied on timeout or error
    scope: ""           # "" = use per-table/per-source flags; "all" = every query
```
При тайм-ауте или ошибке транспорта применяется политика `fallback`. (REQ-247) Автоматический выключатель (по умолчанию: размыкается после 5 последовательных ошибок, полуоткрыт через 30 с) предотвращает каскадные сбои из-за медленного endpoint хука. (REQ-556)

### Пример конфигурации {: #configuration-example }

```yaml
auth:
  approval_hook:
    type: webhook
    url: "http://opa.internal:8181/v1/data/provisa/allow"
    timeout_ms: 300
    fallback: deny

sources:
  - id: analytics_pg
    approval_hook: true   # all tables on this source require hook approval

tables:
  - id: salary_data
    approval_hook: true   # this table always requires hook approval
```
