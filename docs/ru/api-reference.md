# Справочник API {: #api-reference }

## Обзор {: #overview }

Provisa предоставляет REST-эндпоинты под двумя префиксами: `/data` для выполнения запросов и интроспекции схемы, и `/admin` для управления конфигурацией. Большинство эндпоинтов данных требуют идентификатор роли. Операции конфигурации admin используют Strawberry GraphQL API по адресу `/admin/graphql`.

---

## Аутентификация {: #authentication }

Когда `auth.provider` настроен в `provisa.yaml`, все эндпоинты, кроме `/health` и `/setup/status`, требуют заголовок `Authorization: Bearer <token>`.

Без настроенной аутентификации сервер работает в режиме разработки. Любой запрос обрабатывается как identity `anonymous`, которая сопоставляется со всеми настроенными ролями с доступом к доменам по маске (wildcard).

**Вход (`POST /auth/login`)** предоставляется активным провайдером аутентификации, когда настроено `provider: basic`. Формат учётных данных и ответа зависит от провайдера.

**Интроспекция identity:**

```http
GET /auth/me
```

Возвращает id, email, отображаемое имя, членства в организациях и назначенные роли аутентифицированного пользователя. В режиме разработки возвращает `dev_mode: true` со списком всех id ролей.

```http
GET /auth/provider-type
```

Возвращает `{"provider": "<name>"}` или `{"provider": null}`, если аутентификация не настроена.

## Эндпоинты данных {: #data-endpoints }

### `POST /data/graphql`

Выполнить GraphQL-запрос или мутацию.

**Тело запроса:**

```json
{
  "query": "{ orders(where: {region: {eq: \"us\"}}) { id amount } }",
  "variables": {},
  "role": "org_admin",
  "extensions": {}
}
```

Запрос выполняется от своей действующей роли: роли аутентифицированного пользователя или, в режиме разработки (без аутентификации), заголовка `X-Provisa-Role`, а при его отсутствии — `org_admin`. Поле `role` в теле не выбирает роль. Если оно есть, оно должно совпадать с действующей ролью; другое значение возвращает `400` с кодом `data.role_mismatch`, называющим обе роли. То же правило действует для `POST /data/sql`, `POST /data/query` и `POST /query/nl`.

Поле `extensions` поддерживает протокол Automatic Persisted Query (APQ):

```json
{
  "extensions": {"persistedQuery": {"sha256Hash": "<sha256-of-query>"}}
}
```

**Заголовки:**

- `X-Provisa-Role` — роль, от которой выполнять (режим разработки); с аутентификацией — запрос роли, который учитывается, только если роль назначена пользователю
- `Accept` — формат ответа (см. раздел «Согласование содержимого»)
- `Authorization` — `Bearer <token>`, когда включена аутентификация
- `X-Provisa-Redirect-Format` — MIME-тип для вывода перенаправления в S3
- `X-Provisa-Redirect-Threshold` — количество строк, выше которого срабатывает перенаправление
- `X-Provisa-Redirect` — `true` для безусловного принудительного перенаправления

**Кеш ответов:** включается для отдельного запроса директивой операции `@cached` (`query @cached(ttl: 60) { ... }`, `ttl` необязателен); та же директива действует для GraphQL, отправленного через Arrow Flight. Cypher включает кеш строкой `// @provisa cache=true` или `// @provisa cache_ttl=N`, gRPC — метаданными вызова `x-provisa-cache: true` или `x-provisa-cache-ttl: N`. Без неё запрос не читает кеш ответов и не пишет в него. Заголовок ответа `X-Provisa-Cache` сообщает `HIT` или `MISS`. См. [Кеш](configuration.md#per-request-opt-in).

#### Заголовки запроса для кеша ответов {: #response-cache-request-headers }

`/data/graphql`, `/data/cypher`, Neo4j Query API (`/db/{database}/query/v2`), `/data/rest` и `/data/jsonapi` принимают включение также в виде заголовка запроса. Каждая из форм ниже ведёт себя как `@cached(ttl: N)`:

| Заголовок | Равносильно |
| --- | --- |
| `Cache-Control: max-age=N` / `Cache-Control: max-stale=N` | `@cached(ttl: N)` |
| `Cache-Control: max-stale` (без значения) | `@cached` (TTL оператора) |
| `Cache-Control: no-cache` / `no-store` | без кеша, как если бы ничего не было отправлено |
| `x-provisa-cache: true` | `@cached` |
| `x-provisa-cache-ttl: N` | `@cached(ttl: N)` |

Запрос без одного из этих заголовков и без указания в тексте не кешируется, хотя обычные HTTP-кеши кешируют по умолчанию. Настройки кеша оператора действуют так же, как для `@cached`: заголовок никогда не делает чтение более свежим, чем они допускают, и никогда не отклоняется из-за запроса более длинного `ttl`. Остальные директивы `Cache-Control` (`no-transform`, `min-fresh`, ...) игнорируются, как того требует RFC 9111 от кеша.

Запрос может указать включение несколько раз: в тексте и в заголовке или в двух заголовках. Если они совпадают, запрос кешируется один раз, как запрошено. Если расходятся (например, `@cached(ttl: 60)` с `Cache-Control: max-age=5` или `x-provisa-cache-ttl: 10` с `Cache-Control: max-age=20`), запрос завершается ошибкой `400` с кодом `data.invalid_cache_control`, в которой названа каждая отправленная форма. Значение `N`, не являющееся целым числом секунд, приводит к такой же ошибке. Ни одной из форм предпочтение не отдаётся.

```bash
curl -H 'Cache-Control: max-age=120' -H 'X-Provisa-Role: analyst' \
  'http://localhost:8001/data/rest/sales/orders?limit=10'
```

**Ответ (JSON inline):**

```json
{
  "data": {
    "orders": [
      {"id": 1, "amount": 99.99}
    ]
  }
}
```

**Ответ (перенаправление):**

```json
{
  "data": {"orders": null},
  "redirect": {
    "redirect_url": "https://...",
    "row_count": 50000,
    "expires_in": 3600,
    "content_type": "application/vnd.apache.parquet"
  }
}
```

**Ответ (несколько корневых полей со смешанным inline/redirect):**

```json
{
  "data": {
    "orders": [{"id": 1}],
    "customers": null
  },
  "redirects": {
    "customers": {
      "redirect_url": "https://...",
      "row_count": 10000,
      "expires_in": 3600,
      "content_type": "application/vnd.apache.parquet"
    }
  }
}
```

Запросы с несколькими корневыми полями выполняют каждое корневое поле независимо. Поля ниже порога перенаправления возвращаются inline; поля выше — перенаправляются. Ключ `redirects` (во множественном числе) сопоставляет имена полей с информацией о перенаправлении.

**Заголовки кеша:**

- `X-Provisa-Cache: HIT|MISS`
- `X-Provisa-Cache-Age: <seconds>` (при HIT)

**Требуемые возможности:** `QUERY_DEVELOPMENT` для всех запросов, включая интроспекцию.

### Перенаправление {: #redirect }

Результаты, превышающие настроенный порог по количеству строк (или при `X-Provisa-Redirect: true`), записываются в S3, и возвращается предподписанный (presigned) URL.

| Формат перенаправления | Кем записывается | Память |
| --- | --- | --- |
| `application/vnd.apache.parquet` | федеративный CTAS | Не используется — данные никогда не проходят через Provisa |
| `application/x-orc` | федеративный CTAS | Не используется — данные никогда не проходят через Provisa |
| `application/json` | Provisa | Ограничено памятью |
| `application/x-ndjson` | Provisa | Ограничено памятью |
| `text/csv` | Provisa | Ограничено памятью |
| `application/vnd.apache.arrow.stream` | Provisa | Ограничено памятью |

Для больших аналитических выгрузок используйте перенаправление в Parquet или ORC. Движок федерации пишет напрямую в S3 параллельно, и никакие данные не проходят через Provisa.

```yaml
X-Provisa-Redirect-Format: application/vnd.apache.parquet
X-Provisa-Redirect-Threshold: 1000
```

### `POST /data/sql`

Выполнить необработанный SQL через конвейер управления Stage 2.

**Тело запроса:**

```json
{
  "sql": "SELECT id, amount FROM orders WHERE region = 'us'",
  "role": "org_admin"
}
```

`params` (необязательно) несёт значения заполнителей `$1…$n` инструкции, по порядку, отдельно от её текста:

```json
{
  "sql": "SELECT id, amount FROM orders WHERE region = $1 AND amount > $2",
  "params": ["us", 100]
}
```

Значения привязываются при выполнении инструкции, движком или драйвером источника, и никогда не вписываются в саму инструкцию, поэтому значение не может изменить, чем является инструкция. Они передаются ровно с одной инструкцией, плейсхолдеры которой точно их нумеруют. Пакет инструкций, плейсхолдер без значения или значение, которое не принимает ни один плейсхолдер, отклоняются с `400` и кодом `data.sql_parameters_do_not_fit` до того, как инструкция будет проверена управлением или выполнена. Инструкция без плейсхолдеров отправляется без `params`, как и раньше.

**Требуемые возможности:** `QUERY_DEVELOPMENT`.

Нарушения управления на `POST /data/sql` возвращают HTTP 403.

**Ответ:** тот же формат, что и `/data/graphql` (строки JSON по умолчанию, согласование содержимого через `Accept`).

---

### `POST /data/query`

Одна конечная точка для всех языков запросов. Она принимает GraphQL, SQL или Cypher и сама определяет, что получила.

Запросы Cypher также можно отправлять на выделенный эндпоинт `POST /query/cypher`.

**Тело запроса:**

```json
{
  "query": "{ orders { id } }",
  "params": {},
  "variables": {},
  "role": "org_admin"
}
```

Возвращает `{"data": ...}` для GraphQL, `{"columns": [...], "rows": [...]}` для SQL и Cypher.

---

### `POST /data/sql/explain`

Выполнить explain или analyze для SQL-выражения через управляемый конвейер.

Конечная точка оборачивает **управляемый** SQL в синтаксис EXPLAIN диалекта: ту инструкцию, которая на самом деле выполняется под ролью вызывающего, после RLS и маскирования. Поэтому вы видите план авторизованной версии запроса, а не исходного ввода.

**Тело запроса:**

```json
{
  "sql": "SELECT id, amount FROM orders",
  "role": "org_admin",
  "analyze": false
}
```

Установите `analyze: true`, чтобы выполнить EXPLAIN ANALYZE. Запрос выполняется, и план содержит реальные количества строк и тайминги. Не каждый диалект поддерживает ANALYZE; см. таблицу в разделе [Планы запросов и статистика](engines.md#query-plans-and-statistics).

**Ответ:** `{"plan": "<plan text or JSON>", "dialect": "trino", "analyzed": false}`

`400`, если диалект не поддерживает EXPLAIN, или если запрошен `analyze: true` для диалекта, который его не поддерживает (например, SQLite).

### `GET /data/engine/state`

Возвращает текущее состояние шарда движка без его пробуждения.

Интерфейс опрашивает эту конечную точку, чтобы показывать баннер запуска, пока движок стартует с холода. Она никогда не будит движок, поэтому опрос безопасен и не считается активностью для отключения по простою.

**Ответ:**

```json
{"state": "ready"}
```

Возможные значения:

| Состояние | Значение |
| --- | --- |
| `always-on` | Настольная версия, self-hosted или собственный (BYO) координатор — без управления жизненным циклом |
| `ready` | Шард запущен и принимает запросы |
| `starting` | Выполняется холодный старт |
| `stopped` | Шард масштабирован до нуля |

---

### `POST /data/engine/prewarm`

Инициировать пробуждение движка без выполнения запроса.

Сразу возвращает `202 Accepted`, а пробуждение идёт в фоне. Используйте это, когда движок нужен готовым к приходу первого запроса, например из планировщика, который запускает запросы через несколько минут.

**Ответ:** `202 Accepted`, тело `{"started": true}`

### `GET /data/rest/{domain_id}/{table_name}`

Автоматически сгенерированный обычный REST-эндпоинт для каждой зарегистрированной таблицы. Строка запроса сопоставляется с аргументами GraphQL, и запрос компилируется и выполняется через тот же конвейер (RLS, маскирование, маршрутизация), что и GraphQL.

**Параметры запроса:**

- `limit` — максимальное число строк (≥ 1)
- `offset` — пропустить строки (≥ 0)
- `fields` — имена полей через запятую в написании схемы GraphQL, в camelCase при соглашении об именах по умолчанию, например `?fields=orderId,amount` (по умолчанию — все скалярные поля). Имена полей в `filter` и `orderBy` следуют тому же написанию. JSON:API вместо этого принимает физическое имя колонки (`fields[orders]=order_id`).
- `filter` — JSON-массив объектов фильтра `{"field", "comparator", "value"}`. Значение читается как тип своего столбца, поэтому `"100"` в числовом столбце сравнивается как 100; значение, которое тип столбца не может вместить, возвращает `400`.
- `orderBy` — JSON-массив объектов сортировки `{"field", "direction"}`
- `params` — параметры таблицы одним JSON-объектом по именам параметров, например `?params={"region":"EU"}`. У таблицы, зарегистрированной поверх API, и у таблицы-запроса есть параметр для каждого входа, который принимает её источник. Чтение без обязательного параметра возвращает `400` с его именем, как и имя, для которого у таблицы нет параметра. Каждое значение проверяется по типу своего параметра.

Значения фильтров и параметров передаются как переменные рядом с текстом GraphQL, который строит эндпоинт, поэтому значение с кавычкой сравнивается так, как написано.

Аутентифицированная роль обязательна; неаутентифицированные запросы возвращают `401`. Спецификация OpenAPI для этих маршрутов предоставляется по адресу `GET /data/rest/openapi.json`, со Swagger UI по адресу `GET /data/rest/docs`.

**Кеш ответов:** включается заголовком запроса, `Cache-Control: max-age=N` или `x-provisa-cache: true` (см. [Заголовки запроса для кеша ответов](#response-cache-request-headers)). Каждый ответ содержит `X-Provisa-Cache: HIT|MISS`, а при попадании ещё и `X-Provisa-Cache-Age`.

#### Обозреватель OpenAPI / Swagger UI {: #openapi-swagger-ui-explorer }

Страница обозревателя OpenAPI (`/app/openapi`) встраивает Swagger UI в изолированный iframe. Спецификация ограничена ролью, поэтому видны только таблицы и столбцы, доступные текущей роли, а селектор домена может сузить её ещё. Интерфейс сам переключается между светлой и тёмной темой.

Страница загружает HTML спецификации через `fetch()`, а не через прямой `src` iframe. Так запрос несёт bearer-токен сессии, а собственные относительные запросы Swagger UI разрешаются относительно того же источника.

Если страницу открыть по NL-ссылке «Открыть в OpenAPI», она раскрывает целевую конечную точку, заполняет параметры запроса из URL, сгенерированного NL (например, `aggregate`, `groupBy`), и нажимает Execute, опрашивая DOM, чтобы каждый шаг завершился до начала следующего.

### `GET /data/jsonapi/{domain_id}/{table_name}`

Автоматически сгенерированный эндпоинт, совместимый с [JSON:API](https://jsonapi.org), для каждой зарегистрированной таблицы. Те же RLS, маскирование и маршрутизация, что и в GraphQL.

**Заголовок `Accept`:** должен включать `application/vnd.api+json` (медиа-тип JSON:API), иначе запрос вернёт `406`.

**Параметры запроса:**

- `fields[<type>]` — разреженные наборы полей, например `?fields[orders]=amount`. Имена — это физические имена колонок, например `fields[orders]=order_id`, так же как в `filter[...]`, `sort` и ключах выдаваемых атрибутов. REST вместо этого принимает написание GraphQL (`fields=orderId`).
- `filter[<col>]` / `filter[<col>][<op>]` — например `?filter[region]=US`, `?filter[amount][gt]=100`. Значение читается как тип своего столбца; значение, которое тип не может вместить, возвращает `400`.
- `params` — параметры таблицы одним JSON-объектом по именам параметров, например `?params={"region":"EU"}`, как у REST-эндпоинта. Отсутствующий обязательный параметр возвращает `400` с его именем; неизвестное имя или значение неверного типа возвращает `400` с `source.parameter`, равным `params`. Ссылки пагинации сохраняют параметр.
- `sort` — через запятую, префикс `-` для убывания, например `?sort=-created_at,amount`
- `page[number]` / `page[size]` — пагинация
- `page[total]` — `true` подсчитывает строки, подходящие под фильтр, и возвращает `meta.total` и `links.last`. Без него ответ несёт только `links.self`, `links.first`, `links.prev` и `links.next`, и база данных не выполняет подсчёт. Любое значение, кроме `true` или `false`, возвращает `400`. Ссылки в ответе сохраняют параметр.
- `aggregate` — агрегатные функции через запятую, выполняемые вместо получения строк: `count`, `sum`, `avg`, `stddev`, `variance`, `min`, `max`. Используйте `?aggregate=count,sum`, чтобы запросить подмножество. Ответы агрегации возвращают `data: null` с результатами в `meta.aggregate`.
- `groupBy` — имена столбцов через запятую; используется вместе с `?aggregate=` для группировки результатов. Допустимы только столбцы из перечисления `DistinctOnColumn` таблицы; сервер возвращает `400` для любого столбца, который роль не может видеть.
- `includeNodes` — `true`, чтобы включить скалярные столбцы базовой таблицы (и скалярные поля присоединённых измерений, названных в `include=`) внутрь массива `nodes` каждой строки группы. Требуется, когда NL-запрос с группировкой также запрашивает детали измерения.

- `include` — имена связей через запятую в физическом написании, например `?include=order_items,shipment`: каждый связанный ресурс возвращается один раз в `included`, а каждый основной ресурс ссылается на то, что включает, в `relationships.<name>.data` (список идентификаторов ресурсов для связи «ко многим», один идентификатор или `null` для связи «к одному»).

Ответы — это объекты ресурсов с `type`/`id`/`attributes`. `id` ресурса — первичный ключ его таблицы: значение ключевого столбца или, для составного ключа, значения его столбцов в порядке ключа, соединённые через `:` (строка 2 заказа 7 в таблице с ключом `(order_id, line)` — это `7:2`). `:` или `\` внутри значения экранируется символом `\`. Таблица без объявленного первичного ключа использует свой столбец `id`; таблица без того и другого возвращает `400`, как и `include`, который до неё доходит. Ошибки следуют форме объекта ошибки JSON:API.

**Кеш ответов:** включается заголовком запроса, `Cache-Control: max-age=N` или `x-provisa-cache: true` (см. [Заголовки запроса для кеша ответов](#response-cache-request-headers)). Каждый ответ содержит `X-Provisa-Cache: HIT|MISS`, а при попадании ещё и `X-Provisa-Cache-Age`. Две расходящиеся формы возвращают `400` в виде объекта ошибки JSON:API.

#### Обозреватель JSON:API {: #jsonapi-explorer }

Страница обозревателя JSON:API (`/app/jsonapi`) — это браузерный UI поверх этих эндпоинтов. Выберите таблицу из списка, сгруппированного по доменам, затем настройте:

- **Поля (Fields)** — выберите, какие столбцы включить (разреженный набор полей); оставьте все невыбранными, чтобы запросить каждый столбец
- **Связи (Relationships)** — выберите имена связей, производных от внешних ключей, для подгрузки через `?include=`
- **Фильтр (Filter)** — поле, оператор (`eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `like`) и значение
- **Сортировка (Sort)** — одно поле, по возрастанию или убыванию
- **Агрегация (Aggregate)** — выберите столбцы группировки из проверенного сервером списка, затем отметьте одну или несколько агрегатных функций; при выбранных столбцах группировки флажок «Include nodes» добавляет скалярные столбцы базовой таблицы к каждой строке
- **Размер страницы (Page size)** — количество ресурсов на страницу, с навигацией первая/предыдущая/следующая/последняя

Результаты отображаются в отформатированном сводном представлении (карточки ресурсов с кликабельными якорями связей) или на вкладке необработанного JSON. Показывается актуальный URL запроса, который можно скопировать. Выбор таблицы и размер страницы сохраняются между сессиями в `localStorage`.

При переходе по ссылке NL «Open in JSON:API» обозреватель заранее выбирает таблицу и заполняет средство выбора агрегации из параметров запроса, сгенерированных NL, затем автоматически выполняет запрос.

### `POST /query/nl`

Отправить вопрос на естественном языке. Сервис запускает асинхронное задание и немедленно возвращает `202 Accepted` с `job_id`. Требует настроенного провайдера LLM в разделе конфигурации `ai_models`.

**Тело запроса:**

```json
{"q": "How many orders were placed last month?", "role": "org_admin"}
```

Возвращает `{"job_id": "<id>"}`. Превышение ограничения частоты запросов NL для роли возвращает `429` с заголовком `Retry-After`.

**Получение результата:**

- `GET /query/nl/{job_id}` — опрос. Возвращает документ задания.
- `GET /query/nl/{job_id}/stream` — SSE. Одно событие `branch` на каждую цель генерации по мере завершения, затем событие `done`.

Три цикла генерации (Cypher, GraphQL, SQL) выполняются параллельно, каждый проверяется компилятором и уточняется при ошибке. Подсказка (prompt) ограничена видимой схемой роли. Итоговый документ индексирует каждую ветвь по цели:

```json
{
  "job_id": "<id>",
  "state": "complete",
  "branches": {
    "cypher":  {"query": "MATCH ...", "result": [...], "error": null},
    "graphql": {"query": "{ ... }",   "result": {...}, "error": null},
    "sql":     {"query": "SELECT ...", "result": [...], "error": null}
  }
}
```

Ветка, исчерпавшая итерации, возвращает `query: null`, `result: null` и строку `error`. Каждый сгенерированный запрос выполняется с правами потребителя и управлением этапа 2; сервис никогда не обходит управление.

#### NL-группировка с деталями измерения {: #nl-group-by-with-dimension-details }

Возьмём NL-запрос с группировкой, который также проецирует столбцы из присоединённой таблицы измерения, например «число обращений по пользователям с именем и email». Исполнитель выводит пути через точку для каждого поля (`dim_paths`) из столбцов измерения в SELECT. Эти пути заполняют параметр `includeNodes=` в URL, сгенерированных для панелей JSON:API и OpenAPI, и эти панели запрашивают те же поля присоединённого измерения, что разрешили ветки SQL и GraphQL. Без них `includeNodes=true` вернул бы только собственные скалярные поля базовой агрегатной таблицы.

На панели gRPC сгенерированный `{Type}GroupByRequest` несёт `include_nodes` (bool) и `include` (повторяющаяся строка имён полей связи). Возвращаемый `{Type}GroupByRow` включает типизированное поле `nodes` со строками деталей измерения.

### `GET /data/graph-schema`

Возвращает представление схемы роли в виде графа: метки узлов и типы их связей, для клиентов Cypher/графа. Включает `pk_columns` для каждой метки узла, чтобы вызывающие могли определить столбцы первичного ключа.

**Ответ:** `application/json` с `node_labels` (каждая несёт `pk`/`pk_columns`) и `relationship_types`.

Каждый тип связи также несёт `junction_table_name` и `properties`. На ребре через связующую таблицу первое называет ассоциативную таблицу, через которую оно проходит, а второе перечисляет её столбцы, доступные как `r.attr` и для фильтрации в `WHERE`. На ребре по внешнему ключу имя равно `null`, а список пуст — так клиент их различает. Сама связующая таблица никогда не является меткой узла. Она и есть ребро, поэтому у неё нет метки в графовом клиенте и нет строки в `node_labels`.

### `GET /data/catalog`

Возвращает каталог роли, от которой выполняется запрос: таблицы, которые обслуживаются этой роли, в том виде, в каком их даёт перечень Arrow Flight.

**Ответ:** `{"tables": [{"path": ["<domain>", "<table>"], "schema": "<base64>"}]}`. `schema` — схема Arrow таблицы в кодировке Arrow IPC: каждая колонка под именем, по которому её читает SQL, с её зарегистрированным типом, описанием и метаданными ключей (`primary_key`, `references`) в метаданных поля. Команды и метрики не перечисляются.

Роль — та, что установил уровень аутентификации (`X-Provisa-Role` может запросить имеющуюся роль или набор через запятую). Развёртывание без провайдера аутентификации перечисляет весь каталог, как и перечень Flight. Драйвер JDBC читает этот маршрут, когда порт Flight недоступен.

### `GET /data/proto/{role_id}`

Возвращает автоматически сгенерированный файл `.proto` для роли.

**Ответ:** схема protobuf в формате `text/plain`.

`{role_id}` — это одна роль, которой обладает вызывающий, или набор таких ролей через запятую (`analyst,org_admin`), который обслуживается как мета-роль набора: объединение того, что предоставлено его участникам. Роль, которой вызывающий не обладает, отклоняется с `403 auth.role_not_assigned`, а идентификатор мета-роли, указанный напрямую, — с `403 auth.meta_role_named`. `?domains=a,b` сужает proto до этих доменов; домен, которого роль не достигает, отклоняется с `403 data.domain_not_accessible`. Роль без поверхности данных получает `404 data.no_proto_for_role`, неизвестная роль — `404 data.no_role`, а ещё не построенная модель — `503 data.schema_cache_not_ready`.

Каждая таблица в схеме роли порождает proto-`message`. Связи порождают вложенные поля сообщений. Сервис перечисляет RPC только для таблиц в корне схемы роли — тех же, что в её типе `Query` GraphQL; связанная таблица имеет своё сообщение и достигается через свою связь.

Добавьте `?domains=a,b`, чтобы ограничить файл этими доменами. Тогда сервис перечисляет RPC для собственных таблиц выбранных доменов; связанные с ними таблицы присутствуют как сообщения.

Файл следует за моделью. Он пересоздаётся вместе со схемой роли при каждом изменении модели или роли, в том числе для мета-роли. Отображение типов: `integer → int32`, `bigint → int64`, `varchar → string`, `decimal → double`, `boolean → bool`, `timestamp → google.protobuf.Timestamp`.

---

### `GET /data/subscribe/{table}`

Поток Server-Sent Events для уведомлений об изменениях в реальном времени из таблицы.

Доставка уведомлений использует подключаемого (pluggable) провайдера, выбираемого по типу источника: источники PostgreSQL используют `LISTEN/NOTIFY` (через asyncpg), источники MongoDB используют Change Streams (`collection.watch()`), а источники Kafka используют группы потребителей. Каждый провайдер реализует общий асинхронный интерфейс наблюдения (watch). Фильтрация RLS и валидация схемы применяются независимо от провайдера. Источники WebSocket и RSS также поддерживаются.

**Заголовок — `X-Provisa-Sink`:** установите на цель Kafka (например, `kafka://broker:9092/topic`), чтобы перенаправить события изменений в приёмник (sink) Kafka вместо ответа SSE. Сервер запускает потребителя приёмника и возвращает `202 Accepted` вместо открытого потока.

### `POST /data/sources/{source_id}/signal`

Сообщает Provisa, что источник изменился, без строк: приёмник сигнала изменения `signal`. Каждая таблица источника, сигнал изменения которой `signal` (собственный или, если его нет, сигнал источника), считается записанной, как при записи через Provisa: её закешированные ответы отбрасываются, материализованные представления над ней устаревают, и запрашивается сборка её реплики. Сборка таблицы, защищённой от нагрузки, ждёт своего внепикового окна. `?table=schema.table` сигнализирует одну таблицу.

Роли вызывающего нужно право записи, и она должна достигать домена каждой таблицы, которую сигнализирует. Ответ — `202 Accepted` с сигнализированными таблицами:

```json
{"signalled": ["public.orders"]}
```

Несуществующий источник или `table`, которой у него нет, отвечает `404`; источник без таблиц на сигнале изменения `signal` отвечает `409`, потому что обновлять было бы нечего.

## Административные REST-эндпоинты {: #admin-rest-endpoints }

### Конфигурация {: #config }

#### `GET /admin/config`

Скачать текущий `provisa.yaml` как `application/x-yaml` с заголовком `Content-Disposition: attachment`.

#### `PUT /admin/config`

Загружает исправленный YAML конфигурации. Сервер пишет резервную копию `.bak`, сохраняет новый файл, перезагружает из него настройки развёртывания и применяет его к хранилищу модели как явное однократное наполнение: то, что объявляет файл, добавляется или обновляется через хранилище модели, и ничего не удаляется. Последующий перезапуск читает настройки файла и никогда больше не применяет его модель; после первого запуска моделью владеет только хранилище модели.

**Тело запроса:** необработанное содержимое YAML.

**Ответ:**

```json
{"success": true, "message": "Config uploaded and applied"}
```

При сбое перезагрузки: `{"success": false, "message": "<error>"}`.

#### `GET /admin/config/live`

Выгружает модель в текущем виде как файл конфигурации. Он содержит настройки файла развёртывания, а каждый раздел модели читается из хранилища модели: хранилища, регионы, источники, домены, роли, продукты данных, термины глоссария, таблицы и их столбцы, связи, метрики, теги и их назначения, фильтры строк, команды, вебхуки, запланированные триггеры и правила именования. Применённый к пустому хранилищу модели, файл строит ту же модель. То, что развёртывание засевает в каждое хранилище (встроенные источники и их таблицы, системные домены, `org_admin` и `platform_admin`), не включается.

**Параметр запроса:** `sections` (необязательно) — список разделов модели через запятую, например `sources,tables`. Записываются только эти разделы; неизвестное имя даёт ответ 400 `settings.export_unknown_section`.

Endpoint открыт в любом развёртывании для вызывающего с правом на настройки развёртывания; раздел Файл конфигурации на странице администратора предлагает его как **Экспорт модели**.

Возвращает `application/x-yaml` с `Content-Disposition: attachment; filename=provisa.live.yaml`.

#### `GET /admin/config/diff`

Возвращает обе стороны сравнения конфигурации, `original` (исходное состояние при запуске) и `current` (текущее состояние), нормализованные одинаково, поэтому сравнение показывает только настоящие изменения и не учитывает перестановки и правки комментариев.

**Ответ:**

```json
{"original": "<yaml>", "current": "<yaml>"}
```

#### `POST /admin/config/patch`

Сгенерировать унифицированный diff-патч от базовой версии к отправленной конфигурации.

Отправьте исправленный YAML в теле запроса. Ответ — файл `text/x-patch` (`provisa.config.patch`), который `git apply` или `patch` применяют как есть; это удобно, чтобы проводить изменения конфигурации, сделанные в интерфейсе, через конвейер CI/CD.

### Настройки {: #settings }

#### `GET /admin/settings`

Возвращает текущие настройки платформы в формате JSON.

**Ответ:**

```json
{
  "redirect": {
    "enabled": true,
    "threshold": 10000,
    "default_format": "application/vnd.apache.parquet",
    "ttl": 3600
  },
  "sampling": {
    "default_sample_size": 1000
  },
  "cache": {
    "default_ttl": 300
  },
  "naming": {
    "domain_prefix": false,
    "convention": "apollo_graphql"
  },
  "relationships": {
    "auto_track_fk": true
  },
  "otel": {
    "endpoint": "http://otel-collector:4318",
    "service_name": "provisa",
    "sample_rate": 1.0,
    "support_endpoint": "",
    "support_redact_sql_literals": true,
    "support_redact_attributes": []
  }
}
```

#### `PUT /admin/settings`

Обновляет настройки платформы во время работы. Все поля необязательны, и меняются только ключи, присутствующие в теле.

**Тело запроса (частичный пример):**

```json
{
  "otel": {
    "support_endpoint": "https://telemetry.vendor.com/v1/traces",
    "support_redact_sql_literals": true,
    "support_redact_attributes": ["db.statement", "user.email"]
  },
  "cache": {"default_ttl": 600}
}
```

Обновляемые поля по разделам:

- `redirect`: `enabled`, `threshold`, `default_format`, `ttl`
- `sampling`: `default_sample_size`
- `cache`: `default_ttl`
- `naming`: `domain_prefix`, `convention` — записывает в файл конфигурации и вызывает согласование схемы
- `relationships`: `auto_track_fk` — управляет только отслеживанием внешних ключей. Связь на основе связующей таблицы (junction) объявляется при регистрации таблицы и никогда не выводится автоматически, поэтому эта настройка на неё не влияет.
- `otel`: `endpoint`, `service_name`, `sample_rate`, `support_endpoint`, `support_redact_sql_literals`, `support_redact_attributes`

**Ответ:**

```json
{"success": true, "updated": ["otel.support_endpoint", "cache.default_ttl"]}
```

```json
  "current": "trino",
  "persisted": "trino",
  "registry": [
    {"key": "trino", "label": "Trino (embedded)", "fields": [...]},
    {"key": "duckdb", "label": "DuckDB", "fields": []}
  ],
  "note": "Changing the federation engine takes effect after the service is restarted."
}
```

Ключ `current` — это движок, работающий прямо сейчас; `persisted` — то, что записано в файл конфигурации и будет загружено при следующем перезапуске. Они расходятся, если конфигурация была изменена, а сервис ещё не перезапущен.

#### `PUT /admin/federation-engine`

Сохранить выбор движка федерации.

**Тело запроса:**

```json
{"engine": "trino", "federation_engine_url": "http://trino-coordinator:8080"}
```

Выбор записывается в конфигурацию платформы и вступает в силу после следующего перезапуска сервиса, потому что движок выбирается один раз при загрузке.

### Политика домена {: #domain-policy }

#### `POST /admin/domain-policy`

Изменить политику доменов действующей организации (`use_domains` / `default_domain`).

Переключение ничего не удаляет. Оно отклоняется с `409` и кодом `settings.domain_policy_catalog_exists`, пока у действующей организации есть каталог: зарегистрированная таблица, источник или домен, которые развёртывание не добавило само. `params` отказа подсчитывают каждый вид (`tables`, `sources`, `domains`). Сначала удалите эти объекты, каждый своим действием, затем переключайте. Если файл конфигурации объявляет часть этого каталога, код — `settings.domain_policy_catalog_in_config`: следующая загрузка восстановила бы его, поэтому политика задаётся в файле конфигурации.

**Тело запроса:**

```json
{
  "use_domains": true,
  "default_domain": "default"
}
```

`use_domains: null` очищает переопределение организации и возвращается к настройке уровня развёртывания. `use_domains: false` требует `default_domain` (единственное имя домена, в который попадают все таблицы). Пересборка каталога синхронна; ответ возвращается, когда схемы готовы.

### Объектное хранилище {: #object-storage }

#### `GET /admin/org-storage`

Сообщает объём хранилища действующей организации относительно её платформенной квоты и указывает, зарегистрировала ли организация собственное хранилище.

Когда у организации зарегистрирован собственный DSN, её материализации попадают туда и больше не учитываются в квоте. Сам DSN никогда не возвращается.

#### `PUT /admin/org-storage`

Зарегистрировать (или очистить) собственное хранилище материализаций организации.

**Тело запроса:**

```json
{"storage_url": "s3://my-bucket/provisa?region=us-east-1&access_key=..."}
```

DSN проверяется на движке федерации до того, как его примут, поэтому непригодный DSN отклоняется при регистрации, а не через несколько часов при обновлении. Значение хранится зашифрованным и никогда не возвращается через GET.

Отправьте `storage_url: null`, чтобы очистить собственное хранилище организации и вернуть её материализации в платформенное хранилище (и квоту). Среда выполнения организации пересобирается в том же вызове, так что новое хранилище действует немедленно.

### Шифрование организации {: #org-encryption }

#### `GET /admin/org-encryption`

Возвращает текущий статус ключа организации: отпечаток, id и происхождение. Никогда не возвращает материал ключа.

Когда организация не задала ключ, возвращает `{"configured": false}`. Каждая организация начинает в этом состоянии и наследует ключ развёртывания.

#### `PUT /admin/org-encryption`

Задать или сменить ключ шифрования организации в состоянии покоя.

**Тело запроса:**

```json
{"key_b64": "<32 raw bytes, base64-encoded>"}
```

Не указывайте `key_b64`, чтобы Provisa сгенерировал ключ. Это самый безопасный вариант, потому что ключ никогда не попадает в буфер обмена или журнал запросов. Указав `key_b64`, вы приносите собственный ключ.

Смена ключа добавляет новую активную запись в кольцо ключей и сохраняет старую, так что данные, записанные под предыдущим ключом, остаются читаемыми. Смена ключа — это не перешифрование. Эндпоинта удаления нет: удаление последнего ключа сделало бы каждую обёрнутую полезную нагрузку нечитаемой.

Действующее кольцо ключей переподключается в том же вызове, так что следующая зашифрованная запись немедленно использует новый ключ.

### Импорт Hasura / DDN {: #hasura-ddn-import }

#### `POST /admin/import/hasura/preview`

Преобразовать архив проекта Hasura v2 или DDN в предлагаемую конфигурацию Provisa, ничего не записывая.

**Тело запроса:**

```json
{
  "filename": "my-project.zip",
  "content_b64": "<base64-encoded archive>",
  "flavor": "auto",
  "domain_map": {"public": "sales"},
  "source_overrides": {}
}
```

`flavor` — это `"auto"` (определяется по структуре архива), `"hasura_v2"` или `"ddn"`.

**Ответ:**

```json
{
  "config_yaml": "...",
  "warnings": ["..."],
  "summary": {
    "sources": 1, "domains": 2, "tables": 40,
    "columns": 180, "roles": 3, "relationships": 15, "rls_rules": 6
  }
}
```

Ничего не сохраняется. Предпросмотр не кешируется на стороне сервера; `apply` принимает предоставленный вами YAML, так что применяется именно то, что было проверено (и, возможно, отредактировано).

#### `POST /admin/import/hasura/apply`

Загрузить ранее предпросмотренную конфигурацию в действующую организацию.

**Тело запроса:**

```json
{"config_yaml": "<yaml string>"}
```

Импорт — это явное однократное наполнение хранилища модели действующей организации, то же применение, что и `PUT /admin/config`: он добавляет и обновляет через хранилище модели то, что объявляет импортированная конфигурация, с защитами и версиями, и не удаляет ничего, чего не упоминает. Поля `replace` нет. Каталоги движка объявленных источников, пулы организации и её схемы пересобираются до возврата ответа.

**Ответ:** `{"summary": {...}}` — количество того, что объявляет импортированная конфигурация.

### Действия (Функции и вебхуки) {: #actions-functions-and-webhooks }

Все эндпоинты находятся под префиксом `/admin/actions`.

Любой вызов из GraphQL, SQL, Cypher, Bolt, Arrow Flight, MCP `run_sql` или Provisa gRPC, проходит через один управляемый исполнитель. Он каждый раз одинаково применяет назначение команд (`visible_to`), право `write` для мутации и правила управления. Синтаксис вызова для каждого протокола см. в [docs/integrations.md](integrations.md#invoking-commands-across-protocols).

#### `GET /admin/actions`

Возвращает все отслеживаемые функции БД и вебхуки.

**Ответ:**

```json
{
  "functions": [
    {
      "name": "random_grpc_set",
      "implKind": "grpc",
      "binding": {"target": "localhost:50071", "method": "/provisa.demo.RandomData/GetRandomSet"},
      "returns": "",
      "returnSchema": {
        "type": "array",
        "items": {"type": "object", "properties": {"id": {"type": "integer"}, "region": {"type": "string"}}}
      },
      "arguments": [],
      "visibleTo": ["admin"],
      "domainId": "pet-store",
      "description": "Demo gRPC command returning random rows",
      "kind": "query"
    }
  ],
  "webhooks": [
    {
      "name": "add-pet",
      "url": "https://petstore.example.com/pets",
      "method": "POST",
      "kind": "mutation",
      "approved": true
    }
  ]
}
```

Каждый объект вебхука несёт булево поле `approved`. Вебхук становится одобренным, когда стюард выполняет его запрос на создание; объявленные в конфигурации вебхуки одобряются автоматически. Неодобренный вебхук зарегистрирован, но не предоставляется ни на одной поверхности.

#### `POST /admin/actions/functions`

Зарегистрировать отслеживаемую функцию (команду).

**Ключевые поля:**

| Поле | Обязательно | Описание |
| --- | --- | --- |
| `name` | Да | Уникальное имя команды |
| `kind` | Да | `"query"` → поле GraphQL Query; `"mutation"` → поле Mutation |
| `implKind` | Нет | Способ выполнения команды — см. таблицу ниже (по умолчанию `source_procedure`) |
| `binding` | Нет | Детали подключения, специфичные для `implKind` (объект JSON) |
| `returnSchema` | Нет | JSON Schema `{type:"array", items:{type:"object", properties:{...}}}` — делает команду возвращающей набор строк на каждой поверхности |
| `arguments` | Нет | Определения аргументов `[{name, type}]`; порядок позиций важен для вызывающих через SQL и Bolt |
| `visibleTo` | Нет | ID ролей, которым назначена команда (пусто: каждая роль). `mutation` дополнительно требует права `write` |
| `domainId` | Нет | Домен для размещения в GraphQL и контроля доступа |

**Значения `implKind`:**

| `implKind` | Что выполняется | Поля `binding` |
| --- | --- | --- |
| `source_procedure` | Хранимая процедура в зарегистрированном источнике (по умолчанию) | `sourceId`, `schemaName`, `functionName` |
| `script` | Скрипт на стороне сервера (хост-код) | `script` |
| `http` | Исходящий HTTP-вызов | `url`, `method` |
| `grpc` | Исходящий gRPC-вызов к внешнему серверу | `target`, `method` |
| `python` | Python-функция, размещённая в Provisa (хост-код) | `callable` (например, `"demo.py_functions:random_dataset"`) |

`script` и `python` — это хост-код. Пока настройка развёртывания `commands.allow_host_code` выключена, а по умолчанию она выключена, регистрация, обновление или вызов такой команды отклоняется с HTTP 403 и кодом `functions.host_code_refused` (см. [Хост-код](commands.md#host-code)).

Демонстрационная команда `random_grpc_set` (`implKind: grpc`) показывает на практике команду, возвращающую набор, с `returnSchema`; она находится в `config/provisa-install.yaml`.

#### `PUT /admin/actions/functions/{name}`

Обновить отслеживаемую функцию по имени.

#### `DELETE /admin/actions/functions/{name}`

Удалить отслеживаемую функцию по имени.

#### `POST /admin/actions/webhooks`

Регистрирует отслеживаемый вебхук. Регистрация или изменение вебхука ставит в очередь запрос на одобрение стюардом, и вебхук становится активным на всех поверхностях только после одобрения стюардом. Вебхуки, объявленные в конфигурации, одобряются автоматически. **Поля тела запроса:** `name`, `url`, `method`, `timeoutMs`, `returns`, `inlineReturnType`, `arguments`, `visibleTo`, `domainId`, `description`, `kind`.

#### `PUT /admin/actions/webhooks/{name}`

Обновить отслеживаемый вебхук по имени. Любое редактирование сбрасывает одобрение в статус ожидания до повторного одобрения.

#### `DELETE /admin/actions/webhooks/{name}`

Удалить отслеживаемый вебхук по имени.

#### `POST /admin/actions/test`

Протестировать действие (функцию или вебхук) по имени.

### Admin GraphQL

#### `POST /admin/graphql`

Эндпоинт Strawberry GraphQL для всех операций admin: CRUD источников и таблиц, управление связями, конфигурация доменов, правила RLS, контроль кеша, соглашения об именовании, управление запланированными задачами и компиляция запросов.

```graphql
# Scheduled tasks
mutation { toggle_scheduled_task(name: "daily-report", enabled: false) { success } }

# Compile a query (returns enforcement metadata and routed SQL)
mutation {
  compile_query(input: {role: "admin", query: "{ orders { id } }"}) {
    sql semantic_sql trino_sql direct_sql route route_reason sources root_field
    enforcement { rls_filters_applied columns_excluded masking_applied }

}
```

## Эндпоинт Arrow Flight {: #arrow-flight-endpoint }

Порт `8815`. Нативный колоночный транспорт Arrow поверх gRPC.

Запросы и обнаружение каталога доступны на одном и том же соединении. Полный конвейер управления (RLS, маскирование, сэмплирование) применяется к каждому запросу.

Обнаружение каталога (`list_flights`, `get_flight_info`, `get_schema` и тикет без `query`) перечисляет то, что предоставлено роли вызывающего. При включённой аутентификации три вызова без тикета берут учётные данные из заголовка вызова `authorization: Bearer`, а роль — из `x-provisa-role`, и без учётных данных отклоняются; см. [Интеграции](integrations.md).

**Формат тикета** (JSON):

```json
{"query": "{ customers { name email } }", "role": "analyst", "variables": {}}
```

**Использование (Python):**

```python
import pyarrow.flight as flight

client = flight.FlightClient("grpc://localhost:8815")
ticket = flight.Ticket(b'{"query": "{ orders { id amount } }", "role": "admin"}')
# Stream batch-by-batch
for batch in client.do_get(ticket):
    process(batch.data)
# Or read all at once
table = client.do_get(ticket).read_all()
```

Когда доступен прокси Zaychik Flight SQL (порт 8480), пакеты записей передаются потоком от начала до конца без полной материализации. При недоступности Zaychik происходит откат к материализации через слой федеративных запросов.

**Предупреждения.** То, что ответ сообщает о себе, передаётся в потоке как `app_metadata` пакета без строк: `{"provisa_warnings": [{"code", "params", "message"}]}`. Предупреждения, известные до чтения строк, приходят в пакете без строк перед ними. Предупреждение, известное только после чтения строк, приходит во втором пакете без строк, последнем в потоке: `statement.rows_cut` говорит, что ответ был обрезан на лимите строк и подходят ещё строки. Читайте `app_metadata` в каждом пакете, включая последний.

## Эндпоинт Protobuf gRPC {: #protobuf-grpc-endpoint }

Порт `50051` (переопределяется переменной окружения `GRPC_PORT` или конфигурацией `server.grpc_port`).

Передайте роль в ключе метаданных gRPC `x-provisa-role`. Если он отсутствует, сервер прерывает выполнение с `UNAUTHENTICATED`.

Скачайте специфичный для роли proto по адресу `GET /data/proto/{role_id}`. Отображаются только таблицы и столбцы, видимые этой роли.

```proto
service ProvisaService {
  rpc QueryOrders (QueryOrdersRequest) returns (stream Orders);
  rpc InsertOrders (InsertOrdersRequest) returns (InsertOrdersResponse);
}
```

Каждая таблица в корне схемы роли порождает потоковый RPC `Query{TypeName}`. Это те таблицы, которые перечисляет тип `Query` GraphQL этой роли. Таблица, до которой роль добирается только через связь, не имеет собственного RPC, так же как у неё нет корневого поля в GraphQL. RPC `Insert{TypeName}` существуют ради симметрии схемы, но завершаются с `UNIMPLEMENTED`.

**Параметры.** У таблицы с параметрами (таблицы, зарегистрированной поверх API, или таблицы-запроса) есть сообщение `{TypeName}Params` с необязательным полем на каждый параметр, названным без префикса `_nf_`, и `Query{TypeName}Request` несёт его как `params`. Каждое заданное там значение доходит до источника как параметр, связанный в инструкции; имя, не являющееся параметром таблицы, отклоняется с `INVALID_ARGUMENT`, а чтение без обязательного параметра отклоняется с его именем. HTTP-прокси gRPC принимает те же значения в объекте `params` тела (HTTP 400, код `data.invalid_parameter`, для неизвестного имени или значения неверного JSON-типа).

Метод, не входящий в сервис роли вызывающей стороны, отвечает `UNIMPLEMENTED`.

`grpc_reflection.v1alpha` включён для обнаружения сервисов без предварительно скомпилированного proto. Рефлексия описывает каждому вызывающему сервис той роли, от имени которой он действует: тот же `.proto`, который эта роль скачивает через `GET /data/proto/{role_id}`. Она перечисляет по именам сервис Provisa и сервис рефлексии и описывает файл сервиса Provisa.

Вызов рефлексии идентифицируется так же, как любой другой вызов gRPC. При включённой аутентификации роль берётся из учётных данных вызывающего. При отключённой аутентификации укажите роль в `x-provisa-role`; в развёртывании, обслуживающем более одной организации, укажите также организацию в `x-provisa-org`. Вызов без них отклоняется с `UNAUTHENTICATED`. При отключённой аутентификации рефлексия остаётся выключенной, пока не задан параметр `server.grpc_allow_unsecured_reflection`.

```bash
grpcurl -plaintext -H 'x-provisa-role: analyst' localhost:50051 list
grpcurl -plaintext -H 'x-provisa-role: analyst' \
  -d '{}' localhost:50051 provisa.v1.ProvisaService/QueryOrders
```

Сервер gRPC запускается, когда модель, загруженная при старте, определяет сервис gRPC. Далее каждый вызов обслуживается по модели в её текущем состоянии: таблица, зарегистрированная или изменённая во время работы сервера, обслуживается и описывается уже следующим вызовом, без перезапуска.

#### RPC агрегации и группировки {: #aggregate-and-group-by-rpcs }

Когда у таблицы установлен `enable_aggregates`, сгенерированный proto включает два дополнительных RPC наряду с `Query{TypeName}`:

- **`Query{TypeName}Aggregate`** — возвращает агрегатные скаляры для таблицы (`count`; `sum`, `avg`, `stddev`, `variance` для каждого числового столбца; `min`, `max` для каждого сравнимого столбца)
- **`Query{TypeName}GroupBy`** — возвращает одну строку на ключ группы с агрегатными подполями и, опционально, скалярами базовой таблицы и строками присоединённого измерения в поле `nodes`

Оба проходят через тот же конвейер агрегатов компилятора, что и корневые поля GraphQL `{field}_aggregate` и `{field}_group_by`, поэтому отдельной реализации агрегатов нет.

**Поле `funcs`.** Сообщение запроса принимает повторяющееся строковое поле `funcs`. Допустимые значения: `count`, `sum`, `avg`, `stddev`, `variance`, `min` и `max`. Когда `funcs` опущено, запрашивается каждая функция, которую схема предоставляет для этой таблицы. Когда оно задано, отображаются только названные функции. Если ни одна из названных функций не применима к типам столбцов таблицы, запрос откатывается к `count`.

**Поля `include_nodes` и `include`.** Запросы `Query{TypeName}GroupBy` могут установить `include_nodes: true`, чтобы включить скалярные столбцы базовой таблицы в поле `nodes` каждой строки. Повторяющееся строковое поле `include` называет поля связей «многие к одному», чьи скалярные столбцы также вкладываются внутрь `nodes`. Это соответствует поведению `?includeNodes=` / `?include=` в JSON:API.

## Драйвер JDBC {: #jdbc-driver }

Драйвер JDBC Provisa (`provisa-jdbc-<release>.jar`) предоставляет семантический каталог инструментам BI (Tableau, PowerBI, DBeaver).

**URL подключения:** `jdbc:provisa://host:port`

Домены сопоставляются со схемами JDBC. Таблицы используют свои зарегистрированные псевдонимы. Столбцы используют псевдонимы и отображают описания как `REMARKS`. Стандартные методы метаданных (`getPrimaryKeys`, `getImportedKeys`, `getExportedKeys`) предоставляют семантические связи как метаданные PK/FK.

**Поддержка SQL:** `SELECT * FROM <alias> [WHERE col = 'value']`.

По умолчанию драйвер запрашивает перенаправление Arrow IPC. Результаты передаются потоком пакет за пакетом через `ArrowStreamReader`, ограничены одним пакетом записей в памяти.

Подписки SSE доступны по адресу `GET /data/subscribe/{table}`. Доставка уведомлений использует подключаемого провайдера, выбираемого по типу источника: источники PostgreSQL используют `LISTEN/NOTIFY`, источники MongoDB используют Change Streams, а источники Kafka используют группы потребителей. ## Бизнес-глоссарий {: #business-glossary }

Бизнес-глоссарий сопоставляет физические имена полей, как они записаны в исходных базах, с общим человеческим словарём. Каждый столбец, зарегистрированный в модели, получает термин автоматически, поэтому вводить что-либо для наполнения глоссария не нужно. Кураторы добавляют определения, связи и экспертов поверх того, что выводит система.

### Как выводятся термины {: #how-terms-are-derived }

Когда Provisa регистрирует или обновляет столбцы таблицы, `normalize_term` (`provisa/core/glossary.py`) выполняется для каждого имени столбца и формирует каноническую фразу.

Нормализация применяет пять правил последовательно:

1. Разбиение по границам camelCase и символам-разделителям (`_`, `-`, `.`, `/`, пробел).
2. Приведение результата к нижнему регистру.
3. Расширение фиксированной таблицы сокращений (например, `cust` → `customer`, `amt` → `amount`, `dt` → `date`, `id` → `identifier`, `key` → `identifier`, `guid` → `identifier`).
4. Удаление конечного **токена-заместителя (proxy token)** (`identifier`, `code`, `index` или `reference`). Столбец, названный по своему ключу или коду, указывает на лежащее в основе понятие через значение-заместитель, поэтому термином должно быть само понятие. Последний оставшийся токен никогда не удаляется.
5. Уточнение **слишком общей фразы** концептом таблицы. Когда полная нормализованная фраза представляет собой голое слово-атрибут (`name`, `identifier`, `date`, `location`, `message`, `first name`, `last name` и подобные), термин становится `<table concept> <phrase>`: `employees.first_name` → `employee first name`, `orders.id` → `order identifier`. Один общий термин `name` для не связанных между собой таблиц объединил бы разные значения; уточнение вместо этого связывает каждый столбец с его охватывающим концептом. Концепт таблицы — это бизнес-имя таблицы, нормализованное с единственным числом главного существительного (`order_lines` → `order line`).

Псевдостолбцы нативных фильтров (с префиксом `_nf_`, или любой столбец, несущий `native_filter_type`) являются механизмом параметров запроса и не порождают термины.

Поскольку `id`, `key`, `pk` и `sk` — все раскрываются в `identifier` до проверки на заместитель, три физически разных имени столбца попадают точно на один и тот же термин:

| Физическое имя | После нормализации |
| --- | --- |
| `cust_id` | `customer` |
| `customerId` | `customer` |
| `CUSTOMER_KEY` | `customer` |
| `txn_amt` | `transaction amount` |

Первые три сводятся к одному термину. `transaction amount` сохраняет оба токена, потому что `amount` не является заменителем. Одиночный столбец `id` без предшествующих токенов сократить нельзя, поэтому он нормализуется в `identifier`, и термин не остаётся пустым.

Ключевые столбцы не получают нормализованный термин. Каждый столбец первичного ключа ставит свою ссылку на термин-класс своей таблицы, а каждый столбец объявленного внешнего ключа — на класс целевой таблицы, как бы он ни назывался. Таблица с ключом без класса предлагает черновой класс, названный по её понятию. О ролях и о том, как размещаются ключи, см. [Онтология](ontology.md#classes-properties-and-concepts).

### Жизненный цикл {: #lifecycle }

Термины **выводятся из принадлежности к семантическому слою**. Репозиторий таблиц — единственный путь записи: он сверяет столбцы таблицы при каждом сохранении и урегулирует термины, которые удаление оставляет без ссылок.

**Когда добавляется столбец:** Provisa ищет его термин по имени. Если термин существует, столбец получает на него ссылку, а термин, ставший устаревшим из-за потери последнего столбца, восстанавливается. Если термина ещё нет, создаётся черновой.

**Когда столбец исчезает** (изменение схемы или удаление таблицы), его ссылка удаляется, а термин **урегулируется**. Некурируемый термин без оставшихся ссылок удаляется вместе с рёбрами. Курируемый термин (с определением, ребром, экспертом, тегом или выводом из обращения) помечается устаревшим и сохраняется, как и любой термин, удаление которого оставило бы понятие без пути к данным.

У каждого термина один статус: `draft`, `live`, `deprecated` или `retired`. Его несут список, детали и мета-представление. Куратор меняет его только действиями статуса, описанными ниже; `PATCH`, задающий статус, отклоняется. Что означает каждый статус, см. в [Онтология](ontology.md#status).

### Эндпоинты курирования {: #curation-endpoints }

Все эндпоинты находятся под `/admin/glossary` и требуют настроенной организации. Чтение требует права `glossary_read`, а каждое изменение — `glossary_rw`, в пределах доменов, доступных вызывающему. Каждое изменение вызывает публикацию метаданных.

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/admin/glossary/terms` | Список терминов, каждый со своим `status` и числом `findings`. Параметры запроса: `q` (поиск по имени/определению), `include_deprecated` (по умолчанию `true`) |
| `GET` | `/admin/glossary/terms/{term_id}` | Получить детали термина: определение, статус, физические ссылки, типизированные рёбра, эксперты, теги |
| `POST` | `/admin/glossary/terms` | Создать понятие — термин без столбцов и таблиц |
| `PATCH` | `/admin/glossary/terms/{term_id}` | Переименовать, задать определение, задать домены понятия или переключить исключение из экспорта |
| `DELETE` | `/admin/glossary/terms/{term_id}` | Удалить термин, у которого нет столбцов |
| `POST` | `/admin/glossary/refs/move` | Перенести ссылку одного столбца на другой термин |
| `GET` | `/admin/glossary/terms/{term_id}/tables` | Список таблиц, к которым привязан класс |
| `POST` | `/admin/glossary/terms/{term_id}/tables` | Привязать таблицу к термину, сделав его классом таблицы |
| `DELETE` | `/admin/glossary/terms/{term_id}/tables/{table_id}` | Отвязать таблицу; её ключи возвращаются к её предложенному классу |
| `POST` | `/admin/glossary/terms/{term_id}/deprecate` | Пометить действующий термин устаревшим |
| `POST` | `/admin/glossary/terms/{term_id}/retire` | Вывести термин из обращения, перенеся его столбцы или таблицы на преемника |
| `POST` | `/admin/glossary/terms/{term_id}/restore` | Отменить вывод из обращения или пометку куратора об устаревании |
| `GET` | `/admin/glossary/terms/{term_id}/applied-history` | Столбцы и таблицы выведенного из обращения термина на момент коммита, предшествовавшего выводу |
| `GET` | `/admin/glossary/findings` | Каждый термин с замечаниями и его замечания |
| `POST` | `/admin/glossary/terms/{term_id}/edges` | Добавить типизированное ребро связи между двумя терминами |
| `DELETE` | `/admin/glossary/terms/{term_id}/edges` | Удалить ребро (параметры запроса: `to_term_id`, `rel_type`) |
| `POST` | `/admin/glossary/terms/{term_id}/experts` | Отметить пользователя как эксперта или автора для термина |
| `DELETE` | `/admin/glossary/terms/{term_id}/experts/{user_id}` | Удалить назначение эксперта/автора пользователя |
| `POST` | `/admin/glossary/terms/{term_id}/definition/generate` | Составить черновик определения для одного термина с использованием ИИ-модели организации — возвращает только текст, ничего не сохраняется до сохранения |
| `POST` | `/admin/glossary/definitions/generate` | Сгенерировать и сохранить определения для каждого термина, у которого их нет — никогда не перезаписывает текст, написанный человеком |
| `POST` | `/admin/glossary/relationships/generate` | Предложить и сохранить типизированные рёбра по всему глоссарию с использованием ИИ-модели организации |

Роль термина выводится из того, к чему он привязан, и никогда не задаётся. `PATCH` или создание, задающее `is_abstract`, отклоняется (`glossary.abstract_is_derived`).

**Тело `POST /admin/glossary/terms`:**

```json
{"name": "revenue", "definition": "Recognized net revenue after returns and discounts."}
```

**Тело `POST /admin/glossary/terms/{term_id}/edges`:**

```json
{"to_term_id": 42, "rel_type": "KIND_OF"}
```

Допустимые значения `rel_type`: `KIND_OF`, `PART_OF`, `SYNONYM_OF`, `RELATED_TO`, `VALID_VALUE_OF`, `DERIVED_FROM`, `REPLACES`, `PREFERRED_TERM_FOR`, `TRANSLATION_OF`, `ANTONYM_OF`.

**Тело `POST /admin/glossary/terms/{term_id}/experts`:**

```json
{"user_id": "alice@example.com", "kind": "author"}
```

Допустимые значения `kind`: `expert`, `author`.

**Тело `POST /admin/glossary/refs/move`:**

```json
{"table_id": 7, "column_name": "cust_id", "to_term_id": 12}
```

Перенос ссылки урегулирует термин, который её теряет. Используйте это, чтобы объединить два термина, которые нормализация оставила раздельными, например когда источник использует нестандартное сокращение, не покрытое таблицей расширений.

Перенос в класс отклоняется (`glossary.term_is_class`), как и перенос ключевого столбца, куда бы то ни было (`glossary.key_column_derived` с указанием столбца, его таблицы и его класса).

Если перенос снял бы со столбца `pii`, он отклоняется с `409 tag.move_loses` и перечнем столбцов с тегами, которые каждый теряет (`loses`) и получает (`gains`). Отправьте перенос повторно с `confirm_tag_loss`, перечисляющим каждый потерянный тег, или с `carry_tags: true`, чтобы поставить потерянные теги на термин, к которому переходит столбец:

```json
{"table_id": 7, "column_name": "email", "to_term_id": 12, "confirm_tag_loss": ["pii"]}
```

Вывод из обращения, а также сохранение или удаление связи, переселяющее ссылки ключей, принимают те же два поля.

Удаление термина, у которого ещё есть столбцы, возвращает `400 glossary.invalid` с перечнем таблиц. Сначала выведите его из обращения или перенесите его столбцы. Удаление класса сначала отвязывает его таблицы, так что их ключи возвращаются к их предложенным классам.

**Тело `POST /admin/glossary/terms/{term_id}/deprecate`:**

```json
{"reason": "Superseded by net revenue", "retire_on": "2026-12-31"}
```

`reason` обязателен. `retire_on` необязателен и не может быть в прошлом; в эту дату планировщик организации выводит термин из обращения. Пометить устаревшим можно только действующий термин.

**Тело `POST /admin/glossary/terms/{term_id}/retire`:**

```json
{"reason": "Merged into customer", "successor": 12}
```

`successor` обязателен, когда у термина есть столбцы или таблицы. Преемником свойства должно быть свойство или понятие, преемником класса — класс или понятие. Столбцы термина, или его таблицы вместе с ключами, переходят к преемнику, который получает ребро `REPLACES` к выведенному из обращения термину. Ответ перечисляет изменения тегов каждого перенесённого столбца. Каждый отказ — это `400` с названием правила: `glossary.reason_required`, `glossary.successor_required`, `glossary.successor_is_self`, `glossary.successor_retired` или `glossary.successor_role`.

**Ответ `GET /admin/glossary/findings`:**

```json
[
  {
    "term_id": 3,
    "term": "customer",
    "findings": [
      {
        "kind": "unlinked_tables",
        "code": "glossary.finding.unlinked_tables",
        "message": "the class is grounded in tables that same-entity relationships do not all join",
        "params": {"tables": "pg.public.customers, crm.public.contacts"}
      }
    ]
  }
]
```

Виды: `unlinked_tables`, `class_and_attribute`, `tag_wrong_kind`, `retirement_blocked` и `no_data`. Термин без замечаний не включается, а простой черновик замечанием не является. Эндпоинт только сообщает и ничего не меняет.

**Поле `export_excluded` в `PATCH /admin/glossary/terms/{term_id}`:**

```json
{"export_excluded": true}
```

Установка `export_excluded` в `true` исключает термин из всех снимков экспорта метаданных, независимо от его ссылок и роли. Возврат в `false` восстанавливает термин в снимке при следующей публикации. Данные курирования (определение, рёбра, эксперты) не затрагиваются.

### Курирование с помощью ИИ {: #ai-assisted-curation }

Настроенная ИИ-модель организации может составлять черновики определений и предлагать рёбра связей по всему глоссарию за одну операцию. Оба массовых действия требуют права `glossary_rw` и настроенной организации.

**`POST /admin/glossary/definitions/generate`**

Перебирает все термины глоссария, пропускает те, у которых уже есть определение, и просит ИИ-модель организации составить черновик для каждого из остальных. Каждый черновик сохраняется сразу, без шага редактирования, в отличие от конечной точки черновика для отдельного термина (`POST /admin/glossary/terms/{term_id}/definition/generate`). Определение, написанное человеком, никогда не перезаписывается, потому что термин с определением пропускается до любого вызова модели. Одно уведомление о публикации охватывает весь пакет.

Ответ:

```json
{"generated": 12}
```

`generated` — это количество терминов, получивших новое определение. Равно нулю, когда у каждого термина уже есть определение.

**`POST /admin/glossary/relationships/generate`**

Отправляет полный список терминов ИИ-модели организации с подсказкой, которая указывает десять допустимых типов рёбер (`KIND_OF`, `PART_OF`, `SYNONYM_OF`, `RELATED_TO`, `VALID_VALUE_OF`, `DERIVED_FROM`, `REPLACES`, `PREFERRED_TERM_FOR`, `TRANSLATION_OF`, `ANTONYM_OF`) и просит только уверенные предложения. Модель отвечает JSON-массивом; каждая запись проверяется перед любой записью: неизвестные имена терминов, само-рёбра и типы рёбер вне закрытого перечисления молча отбрасываются. Валидные предложения записываются идемпотентно через upsert. Повторный запуск действия не дублирует рёбра. Одно уведомление о публикации покрывает пакет. Эндпоинт немедленно возвращает `{"added": 0}`, когда глоссарий содержит менее двух неустаревших терминов.

Ответ:

```json
{"added": 5}
```

`added`: число записанных рёбер. Уже существовавшее ребро тоже считается: upsert проходит успешно, но данные ребра не меняются.

### Инструмент MCP `search_terms` {: #mcp-search_terms-tool }

```
search_terms(query, role=None, limit=25)
```

Ищет по именам и определениям терминов с сопоставлением подстроки без учёта регистра, до `limit` результатов. Каждый результат — полные детали термина: `name`, `definition`, `is_abstract`, `deprecated`, физические ссылки (с `source_id`, `schema_name`, `table_name`, `column_name`), типизированные рёбра и назначения экспертов.

Используйте `search_terms` перед написанием SQL, чтобы найти каждое физическое поле, представляющее понятие по имени. Например, поиск `"order date"` возвращает термин и все столбцы `order_dt`, `orderDate`, `ORDER_DATE` во всех зарегистрированных таблицах.

### Статистические инструменты MCP {: #mcp-statistics-tools }

```
describe(sql, role=None)
correlate(sql, columns, method="pearson", role=None)
regress(sql, target, features, kind="linear", role=None)
compare(sql, value, group, role=None)
forecast(sql, time, value, horizon, seasonal_periods=None, role=None)
```

Каждый инструмент принимает набор данных, заданный `sql`, и выполняет его через тот же управляемый конвейер, что и `run_sql`, от роли вызывающего: действуют правила строк, маскирование и редактирование, SQL, который конвейер отклоняет, завершается ошибкой так же, как в `run_sql`, а роль, которой у вызывающего нет, отклоняется. Каждый возвращает результаты, а не строки, вместе с использованным методом и подсчитанным `n`.

| Инструмент | Возвращает |
| --- | --- |
| `describe` | По каждому столбцу: `count`, `missing`, `distinct`; для числа — `mean`, `sd`, `min`, `max` и `quantiles` (p0, p5, p25, p50, p75, p95, p100); `top_values` (пять самых частых) |
| `correlate` | `matrix` корреляции `pearson` или `spearman` для числовых `columns` по строкам, полным во всех них, и это `n` |
| `regress` | `kind="linear"`: `coefficients` метода наименьших квадратов (`estimate`, `se`, `p_value`), `r_squared`, `adj_r_squared`. `kind="logistic"`: `target` с двумя значениями, `coefficients` максимального правдоподобия, `pseudo_r_squared`, `auc` и `positive_value`. Текстовый признак становится индикатором для каждого значения, кроме первого |
| `compare` | `n`, `mean` и `sd` каждой группы; для двух групп — t-критерий Уэлча (`t`, `df`, `p_value`) и d Коэна; для большего числа — однофакторный ANOVA (`f`, `df_between`, `df_within`, `p_value`) и эта-квадрат |
| `forecast` | `horizon` точек после последнего `time`, каждая с `value`, `lower` и `upper` (95%-й интервал прогноза), экспоненциальным сглаживанием (ETS) с аддитивной ошибкой, аддитивным трендом от 10 точек и аддитивной сезонностью, если задан `seasonal_periods` |

Движок вычисляет всё, что может, по каждой строке, которую читает роль: количества, количества различных значений, средние, стандартные отклонения, минимумы и максимумы для `describe`, а также `n`, среднее и дисперсию каждой группы для `compare`. Подогнанная модель, а также квантили и самые частые значения `describe` читают не больше `mcp.stats_max_rows` строк (Admin → Settings → Limits; по умолчанию 100 000). Каждый ответ, читающий строки, указывает `rows_read`, `row_cap` и `truncated`, а собственный лимит строк роли сообщается в `warnings`, как для `run_sql`.

Статистические инструменты возвращают только результаты, поэтому строки, стоящие за анализом, никогда не попадают в контекст модели: минимизация данных по умолчанию. То, что агент может узнать, ограничивает контроль доступа. Чтобы держать личности вне досягаемости агента, предоставьте его роли только те столбцы, которые никого не идентифицируют; роль, которая может прочитать столбец, может его агрегировать, а агрегаты по малым группам всё равно могут выявить отдельных людей. См. [Безопасность](security.md#statistics-over-mcp).

### Экспорт метаданных {: #metadata-export }

Граф терминов глоссария включён в каждый `MetadataSnapshot`, построенный `build_snapshot`.

Экспорт применяет те же фильтры, что и остальная часть снимка:

- Публикуются только действующие термины: находящиеся в обращении, определённые и связанные с термином, чей столбец или таблица публикуется.
- Столбец публикуется, когда проходит и фильтр **Data Product** (флаг `data_product` таблицы должен быть `true`), и фильтр **технических** столбцов (столбцы с тегом `technical` исключаются). Термин, все ссылки которого исключены таким образом, для экспорта не считается привязанным.
- Понятие публикуется, когда через граф связей доходит до опубликованного термина.
- Термин, помеченный `export_excluded`, исключается полностью.
- Устаревший термин публикуется со своими `status`, `status_reason` и `retire_on`, чтобы каждый каталог сопоставил его со своей отметкой об устаревании.
- Ребро между двумя терминами публикуется только тогда, когда публикуются оба конечных термина.

Каждый адаптер поставщика публикует граф терминов нативно, в контейнер глоссария, которым владеет Provisa и который он создаёт идемпотентно, и никогда в существующий глоссарий каталога:

| Провайдер | Контейнер | Термины | Отношения | Устаревание |
| --- | --- | --- | --- | --- |
| Apache Atlas | «Provisa Glossary» (API глоссария) | термины глоссария, определение в `longDescription` | KIND_OF → `isA`, SYNONYM_OF → `synonyms`, RELATED_TO/PART_OF → `seeAlso` | маркер shortDescription `[DEPRECATED]` |
| Atlan | глоссарий Provisa по стабильному qualifiedName | `longDescription` (никогда не человеко-редактируемый `userDescription`) | то же сопоставление Atlas | `certificateStatus = DEPRECATED` |
| DataHub | `urn:li:glossaryNode:provisa.<org>` | аспект `glossaryTermInfo` на термин | KIND_OF → Inherits, PART_OF → Contains (инвертировано), RELATED_TO/SYNONYM_OF → related terms | аспект устаревания; переименования следуют преемственности URN |
| OpenMetadata | глоссарий Provisa через `/v1/glossaries` | PUT с ключом fqn, переименования — PATCH-перепривязка по хранимому UUID | KIND_OF → нативная родительская иерархия, SYNONYM_OF → `synonyms`, остальные → `relatedTerms` | `entityStatus` |
| Collibra | домен типа «Глоссарий» «Provisa Glossary» | активы Business Term через Import API | нативные типы отношений Business Term | статус актива |

Значение имеет привязка, а не имя. Идентификатор поставщика каждого опубликованного термина записывается в `catalog_bindings` под URN термина (`provisa://<org>/terms/<name>`), и Provisa изменяет или удаляет элемент глоссария на стороне поставщика только тогда, когда владеет этой привязкой или элемент лежит в контейнере, который создал Provisa. Элемент глоссария без привязки Provisa пришёл из внешней системы и никогда не трогается. Обновления читают и объединяют, поэтому поля, добавленные стюардом к собственным терминам Provisa, сохраняются, и ничего не удаляется, когда термин выходит из снимка. Каждый термин несёт свою роль (класс, свойство или понятие) как свойство термина: `provisaRole` в пользовательских свойствах DataHub, пользовательское свойство в OpenMetadata, дополнительные атрибуты термина в Atlas, Purview и Atlan и атрибут `Provisa Role` в Collibra. В DataHub у узла Provisa организации есть дочерний узел для каждой роли: Classes, Properties и Concepts. В OpenMetadata нет узла глоссария, кроме термина, поэтому каждая роль — это групповой термин, содержащий термины верхнего уровня этой роли, а термин с родителем `KIND_OF` остаётся под этим родителем. Provisa также назначает каждый термин данным, которые он обозначает. Термин-класс назначается опубликованным таблицам, которые он заземляет, термин-свойство — своим опубликованным столбцам, а понятие — ничему. Каждое назначение записывается как собственное автоматическое назначение каталога и приписывается Provisa: метка `Automated` в OpenMetadata, связь термина, приписанная актору Provisa, в DataHub, семантическое назначение с источником Provisa в Atlas и Atlan и связь, созданная пользователем Provisa, в Collibra. Provisa добавляет и отзывает только их, поэтому назначение, сделанное стюардом, никогда не удаляется и не дублируется. Назначение не отзывается из-за того, что запрос завершился ошибкой. В Collibra назначения идут через API связей, а не через Import API, потому что импорт заменил бы связи стюарда того же типа. В Collibra, в частности, Import API заменяет то, что получает, и безопасность держится на ограничении: полезная нагрузка называет только активы внутри домена глоссария Provisa и связи только между терминами Provisa, поэтому глоссарии стюардов и их связи недосягаемы.

## Продукты данных {: #data-products }

Продукт данных группирует таблицы, публикуемые вместе для потребления, принадлежащие ровно одному домену. Поля следуют словарю ODPS (Open Data Product Standard) там, где у Provisa уже есть источник истины. Admin UI предоставляет продукты данных в разделе **Admin → Data Products**.

### Возможности {: #capabilities }

| Возможность | Предоставляет |
| --- | --- |
| `data_product_read` | Доступ на чтение к полю запроса `data_products` и странице admin «Data Products». По умолчанию предоставлена `org_admin`, `analyst`, `developer` и `modeler`. |
| `data_product_rw` | Мутации создания и удаления. Включает элементы управления New / Edit / Delete в UI. |

### Admin GraphQL

Все операции с продуктами данных проходят через `POST /admin/graphql`.

**Запрос:**

```graphql
query {
  data_products {
    id
    domain_id
    name
    owner_role
    team_role
    purpose
    limitations
    usage
    version
    status
    sla
    support
    custom_properties
  }
}
```

Требует `data_product_read`.

**Создание или обновление:**

```graphql
mutation {
  create_data_product(input: {
    id: "customer_360"
    domain_id: "sales"
    name: "Customer 360"
    owner_role: "data-product-owner"
    team_role: "sales-analytics"
    purpose: "Single view of a customer across all touchpoints."
    status: "active"
    version: "1.0.0"
  }) {
    success
    message
  }
}
```

`create_data_product` выполняет upsert: вызов с существующим `id` обновляет запись. Требует `data_product_rw`.

**Удаление:**

```graphql
mutation {
  delete_data_product(id: "customer_360") {
    success
    message
  }
}
```

Удаление продукта очищает `product_id` у каждой входящей в него таблицы, снимая её членство. Требует `data_product_rw`.

### Схема полей {: #field-schema }

| Поле | Тип | Обязательно | Примечания |
| --- | --- | --- | --- |
| `id` | `String` | Да | Машиночитаемый стабильный идентификатор, например `customer_360` |
| `domain_id` | `String` | Да | Владеющий домен. Входящие таблицы должны иметь тот же `domain_id` — несовпадения отклоняются при сохранении |
| `name` | `String` | Да | Отображаемое имя |
| `owner_role` | `String` | Нет | Роль, ответственная за этот продукт; отличается от стюарда домена |
| `team_role` | `String` | Нет | Роль, чьи носители сопровождают этот продукт день за днём; разрешается до конкретных людей |
| `purpose` | `String` | Нет | Что публикует этот продукт и зачем |
| `limitations` | `String` | Нет | Известные ограничения, оговорки или исключения |
| `usage` | `String` | Нет | Как потреблять этот продукт |
| `version` | `String` | Нет | например, `1.2.0` |
| `status` | `String` | Нет | например, `proposed`, `active`, `deprecated`, `retired` |
| `sla` | `String` | Нет | Обязательства по уровню обслуживания; проза — продукт охватывает несколько таблиц, и структурированный SLA не может однозначно назвать, к какому именно участнику он относится |
| `support` | `String` | Нет | Произвольный текст с рекомендациями по поддержке |
| `custom_properties` | `JSON` | Нет | Произвольные метаданные ключ-значение, не покрытые стандартными полями |

В модели есть ещё два поля, которые не доступны в `DataProductType` / `DataProductInput`. Они относятся только к Snowflake Horizon Catalog:

| Поле | Примечания |
| --- | --- |
| `support_contact` | Email или URL; обязателен для манифестов листинга организации Horizon Catalog |
| `publish` | `true` для немедленной публикации листингов Horizon; новые листинги по умолчанию имеют статус DRAFT |

### Членство таблиц {: #table-membership }

Таблица входит в продукт данных, когда в форме редактирования таблицы задано её поле `product_id`. Список предлагает только продукты, чей `domain_id` совпадает с доменом таблицы, поэтому таблице домена `marketing` никогда не будет предложен продукт домена `sales`.

Команды в том же домене также могут быть назначены участниками.

### Фильтр экспорта метаданных {: #metadata-export-filter }

`build_snapshot` применяет `data_products_only=True` при каждой публикации каталога. Таблицы без `product_id` исключаются из снимка вместе с их рёбрами связей, рёбрами происхождения и тегами управления. Источники и домены публикуются всегда. Термины глоссария публикуются только тогда, когда хотя бы одна из их физических ссылок принадлежит экспортированной (входящей в продукт) таблице.

Продукт без экспортированных участников не получает записи в снимке, потому что перечень без участников исказил бы представление каталога о продукте.

### Поддержка продуктов данных по целевому каталогу {: #data-product-support-by-catalog-target }

`MetadataSnapshot.data_products` достигает каждого адаптера, но только адаптеры, чья платформа имеет нативное понятие продукта данных, публикуют его как отдельную сущность; остальные публикуют входящие таблицы (уже отфильтрованные выше) без группировки по продукту.

| Цель | Представление продукта данных |
| --- | --- |
| Snowflake Horizon | Каждый продукт становится `SHARE` над физическими адресами входящих в него таблиц, обёрнутым во внутренний `CREATE ORGANIZATION LISTING` — нативный продукт данных Horizon Catalog. `publish=true` немедленно публикует листинг вживую; иначе он попадает в статус DRAFT. |
| BigQuery Dataplex | Каждый продукт становится листингом Analytics Hub через `/v1/dataProducts`. |
| OpenMetadata | Каждый продукт становится нативной сущностью `DataProduct` (`/api/v1/dataProducts`) с владением, производным от домена. |
| DataHub | Каждый продукт становится нативной сущностью `dataProduct` (`urn:li:dataProduct:...`) с собственными аспектами `dataProductProperties`/владения. |
| Collibra | Каждый продукт становится активом типа community `Data Product`, связанным со своими входящими таблицами через отношение `Data Product groups Table`. |
| Atlan | Публикуется как предполагаемый (guess) пользовательский typedef `DataProduct` — у Atlan нет документированного стабильного имени типа для этого понятия, поэтому сопоставление выполняется по best-effort. |
| Apache Atlas | Публикуется как пользовательский typedef `provisa_data_product` с отношением `provisa_data_product_members` — у Atlas нет нативного типа сущности продукта данных. |
| OpenLineage | Отдельной сущности нет; входящие таблицы несут пользовательскую фасету `provisa_data_product`, называющую владеющий продукт. |
