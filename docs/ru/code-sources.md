# Источники Node и Python

Иногда нужные вам данные скрыты за кодом, который ваша команда уже написала: модель скоринга, клиент внутреннего сервиса, скрипт, приводящий в порядок выгрузку. Источник Node или Python позволяет отдавать этот код в виде таблиц. Вы помечаете функции, которыми хотите поделиться, указываете Provisa, где лежит код, и каждая помеченная функция становится таблицей, которую любая роль читает по тем же правилам, что и любую другую таблицу.

## Во что превращается функция {: #what-a-function-becomes }

Provisa читает объявления самого кода: теги JSDoc и типы TypeScript для Node, docstring и аннотации типов для Python. Значение имеют три тега.

| Тег | Становится |
|---|---|
| `@table` | Таблицей. Функция возвращает список или итерируемый объект, и каждый элемент — это строка |
| `@command` | Командой, которая выполняется по запросу |
| `@stream` | Живой таблицей. Функция — генератор, и каждая строка отправляется, как только она выдана |

Функция без тега игнорируется. Незнакомый Provisa тег отклоняется, как и тип, который он не может отобразить. Отказ называет функцию и перечисляет все проблемы сразу, так что вы исправляете их за один проход.

Тип строки задаёт столбцы. Текст, числа, логические значения, даты и метки времени отображаются в свои типы столбцов, списки остаются списками, а вложенные объекты становятся именованными типами. В TypeScript тип строки — это интерфейс, псевдоним типа или класс. В Python — dataclass, `TypedDict`, `NamedTuple`, модель Pydantic или любой класс с аннотированными полями. Строки модели Pydantic передаются в том виде, в каком их возвращает `model_dump(by_alias=True)`, поэтому поле с псевдонимом становится столбцом с именем этого псевдонима. Собственная документация поля становится описанием его столбца при регистрации таблицы: doc-комментарий к свойству TypeScript или `Field(description=...)` в Pydantic. Когда тип строки нестрогий (`any`, `unknown` или `Record` в TypeScript, `Any` или `dict` в Python), Provisa один раз вызывает функцию без аргументов и предлагает столбцы по вернувшимся строкам. Если у функции есть обязательный параметр, так её вызвать нельзя, и столбцы вы типизируете сами при регистрации таблицы.

Параметры функции становятся параметрами таблицы. Параметр без значения по умолчанию обязателен, поэтому чтение без него отклоняется ещё до запуска вашего кода. Параметр со значением по умолчанию необязателен; если его опустить, применяется ваше значение по умолчанию. Стюард всё равно может сделать необязательный параметр обязательным.

## Откуда берётся код {: #where-the-code-comes-from }

Код закреплён, поэтому источник всегда выполняет ровно то, что было зарегистрировано:

- **Пакет**: пакет npm для Node или пакет PyPI для Python, точной версии.
- **Git-репозиторий**: полный коммит из 40 символов, с подкаталогом, если код лежит не в корне.
- **Загрузка**: архив `.zip`, `.tgz` или `.tar.gz` с кодом.

Код Node выполняется на Node.js, Bun или Deno — на ваш выбор. Код Python выполняется на Python, который поставляется с Provisa. Если у кода больше одного модуля Python верхнего уровня, укажите в поле **Входной модуль**, через какой в него входить.

## Установка зависимостей {: #installing-dependencies }

Коду с зависимостями нужен lockfile, и каждая установка следует ему в точности. Без него пакет, объявляющий зависимости, отклоняется, и отказ подсказывает добавить lockfile.

| Среда выполнения | Lockfile |
|---|---|
| Node.js | `package-lock.json` или `npm-shrinkwrap.json` |
| Bun | `bun.lock` или `bun.lockb` |
| Deno | `deno.lock` |
| Python | `uv.lock` (со своим `pyproject.toml`), `pylock.toml` или `requirements.txt` с `--hash` в каждой строке |

Lockfile необязателен, но без него две установки одного и того же кода могут различаться, и тест, который проходит сегодня, может завтра упасть на новой версии зависимости. Чтобы каждая установка была одинаковой, код должен содержать lockfile, или вы создаёте его и указываете здесь. Собранный образ уже зафиксирован. Когда вы собираете образ источника ([Собрать образ](#running-on-a-remote-host)), его зависимости оказываются внутри, и если именно этот образ проходит ваше тестирование и CI/CD, то запускается тот же образ, который вы проверили. Lockfile важен для режима dev и для каждой новой сборки образа. Код со своим lockfile устанавливается по нему: репозиторий Git или загрузка, в которых он есть, или пакет npm, автор которого опубликовал `npm-shrinkwrap.json` (npm никогда не публикует `package-lock.json`). Код без lockfile устанавливается с незафиксированными зависимостями: репозиторий Git или загрузка без lockfile, большинство пакетов npm и пакеты Python из PyPI, в wheel которых для него нет места. Укажите lockfile рядом с таким кодом, чтобы каждая установка была одинаковой. Некоторому коду lockfile не нужен, потому что способ его распространения уже фиксирует каждую зависимость.

Ни одному пакету не разрешено запускать собственные скрипты установки: npm устанавливает с `--ignore-scripts`, а Python ставит только wheels и никогда не собирает из дистрибутива исходного кода.

Пакеты берутся из собственных реестров вашей организации, если они есть. Администратор один раз вносит ваши реестры npm, индексы PyPI и хосты Git в разделе **Admin → Реестры пакетов**, и каждый источник Node и Python организации устанавливается через них. Публичному реестру npm и публичному PyPI запись не нужна. См. [Реестры пакетов](package-registries.md).

Установка кэшируется по хэшу содержимого кода, так что один и тот же код устанавливается один раз.

## Песочница {: #the-sandbox }

Ваш код выполняется в собственном рабочем процессе, в песочнице. Он может читать свой установленный код и больше ничего на диске. Он достаёт только до хостов из списка разрешённого исходящего трафика развёртывания, через прокси, который запускает Provisa, и никогда — до собственных портов Provisa. Хост, который не может обеспечить песочницу, отказывается запускать рабочий процесс и называет, чего не хватает, вместо того чтобы выполнить код без ограничений. В Windows источники кода отклоняются.

## Секреты {: #secrets }

Коду, который вызывает платный API, нужен его ключ, а ключу место в хранилище секретов вашей организации, а не в коде. В разделе **Secrets** формы источника выберите секреты организации, которые код может читать. В файле конфигурации перечислите их в mapping источника:

```yaml
mapping:
  secrets: [openrouter]
```

Имя само по себе означает секрет организации с этим именем. Чтобы вместо этого прочитать переменную окружения развёртывания, укажите ссылку: `secrets: {openrouter: "${env:OPENROUTER_API_KEY}"}`. Список ссылается на хранилище и никогда не копирует значение, поэтому конфигурация, которая называет секрет, ещё никем не сохранённый, всё равно загружается.

Ваш код получает одну переменную окружения, `PROVISA_SERVICES`, и читает секрет из `$PROVISA_SERVICES/secrets/<name>`, когда он нужен. На Python:

```python
import os, urllib.request
key = urllib.request.urlopen(f"{os.environ['PROVISA_SERVICES']}/secrets/openrouter").read().decode()
```

На TypeScript:

```typescript
const key = await (await fetch(`${process.env.PROVISA_SERVICES}/secrets/openrouter`)).text();
```

Запрос идёт через тот же исходящий прокси, что и остальной трафик вашего кода, и прокси отвечает на него сам. Больше ничего из Provisa этим путём недоступно. Адрес содержит токен, который есть только у воркера этого источника; он читает только имена, перечисленные источником, и перестаёт работать, когда воркер останавливается. Каждое чтение разрешает секрет в хранилище в этот момент, поэтому сменённый секрет действует со следующего чтения.

Имя, которого источник не перечисляет, отклоняется, как и секрет, который не удаётся разрешить. Отказ называет секрет, но никогда его значение. Каждое чтение записывается в журнал аудита организации с источником, именем и временем, и никакое значение никогда не попадает в лог. Хост API всё равно должен быть в списке разрешённого исходящего трафика.

## Вызов модели {: #calling-a-model }

Ваш код может вызывать языковую модель через Provisa, не храня ключ поставщика. `$PROVISA_SERVICES/llm/v1` — это совместимый с OpenAI эндпоинт, поэтому любой SDK OpenAI работает, если указать там его базовый URL. Адрес и есть учётные данные, поэтому ключом, который просит SDK, может быть любой текст. На Python:

```python
import os
from openai import OpenAI

client = OpenAI(base_url=f"{os.environ['PROVISA_SERVICES']}/llm/v1", api_key="unused")
reply = client.chat.completions.create(
    model="provisa:sql_generation",
    messages=[{"role": "user", "content": "Summarise this account's last quarter."}],
)
```

На TypeScript:

```typescript
import OpenAI from "openai";

const client = new OpenAI({ baseURL: `${process.env.PROVISA_SERVICES}/llm/v1`, apiKey: "unused" });
const reply = await client.chat.completions.create({
  model: "provisa:sql_generation",
  messages: [{ role: "user", content: "Summarise this account's last quarter." }],
});
```

Называйте модель по её роли, в виде `provisa:<role>`: вы получаете ту модель, которую ваша организация назначает этой роли в **Admin → AI Models**, и она следует этому выбору, когда администратор его меняет. Можно назвать модель и напрямую, если она назначена какой-либо роли. Для эмбеддингов `$PROVISA_SERVICES/llm/v1/embeddings` принимает любую из векторных моделей вашей организации. Любая другая модель отклоняется с указанием имени. Вызов уходит через собственных поставщиков, эндпоинты и ключи вашей организации, а то, что он отправляет, сначала проходит через правила маскирования Provisa. Потоковая передача не поддерживается: отправляйте `stream: false`, это значение по умолчанию.

Каждый вызов записывается для источника, с моделью, её токенами и стоимостью по записи модели в **Polly model prices**, и попадает в журнал аудита организации. Чтобы ограничить расходы источника, задайте **LLM monthly cap** в его форме, в USD. В файле конфигурации это задаётся в mapping:

```yaml
mapping:
  llm: {cap_usd: 20}
```

Источник с лимитом может вызывать только модели, у которых там есть цена. Когда его расходы за месяц (UTC) достигают лимита, его вызовы отклоняются до смены месяца. Вызовы, уже идущие в момент достижения лимита, всё же завершаются, поэтому месяц может закончиться немного выше лимита.

## Сервисы Provisa {: #provisas-services }

Ваш код может импортировать модуль, который Provisa предоставляет везде, где код выполняется: `provisa_services` в Python и `@provisa/services` в Node.js, Bun и Deno. Ничего устанавливать не нужно, и его нет ни в одном реестре пакетов. Вне Provisa модуля не существует, поэтому тесты ваших функций подменяют его моком.

```python
import provisa_services as ps

region = ps.settings.get("region")
rates = ps.cache.get("rates") or fetch_rates()
ps.cache.set("rates", rates, ttl=3600)
```

```typescript
import { settings, cache } from "@provisa/services";

const region = await settings.get("region");
const rates = (await cache.get("rates")) ?? (await fetchRates());
await cache.set("rates", rates, 3600);
```

| Вызов | Что он делает |
|---|---|
| `secrets.get(name)` | Один из объявленных секретов источника, прочитанный из хранилища сейчас. См. [Секреты](#secrets). |
| `settings.get(name, default)` | Одна из настроек источника, из раздела **Settings** его формы, которую steward может изменить, не меняя код. Если её нет и нет значения по умолчанию, вызывается ошибка. |
| `cache.get(key, default)`, `cache.set(key, value, ttl)`, `cache.delete(key)` | Собственный кэш источника, общий для всех его воркеров. Значение — всё, что может хранить JSON, до 1 МБ, хранится `ttl` секунд или пока его не заменят. |
| `vectors.upsert(items, model)`, `vectors.search(query, k, model)`, `vectors.embed(texts, model)`, `vectors.delete(ids)` | Собственная векторная коллекция источника для его справочных данных. У элемента есть `id` и `text` или `vector`; текст векторизуется одной из векторных моделей вашей организации. Искать по вашим управляемым таблицам она не может: их данные попадают в код только как параметры. |
| `http.get(url)`, `http.post(url, ...)` | Запрос, который Provisa выполняет для кода, через исходящий прокси и центры сертификации развёртывания. Хост должен быть в списке разрешённого исходящего трафика, и каждый запрос записывается в журнал аудита. |
| `llm.chat(model, messages)`, `llm.embeddings(model, input)`, `llm.base_url()` (`llm.baseUrl()` в JavaScript) | LLM-сервис Provisa. См. [Вызов модели](#calling-a-model). |
| `dq.dataset(name)`, `dq.product(id)` | Качество данных набора данных (`domain.table` или id его таблицы) или продукта данных так, как метадомен показывает его роли запроса, который обслуживает ваш код. Для набора данных: таблицы проверок, сканирующие его, каждая с описанием, контрактом, назначенным продуктом и последним запуском (результат, время и неудачные проверки), а также его профили с последним запуском каждого. Для продукта: его обещания, ожидания, партнёрские и осиротевшие проверки. |
| `log(message, level, fields)`, `metric(name, value, kind, attributes)` | Строка лога и точка метрики с именем `code_source.<name>`, привязанные к запросу, который обслуживает ваш код. |

Вызов, который сервис отклоняет, вызывает `ServiceError` с названием сервиса и причиной.

Сервисы отвечают коду, выполняющемуся на сервере Provisa. На удалённом хосте они пока недоступны, и каждый вызов завершается ошибкой.

Каждый вызов вашего кода трассируется как часть запроса, который его вызвал: функция, её вид, сколько аргументов она получила (никогда их значения), возвращённые строки и пакеты, длительность и CPU воркера. Каждый вызов сервиса трассируется так же. При обычной детализации трассировки эти сведения находятся в спане запроса; при отладочной каждый вызов — отдельный спан. Если ваш код использует OpenTelemetry, его спаны входят в ту же трассу.

## Запуск на удалённом хосте {: #running-on-a-remote-host }

По умолчанию источник работает на сервере Provisa; это режим dev. Когда его коду нужна машина, которой сервер не является, например машина с GPU или хост в другой сети, соберите его образ и запустите его там. Тогда источник работает в режиме built, а его таблицы, права и читатели остаются прежними.

**Сборка образа.** Сначала сохраните источник в режиме dev, чтобы его код был прочитан и закреплён. В разделе **Remote host** его формы выберите архитектуру (Linux x86-64 или ARM64) и куда отправить образ: в один из реестров контейнеров вашей организации, заведённых в **Admin → Container registries**, или на скачивание. Provisa собирает образ сам. В нём код с закреплённым хешем, его зависимости, установленные для этой платформы из lockfile кода через ваши реестры пакетов, закреплённая среда выполнения и программа удалённого хоста, на минимальном базовом образе. При сборке в образе ничего не запускается, и демон Docker не участвует. Тег образа содержит хеш кода и версию Provisa, а его метки называют среду выполнения, хеш кода и экспорты.

**Запуск.** Форма показывает сервис compose для образа. Скачанный образ сначала загружается командой `docker load -i <file>`. Контейнер слушает внутри порт 7443 и хранит свою идентичность на томе. Порт хоста вы задаёте через `PROVISA_HOST_PORT`; без него сервис не запустится:

```yaml
services:
  provisa-code-rates:
    image: ghcr.io/example/provisa-code-rates:3f9a1c2e7b40-0.1.0
    restart: unless-stopped
    ports:
      - "${PROVISA_HOST_PORT:?set PROVISA_HOST_PORT to a free port on this host}:7443"
    volumes:
      - provisa-code-rates-state:/var/lib/provisa
volumes:
  provisa-code-rates-state: {}
```

При первом запуске контейнер пишет в лог строку, начинающуюся с `pairing code:`.

**Подключение.** Вернувшись в форму, введите хост, по которому Provisa обращается к контейнеру, опубликованный вами порт и код сопряжения. В общей сети Docker или в Kubernetes введите имя контейнера или Service и 7443, ничего не публикуя. Provisa сопрягается с контейнером по взаимному TLS. Код используется один раз, и с этого момента каждая сторона принимает только другую. Затем Provisa проверяет, что контейнер выполняет код источника и предлагает его экспорты, и переводит источник в режим built. Каждый процесс Provisa держит своё соединение с хостом и переподключается, если хост перестаёт отвечать. Пока хост не отвечает, чтения таблиц источника завершаются ошибкой с названием хоста.

**Если код меняется.** Контейнер, вернувшийся с другим кодом, отклоняется с указанием хеша, к которому закреплён источник, и хеша, который сообщает хост, пока steward не проверит код и не закрепит его заново в форме. Чтобы изменить сам код, верните источник в dev, сохраните новый код и соберите образ снова.

В контейнере границей исходящего трафика кода служит его сетевая политика; список разрешённого исходящего трафика сервера действует в режиме dev.

## Чтение таблицы {: #reading-a-table }

Таблица источника кода загружается в хранилище, а не читается на месте. Provisa вызывает функцию с аргументами чтения, проверяет каждую строку по столбцам и хранит строки под этими аргументами в течение TTL кэша таблицы. Затем к загруженным строкам применяются видимость, маски и правила строк, как к любой таблице.

Аргументы передаются как любой параметр таблицы: условиями `_nf_` в SQL и аргументами полей в GraphQL.

## Ключи пакетом: параметр `loader` {: #batched-keys }

Join может дойти до таблицы кода: строки другой таблицы задают её параметры, например клиенты, соединённые со своей оценкой оттока. По умолчанию Provisa вызывает функцию один раз для каждого отдельного набора аргументов, которые дают соединяемые строки, и отправляет все эти вызовы воркеру одним запросом.

Функция с параметром `loader` вместо этого вызывается один раз на пакет, по образцу DataLoader из GraphQL. `loader` — это хеш: словарь (объект в TypeScript), сопоставляющий стабильному хешу каждого ключа сам ключ, JSON-объект со значениями соединяемых строк для остальных параметров функции. Provisa убирает повторяющиеся ключи, так что каждое отдельное сочетание значений встречается один раз. Ключ разрежённый: поле без значения не включается, а не передаётся как null, поэтому действует собственное значение функции по умолчанию, как при одиночном вызове.

Функция возвращает ту же форму: хеш, сопоставляющий каждому полученному ключу строки этого ключа, обычные строки таблицы. Provisa отдаёт строки каждого ключа всем соединяемым строкам, у которых был этот ключ, и ключу может соответствовать ни одной строки или много. Сопоставление по хешу, а не по значениям строк, сохраняет сопоставление для разрежённого ключа: функция заполняет его недостающие поля значениями по умолчанию, поэтому значения, которые она видит, отличаются от значений соединяемой строки. Хеш вычисляет Provisa; функция лишь возвращает полученные ключи. Функция по-прежнему объявляет только свой тип строки, список строк, и строки каждого ключа имеют этот тип. Её параметрам рядом с `loader` нужны значения по умолчанию, потому что вызов с loader передаёт только `loader`.

Функция может ограничить размер пакета, как `maxBatchSize` в DataLoader, объявив `loader N` в одном из трёх мест: строкой `@loader 100` рядом с `@table` в docstring или JSDoc, комментарием `/* @loader 100 */` прямо перед параметром `loader` в TypeScript или строкой `Annotated` на параметре в Python, `loader: Annotated[dict[str, CustomerKey] | None, "loader 100"] = None`. Тогда Provisa делит ключи на пакеты этого размера, вызывает функцию один раз на пакет и объединяет ответы по хешу. Без размера один пакет содержит все ключи. Обнаружение отклоняет с указанием имени размер у функции без параметра `loader`, размер, не являющийся положительным целым числом, и два размера у одной функции.

Используйте `loader`, когда один вызов на много ключей лучше, чем много вызовов на один ключ:

- Оценка моделью целого пакета за один векторизованный проход.
- Объединение запросов к API или языковой модели, которые принимают много входных данных сразу.
- Подготовка один раз на пакет, например загрузка модели или открытие соединения, а не один раз на ключ.

Эта функция на Python оценивает каждого клиента пакета за один проход:

```python
from dataclasses import dataclass
from typing import TypedDict


class CustomerKey(TypedDict, total=False):
    customer_id: str
    plan: str
    region: str


@dataclass
class Score:
    customer_id: str
    score: float


def churn_score(
    customer_id: str | None = None,
    plan: str = "basic",
    region: str = "US",
    loader: dict[str, CustomerKey] | None = None,
) -> list[Score]:
    """Churn score of each customer in the batch.

    @table
    """
    keys = loader or {"": {"customer_id": customer_id, "plan": plan, "region": region}}
    rows = {h: {"plan": "basic", "region": "US", **key} for h, key in keys.items()}
    scores = MODEL.predict(features(list(rows.values())))  # one vectorized call for the batch
    out = {h: [Score(r["customer_id"], s)] for (h, r), s in zip(rows.items(), scores)}
    return out if loader else out[""]  # a loader call returns the hash of key to rows
```

При соединении с таблицей клиентов она вызывается с `loader` вида `{"9f2c...": {"customer_id": "637", "plan": "pro", "region": "EU"}, "41ab...": {"customer_id": "638"}, ...}`. Второй ключ содержит только `customer_id`, поэтому тариф и регион получают значения по умолчанию. Функция возвращает `{"9f2c...": [...], "41ab...": [...], ...}`, и Provisa отдаёт каждый список строк каждой строке клиента с этим ключом.

Та же функция на TypeScript:

```typescript
export interface CustomerKey {
  customer_id: string;
  plan?: string;
  region?: string;
}

export interface Score {
  customer_id: string;
  score: number;
}

/** Churn score of each customer in the batch.
 * @table
 */
export async function churnScore(
  customer_id?: string,
  plan = "basic",
  region = "US",
  loader?: Record<string, CustomerKey>,
): Promise<Score[]> {
  const keys = loader ?? { "": { customer_id, plan, region } };
  const rows = Object.entries(keys).map(([h, key]) => [h, { plan: "basic", region: "US", ...key }] as const);
  const scores = await model.predict(rows.map(([, row]) => row)); // one call for the whole batch
  const out = Object.fromEntries(
    rows.map(([h, row], i) => [h, [{ customer_id: row.customer_id, score: scores[i] }]]),
  );
  return loader ? out : out[""]; // a loader call returns the hash of key to rows
}
```
