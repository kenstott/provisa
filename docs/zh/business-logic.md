# Provisa 中的业务逻辑

## 问题所在 {: #the-problem }

业务逻辑散落各处：ETL 作业、仪表板和 API 里都有，归不同团队所有，却没有人为它们编目。“净收入”在数据仓库作业里是一种算法，在财务仪表板里是另一种，在计费 API 里又是第三种，没有人说得清哪个对。

这不是谁的错。只是一直没有一个共享、简单的模型来存放这些规则。

## 什么是业务逻辑 {: #definition }

业务逻辑是创建、更新、删除或转换数据的规则。

业务术语是另一回事。域、表和列的名称与描述，以及[术语表](glossary.md)中的术语，说明数据的含义。业务逻辑说明对数据做了什么。

## 三种角色 {: #roles }

每条规则扮演三种角色之一，每种角色都可以用三种方式编写：

| 角色 | SQL | 外部调用 | 代码解析器 |
|---|---|---|---|
| **数据集** | 视图、语句命令 | 返回行的 API 或存储过程 | `@table`, `@stream` |
| **值** | 视图表达式、指标 | — | — |
| **变更** | `INSERT`, `UPDATE`, `DELETE`, 语句命令 | API 写入、mutation、存储过程 | `@command` |

- **外部调用。** 另一个系统的 GraphQL、REST 或 gRPC API，或数据库的存储过程，注册为命令。
- **指标。** 一个只定义一次的具名聚合，例如把 `net_revenue` 定义为 `SUM(orders.amount) - SUM(orders.refunds)`。每个查询按自己请求的维度展开它，因此数据仓库、仪表板和 API 读到的是同一个数字。

## 隐藏的副作用 {: #side-effects }

隐藏的副作用是从规则的定义中看不出来的副作用。

每条规则都有名称和类型，并且已注册、受审计、受保护。

| | 可能的副作用 | 限制方式 |
|---|---|---|
| **SQL** | 无 | — |
| **外部调用** | 另一个系统自身的工作流、通知和级联操作 | 审批 |
| **代码解析器** | 对外部服务和网络的调用；结果会变化；成本 | 沙箱、计量 |

外部调用的类型来自该系统自身的模式，或你注册命令时声明的参数和返回列。

这些限制能约束副作用，但无法消除它们。外部系统或你自己的代码做什么，最终取决于它自己。

## 模型带给你什么 {: #what-you-get }

- 每条规则都注册在一个域中，并有授权。
- 每条规则都以同样的方式治理，无论它如何编写。
- 每条规则都在[血缘](lineage.md)中可见。
