# 环境 {: #environments }

环境是组织受治理模型的一个具名副本。物理上，这个副本是一个独立的 PostgreSQL 模式：真正的模式，没有判别列，也没有前缀。所以现有的每个仓库查询在环境内无需改写就是正确的，漏写的谓词也无法让一个环境的行被另一个环境读到。

每个组织起步时都有一个名为 `prod` 的环境。它不能被删除或重命名。未指名环境的请求由 `prod` 服务；指名了不存在环境的请求会被拒绝。

环境功能面向付费套餐的组织提供。

要为非生产环境填充可安全使用的数据，请参阅[构建测试环境](test-data.md)。

## 环境名称 {: #environment-names }

名称必须匹配 `[a-z][a-z0-9_]{1,31}`：2 到 32 个小写字母、数字和下划线，以字母开头。`prod` 以及以 `pg_` 开头的名称会被拒绝。某个组织的最大长度取决于该组织自身的 id。PostgreSQL 会悄悄截断超过 63 字节的标识符，这个上限防止的就是环境推导出的最长模式名被截断。

## 副本带走什么 {: #what-a-copy-carries }

组织模式中的每张表都恰好属于一个类别。这种分类是白名单式的：后来新增的表在有人于此处指定其类别之前不会随副本迁移，所以遗漏一张表会表现为测试变红。

| 类别 | 表 | 复制时会发生什么 |
| --- | --- | --- |
| CARRIED | domains, naming_rules, registered_tables, table_columns, relationships, metrics, roles, rls_rules, tags, tag_param_values, tag_assignments, glossary terms, materialized_views, calendars, api_endpoints, tracked_functions, tracked_webhooks, table_meta_links | 整体复制 |
| IDENTITY_ONLY | sources, api_sources, kafka_sources | 身份与治理字段随行；连接值留在原处（见"绑定"） |
| SEEDED_AT_CREATION | roles, user_role_assignments | 仅在环境首次创建时复制；之后的合并不会碰它们 |
| PARTIAL | org_settings | 按键复制：治理设置随行，指向外部目标或按环境运行时的键留在原处 |
| NEVER_SENSITIVE | org_secrets, user_directory | 从不复制 |
| NEVER_RUNTIME | mv_refresh_log, relationship_candidates, admin_audit_log 等 | 从不复制 |

`SEEDED_AT_CREATION` 的存在是为了解决一个具体问题。新环境需要角色和分配，否则它一开张就没人能做任何事。但如果后来的合并把 `prod` 的 `developer` 行也带过来，就会覆盖某个受限分支可能需要的受限版本，从而把评审路径变成提权通道。因此角色和分配只在创建时随行一次，此后就是各环境自己的答案。

## 绑定 {: #bindings }

绑定是指明数据源实际指向何处的那些列：`host`、`port`、`database`、`username` 等。它们从不随副本迁移。尚未绑定的环境会标记为 `unbound`，而不是留空，因为空主机不等于没有主机，连接构建器会把空主机读成 `localhost:5432`。

以 Unbound 之外的任何方式创建的环境，会按其父环境写入的原样复制每个数据源的连接：
`${secret:...}` 或 `${env:...}` 引用被复制为同一个引用，从不解析。创建之后，副本就是该环境
自己的行，可在数据源页面编辑；构建环境的运行时时，不会经由父环境解析任何内容。
每个数据源的 `binding` 字段说明其连接来自何处：`copied`、`own`（在此环境中提供）
或 `unbound`。编辑复制来的连接会使其变为 `own`。**从父环境重新复制**
（`POST /admin/orgs/{org}/environments/{name}/sources/recopy`）会再次复制父环境的连接。
合并或部署不携带连接，因此它们带入的数据源以 `unbound` 状态到达。

## git 投影 {: #the-git-projection }

对模型的每次写入都会把结果提交到该环境的 git 分支。部署一棵树需要显式调用：在 git 托管平台上合并的 pull request 不会自行部署。

每个实体对应一个文件。路径是实体的 `provisa://` 地址去掉协议和组织部分：`provisa://acme/sales/tables/Order` 变成 `sales/tables/Order.yaml`。数据源放在 `sources/`，命令放在 `commands/`，指标放在 `metrics/`。依附于父对象的子行（列、关系、RLS 规则）写在父对象的文件中，不单独成文件。

命令及其标签分配能完整往返。命令上的标签会被路由到该命令自己的文件（`commands/<name>.yaml`）；不属于任何文件的标签会从投影中消失，并会在该树的下一次部署时被删除。

任何代理键都不会写进文件。`registered_tables.id` 是自增整数，所以同一个模型在两个环境中会得到不同的整数，简单导出的结果会和自己产生差异。所有代理键都被去掉，对它们的每个引用都写成目标的路径。

序列化是确定性的。键按字母序输出，子集合按各自的地址排序，YAML 样式固定。持有同一模型的两个环境会产出逐字节相同的树。

## 合并 {: #merge }

把一个环境的模型合并到另一个环境时，按标识更新：源中有的每个对象都会在目标中创建或更新。源中已不存在的对象，只有在调用方明确要求删除时才会被删除。一次合并就是一个事务，所以中途失败时目标保持原样。

在应用之前，先调用预览终结点（`GET /{name}/merge-preview`）或传入 `dry_run: true`。预览走的是合并所用的同一条代码路径；它是一个 `GET` 终结点，因此把标志写错的 CI 脚本不会误把它本想查看的合并给应用了。

合并会让目标的绑定、角色和密钥保持原封不动。开发环境不会因为从 prod 取来一份更新的模型而丢掉自己的数据库连接。prod 也不会获得 dev 的授权。

### 报告点名了什么 {: #what-the-report-names }

合并报告按路径列出新增、修改、删除和未变的内容。它还会列出**冲突**：自上次共享某个提交以来，双方都修改过的对象。冲突只做报告，由源方胜出，因为合并到目标本来就是这个意思。Provisa 不提供冲突解决、合并标记或逐对象选择。冲突列表的价值在于提醒：有两个人在不知情的情况下改了同一个对象。

如果双方把某个对象改成了相同的值，那就是一致，不算冲突。如果两个环境完全没有共同祖先，报告中的基线为 `None`，空的冲突列表表示根本没有做比较，而不是没有冲突。

合并以一个压缩提交的形式落到目标分支上。提交信息是必填的，不能为空，因为它是这个压缩提交所代表的那段工作的唯一说明。源方的提交保留在原处，之后仍可按 SHA 部署。

## 拉取 {: #pull }

拉取会取来远端为某个环境所持有的内容，并使其成为模型。它不会直接快进本地分支；它把取来的树经由普通的部署路径应用，因此管辖手动部署的那套校验和审计也同样管辖拉取。

与合并一样，pull 会报告它覆盖了什么：传入的树修改过、而本地环境自两条线最后一次共享提交以来也修改过的对象。从未提交的本地更改会使环境处于偏离状态（见下文“历史”），pull 会在报告中把它列为普通更改。

当两条线已经**分叉**，即双方都有对方没有的提交时，pull 会被拒绝。拒绝信息会列出双方都改动过的对象，让需要决定保留谁的工作的人知道该看哪些对象。

## 历史 {: #history }

每次部署都会让环境的游标沿着它自己的提交线向前移动。撤销后退一个提交，重做再朝撤销开始的位置前进。两者都不会删除提交：后退只是增加一个位置，历史保持不变。

分支是在其创建来源环境的顶端播种的，因此撤销会停在那个播种点，不会走到父环境的提交上。

`can_undo` 和 `can_redo` 标志随环境列表响应一起返回。当投影中没有控制平面所指的提交时，两者都为 `false`，这种状态是设计所允许的，称为**偏离**。如果某个节点的仓库存储从未收到某个提交，它仍会列出自己的环境，只有历史相关的答案会变化。

## 授权 {: #authorization }

环境由两项权限管辖。默认情况下，分析师两项都不持有。

| 权限 | 谁持有它（初始播种） | 它管辖什么 |
| --- | --- | --- |
| `environment_management` | org_admin、developer | 创建和删除环境 |
| `environment_switch` | org_admin、developer | 由 prod 之外的任何环境提供服务 |

`prod` 不需要任何权限。没有指定环境的请求都由它来服务，拒绝它就等于拒绝所有请求。

检查发生在选择环境的那一刻，在到达任何路由之前。没有 `environment_switch` 的成员会在所有入口同时被拒绝（HTTP、GraphQL、SQL 以及各线路协议），因为环境是在中间件中绑定的，而不是在各个处理程序中。

不持有任何环境权限的分析师可以查询 `prod`，且看不到环境切换器。被授予分析师角色的外包人员看不到环境相关界面，也无法创建或切换到生产以外的任何环境。

### 环境所有者的权限 {: #environment-owner-authority }

创建环境是只读成员获得模型编辑权的唯一途径。在自己创建的环境中，创建者拥有 `developer` 角色的能力，但不含数据权限（`write`、`full_results`、`usage`）：有构建模型的权限，没有数据权限。

该授予是在授权时从 `environments.created_by` 推导出来的，绝不写入任何授权表。删除该环境的同一个动作就把它一并撤除。

域成员资格仍然限制所有者可以改动什么。开分支改变的是成员可以做什么；它绝不改变他们可以对哪些域去做。

## 受保护的环境 {: #protected-environments }

环境可以被设为受保护。向受保护环境的合并或部署不会在请求时被应用；它会被提出为一项提案，且必须由请求者之外的人批准。

一旦组织成员超过一人，`prod` 会自动受保护。只有一个成员的组织无法满足“申请人以外的另一个人”，所以规则在那里不适用，否则就永远无法合并到 `prod`。org_admin 可以把任何环境标记为受保护。

合并请求是一条保存下来的记录，不能用确认对话框代替。批准人按定义不是申请人本人，提出请求时也不在场。一次性的确认框会迫使批准在申请人的会话中完成，而这恰恰是规则所禁止的。

请求行携带合并报告以及请求者的留言。是否过期是在读取时推导的，从不存储：在读取时重新规划并与已存报告比对，是唯一不会出错的做法。过期的请求必须重新发起。请求者不能批准自己的请求。

请求的生命周期状态：`requested` → `approved`/`rejected` → `applied`。`stale` 是推导出来的。

从仓库 ref 部署也走同一道门，请求会在提出时锁定 SHA。如果 ref 在提出和决定之间移动了，批准人看到的是锁定提交的报告，而不是新提交的报告。

!!! note
    合并请求的 UI 位于环境面板的**合并请求**选项卡下。
    **报告**列按数量展示会有什么变化；展开该行可查看逐对象的详情。

## `env` CLI 命令 {: #the-env-cli-commands }

`provisa env deploy` 把某个 ref 上的模型发送到一个环境。部署已应用或是一次试运行时，它以 0 退出；环境受保护、部署只是被提出时，它以 2 退出。把待批准当成已发布部署的流水线就错了，退出码正好能区分这两种情况。

```
provisa env deploy --org acme --env prod --ref main --token <token> --api <url>
```

`provisa env fetch` 把组织的远端分支取到本地仓库。之后部署就可以指名 `origin/<branch>`。

```
provisa env fetch --org acme --api <url> --token <token>
```

两个命令都接受 `--api`（Provisa API 的 URL）和 `--token`（bearer 令牌）。在环境中设置 `PROVISA_API_URL` 和 `PROVISA_API_TOKEN`，即可免去每次调用都传它们。

仓库驱动工作流的典型 CI 流水线：

```bash
provisa env fetch --org acme --api "$PROVISA_API_URL" --token "$PROVISA_API_TOKEN"
provisa env deploy --org acme --env prod --ref "origin/main" \
  --message "release: $GIT_COMMIT_MSG" \
  --api "$PROVISA_API_URL" --token "$PROVISA_API_TOKEN"
```
