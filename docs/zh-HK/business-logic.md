# Provisa 中的業務邏輯

## 問題所在 {: #the-problem }

業務邏輯散落各處：ETL 作業、儀表板和 API 裡都有，歸不同團隊所有，卻沒有人為它們編目。「淨收入」在數據倉庫作業裡是一種算法，在財務儀表板裡是另一種，在計費 API 裡又是第三種，沒有人說得清哪個對。

這不是誰的錯。只是一直沒有一個共用、簡單的模型來存放這些規則。

## 甚麼是業務邏輯 {: #definition }

業務邏輯是建立、更新、刪除或轉換數據的規則。

業務術語是另一回事。網域、表和欄的名稱與描述，以及[詞彙表](glossary.md)中的術語，說明數據的含義。業務邏輯說明對數據做了甚麼。

## 三種角色 {: #roles }

每條規則扮演三種角色之一，每種角色都可以用三種方式編寫：

| 角色 | SQL | 外部呼叫 | 代碼解析器 |
|---|---|---|---|
| **數據集** | 視圖、語句指令 | 返回行的 API 或預存程序 | `@table`, `@stream` |
| **值** | 視圖運算式、指標 | — | — |
| **變更** | `INSERT`, `UPDATE`, `DELETE`, 語句指令 | API 寫入、mutation、預存程序 | `@command` |

- **外部呼叫。** 另一個系統的 GraphQL、REST 或 gRPC API，或數據庫的預存程序，登錄為指令。
- **指標。** 一個只定義一次的具名聚合，例如把 `net_revenue` 定義為 `SUM(orders.amount) - SUM(orders.refunds)`。每個查詢按自己要求的維度展開它，因此數據倉庫、儀表板和 API 讀到的是同一個數字。

## 隱藏的副作用 {: #side-effects }

隱藏的副作用是從規則的定義中看不出來的副作用。

每條規則都有名稱和類型，並且已登錄、受稽核、受保護。

| | 可能的副作用 | 限制方式 |
|---|---|---|
| **SQL** | 無 | — |
| **外部呼叫** | 另一個系統自身的工作流程、通知和連鎖操作 | 審批 |
| **代碼解析器** | 對外部服務和網絡的呼叫；結果會變化；成本 | 沙盒、計量 |

外部呼叫的類型來自該系統自身的結構描述，或你登錄指令時宣告的參數和返回欄。

這些限制能約束副作用，但無法消除它們。外部系統或你自己的程式碼做甚麼，最終取決於它自己。

## 模型帶給你甚麼 {: #what-you-get }

- 每條規則都登錄在一個網域中，並有授權。
- 每條規則都以同樣的方式治理，無論它如何編寫。
- 每條規則都在[血緣](lineage.md)中可見。
