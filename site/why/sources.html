Provisa / Sources

Connect your databases, APIs and files. Query in 5 minutes.

Any SQL database. Any REST, GraphQL, gRPC or OData API. Any file or object store. Your own code in Node, Python, Go or Rust. Each becomes a governed table you query where the data already lives, joined to everything else, and you copy data only when you declare a copy.

A long list of logos proves little on its own, so here is how the list is built. Today that means 79 connectors reaching over 200 named sources.

Four classes of source

Any SQL database

PostgreSQL, Snowflake, Oracle, BigQuery and the rest of the SQL family. The query engines read them natively.

Any API

REST with an OpenAPI description, GraphQL, gRPC and OData. Provisa reads the API's own description to find its tables.

Any file or object store

A folder, a bucket, an SFTP host or a SharePoint site. CSV, Parquet, Excel and the tables inside documents.

Your own code

A function in Node, Python, Go or Rust that returns rows. It becomes a table like any other.

One contract, a tree of connectors

Every connector answers the same questions. Which tables and columns does the source have, with what types and descriptions? How are rows read? Which filters can it take? What does it need to connect, and how does it sign in? Does it run inside Provisa or on a host of its own? Those answers are the source contract.

Four runtimes implement the contract, one each for Node, Python, Go and Rust. On those runtimes sit a handful of bases: OpenAPI and REST, GraphQL, gRPC and OData. A named source such as Stripe or Jira is one of those bases plus a short configuration giving its URL, how it signs in and a few fixed values. Hand-built connectors are kept for the few sources whose logic fits no base.

The other root is everything the query engines read natively, with no runtime in between: SQL databases and warehouses, files and lakes such as Parquet, Delta and Iceberg, and stores like MongoDB, Kafka and Elasticsearch.

Every connector inherits its base's tests

Each base has a conformance suite, and every connector built on that base inherits it. Discovery, types, paging, the filters it accepts, sign-in and errors are tested once, at the base. A named source's own tests then cover only what it adds, its configuration and any overrides.

So the two-hundredth source on a base is held to the same bar as the first one.

A page for every source

Each named source has a page generated from its definition. It shows the base the source is built on, what Provisa pushes down to it, what you need to connect, and when it was last verified against a live account. Where no live check has run yet, the page says when the source last passed its base's suite.

Nobody writes these pages by hand, so they can't drift from what the connector does.

Not on the list? Write it in 15 minutes

Write a function in Node, Python, Go or Rust that returns typed rows, and it becomes a table. It gets the same catalog entry, governance, hosting and protocols as every named source. Visibility, masks and row rules apply to what it returns, you can join it to the rest of the model, and SQL, GraphQL and Cypher clients all reach it. Its code is pinned by version, commit or hash, so it is promoted with the model.

Run it inside Provisa, or on a host of its own beside the data, on a GPU box or inside another network. Provisa builds the container image for you and pairs with it over mutual TLS.

The file crawler

Seventy-nine connectors, and one of them finds the rest of your data. Seventy-eight of them connect to a system you already know you have. The seventy-ninth is a crawler, and it tends to find the half of your estate nobody put on the inventory.

It is one source type, and the only one where you register a location rather than a system. Point it at a folder, a bucket, an FTP or SFTP host, or a SharePoint site and it walks the tree recursively, looking for database files and for files with tabular data embedded in them. What it finds gets cataloged as an available table; registering it is still your call, the same as for any other source.

A CSV or Parquet file is a table. In an Excel workbook it looks through each sheet, finds the regions that look like tables, and extracts each one. In HTML, Markdown, Word and PowerPoint documents it extracts the tables the document marks as tables. In documents with links it follows them too, from each start URL down to a configurable depth, so it works well over websites and documentation portals.

The data that runs a department often sits in a share drive and has never been near a governance program. Finding it used to be a project. Once found, what you register lands under the same row-level security, masking and relationship rules as the databases.

Systems that aren't databases

Connect SharePoint and its lists enumerate as schemas you can query. Run a Splunk search and the results come back as a table you can JOIN to your business data. A live Google Sheet is a table, and so is a REST, GraphQL, gRPC, WebSocket or RSS endpoint, registered as a governed table that cross-source joins reach like any other.

Shaping takes a declaration instead of a program

Non-relational data is where pipelines are born: the response is nested, the document has an array inside it, the location is a pile of files, so somebody writes code to flatten it and a procedure enters the path permanently. The variety is smaller than it looks. There's a modest set of structure types, each with a short declarative rule for projecting it into rows and columns: the path to the collection and the fields to lift from it, a sampled document schema with the steward's explicit types overriding what was inferred, or a crawled location that catalogs what it finds. Once it's flat, everything after it is SQL, which a machine can read back.

Why that removes the downstream pain

Graph and RDF are first-class

Neo4j and SPARQL sources take part in the same model, the same relationship registry and the same access-control layers as the relational ones. So a Cypher traversal across a relational source and a graph source is one legal query, not two queries and a join in application code.
