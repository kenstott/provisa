Provisa / An opinionated view

Why data management keeps failing

Forty years of advances in data management share a common failure: each one added a piece of what an organization needs, and none assembled the pieces into one model that fuses governance, meaning, the data itself, and access. The result is estates held together by integration projects that never quite close. AI has made the gap impossible to ignore. An agent handed data with no fused meaning, ownership or governance shows the seams at once.

Each generation added a piece

  • Data warehouses (Inmon, Kimball): one integrated copy of the truth, meaning encoded in a carefully designed schema — but access still scattered across tools, and governance bolted on afterwards.
  • Big data and data lakes (Hadoop, object stores): scale without limits; meaning and governance were left behind, and the lake became a swamp.
  • Data catalogs and governance tools: meaning documented and policies recorded — but neither bound to the data nor enforced at query time.
  • Semantic layers and metrics stores: shared metric definitions for BI — but a thin slice of meaning covering only aggregations, with no model of who owns what or what the terms mean.
  • Ontologies and knowledge graphs: formal meaning, relationships and reasoning — but rarely bound to operational records and almost never enforced at access.
  • Data mesh: domain ownership and data as a product, with federated computational governance — but deliberately no runtime, leaving programs to implement governance themselves over every domain's own systems.
  • Palantir Foundry: the ontology is bound to data and access is controlled, which gets closer than almost anything else. Our reading of their public documentation: Foundry builds applications on top of its own connectors and ontology framework rather than serving consumers over standard protocols. Value scales with the applications specialists build inside the platform, not with the concepts and relationships that people throughout the organization can own. Operations are expressed in TypeScript or Python functions, and applications are built in Workshop, rather than from a small set of declared primitives a domain steward can read and approve. Its governance model is controls-based: Markings, permissions, project roles, and Organizations determine who may see and do what. What we find missing is a stewardship model for meaning: an accountable owner who defines and approves what a term means within a domain hierarchy, and whose approval is recorded with the term. To be clear: this is Provisa's opinion. Foundry's object and link types and its declarative Action rules are genuine contributions to the field.

The opinions behind the model

A concept without a binding is documentation. A term defined in a glossary tells you what "customer" should mean. Without a link to the column that holds the customer ID, the definition and the data have no relationship to each other. You can read one without the other, and so can an agent. A concept earns its place in the model by reaching data, directly or through other concepts. Until then, it is a draft. What grounding means in practice.

The model governs reality; it does not contain it. Sources stay where they are. Interfaces — not pipelines — are the boundary between the model and the systems it governs. A platform that processes data to govern it creates a copy and a latency; it also fuses the governance with the platform, so replacing the platform means replacing the governance too.

It pays off on day one. One domain, one steward, one concept, bound to existing records. That is the minimum viable model. It governs one slice of the organization from the first day it is declared, without a rebuild, a migration, or a platform project first. Start there.

Domain boundaries are hypotheses. A boundary that looks right on a whiteboard will be wrong in the data. The right sequence is: refine the meaning of concepts within a domain, then refine the relationships between domains, then expand or realign a boundary, and add new concepts last. Carving out a new domain before the existing ones are well-grounded accelerates the drift.

The model compounds. A second domain can bind concepts to the first domain's terms. A third relationship makes three possible join paths available to every query. Each addition multiplies what earlier additions can express, unlike a pipeline estate where each addition is an independent cost.

Its value is measured, not assumed. An ontology that exists as a de facto good gives you no way to know whether it is working. Grounding is measurable: which terms reach data and which are approved but reach nothing. The latter are invisible to agents and queryable as a finding. That is the start of a measurement practice, not the end of one.

Provisa as an attempt

Each opinion above corresponds to something in the model. Grounding is computed from the live model and shown on every term, so a steward can see at a glance whether their concept reaches data. The ontology links concepts to columns, to relationships, and to each other, with domain stewards as the accountable owners. Access control — row-level security, column masking, role inheritance through the domain hierarchy — is compiled into every query plan, so governance is not a layer applied to a copy but a constraint on the query itself. One model is served over pgwire, JDBC, Flight SQL, GraphQL, REST, gRPC, Cypher/Bolt, SPARQL, and MCP, so existing tools connect without being rebuilt inside the platform. Derived views capture their own lineage. Commands declare write operations over governed tables.

What is not yet built is worth stating. Grounding status is tracked and surfaced. Which terms appear in queries that actually run is not yet tracked as a first-class metric; that is a gap in the measurement practice described above.

The model matters more than the tool

The framework — fuse governance, meaning, data and access into one model, ground concepts to records, govern reality at the boundary rather than inside a platform — can be applied without Provisa. The practices are not ours. If you apply them with the tools you have, you get most of the value. Provisa is an attempt to make the whole thing declarative, so you do not have to implement it yourself.
