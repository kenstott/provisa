Provisa / Compare / Provisa and data catalogs

See it. Fix it. Stop it.

Data catalogs describe and govern data after it exists, alongside your systems. They help you see the mess. Provisa makes the declaration the system itself — so the mess never forms — then publishes to your catalog so the catalog shows what is actually governed, not what someone last wrote down.

Three different positions

See it

Catalogs excel here. Browse, search, tag, classify and document assets across every system. Atlan, Collibra, Alation and DataHub all do this well. A steward can find any table, read its lineage, and understand its business meaning. The problem is the catalog came after the data — it describes what was built, and keeping that description accurate requires discipline.

Fix it

Catalogs can flag problems and let stewards annotate them. Some can propagate classification tags into the SQL warehouses they connect to. Fixing the underlying policy, the missing join, or the inconsistent name still means going back to the data platform itself. The catalog is beside the system; it cannot change it.

Stop it

This is Provisa's position. You declare sources, tables, relationships and governance in a model. Provisa compiles that declaration into the running system. A table that is not in the model does not exist in any API, query result or published catalog entry. Drift cannot form because there is no gap between the declaration and what runs.

Use them together

Provisa publishes to your catalog automatically. Every governed table, column, domain, approved relationship, ontology term and column-level lineage edge flows to the target on each model change — typically within fifteen seconds. Your catalog does not need to crawl anything; it receives what Provisa knows.

Supported targets: OpenMetadata, DataHub, Collibra, Atlan (beta), Apache Atlas, Microsoft Purview, OpenLineage (Marquez and any OpenLineage consumer), Databricks Unity Catalog, Amazon DataZone, Google Dataplex, and Snowflake Horizon Catalog (data products). Configure one or several in Admin — each gets the same snapshot, covering every domain you assign to it.

Governance signals travel with the publish. A masked column arrives in the catalog with the fact that it is masked and which roles the mask applies to. Rule bodies never leave Provisa, so the catalog does not expose your policy logic.

You can also take descriptions back. When a steward edits a table's description in the catalog, the Catalogs panel in Provisa lets them pull that edit into the model, table by table. Governance rules — grants, row rules and masks — are never read from a catalog; they belong in the model.

If you only need a catalog

You want to document and classify data that already exists across many teams and systems. Governance is handled by each platform independently. The problem you are solving is visibility and discoverability, not uniformity of enforcement. A catalog covers that on its own.

If you only need Provisa

You are building new APIs, governed access across source types, or a data control plane for a product. You want governance to hold from the moment data is declared, not applied retroactively. You may not have an external catalog yet — or you want to keep the one you have accurate without manual effort.
