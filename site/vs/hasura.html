Provisa / Coming from Hasura

Where the v2 idea kept going.

Instant, per-role, metadata-driven APIs over your own databases was the right idea. Provisa keeps the premise and adds more languages, more ways in, and governance that holds on all of them. Bring your metadata with you: the converter reads a Hasura v2 metadata directory and writes a Provisa config, tables, permissions, relationships, remote schemas, actions and triggers included. Admin › Import does the same from an upload and shows what each piece became before it applies anything.

One command

# Read a Hasura v2 metadata directory, write a Provisa config
python -m provisa.hasura_v2 ./hasura/metadata -o provisa.yaml

# Validate without writing, map schemas onto domains, override connections
python -m provisa.hasura_v2 ./hasura/metadata --dry-run
python -m provisa.hasura_v2 ./hasura/metadata --domain-map public=sales billing=finance

What converts

  • Sources — Postgres, Citus, MySQL, MS SQL, and BigQuery connections map to Provisa sources.
  • Tables and columns — with per-role select permissions becoming column visibility.
  • Row permissions — Hasura boolean expressions convert to SQL row-level security rules.
  • Relationships — object and array relationships become registered, governed relationships.
  • Remote schemas — mapped to GraphQL remote sources.
  • Actions — each becomes a command that calls the same handler, with its arguments and output.
  • Event triggers and cron triggers — carried across as event and scheduled triggers.
  • Roles and rate limits — preserved as Provisa roles.

Anything the converter can't map cleanly is reported as a warning, so the gaps are a list you work through.

What you keep

A per-role GraphQL API over your database, generated from metadata, with permissions enforced at query time. That model was right, and Provisa keeps it: per-role schemas, field-level visibility, cursor pagination, aggregates, and Apollo Automatic Persisted Queries. No new modeling universe to learn first, no rewrite as the price of admission.

Your own code

Hasura DDN puts your code behind the API in two ways. A lambda connector turns each TypeScript, Python or Go function into a command: a query or a mutation, marked with a @readonly JSDoc tag, a @connector.register_query decorator or a Function name prefix. A connector you build yourself implements the NDC specification's endpoints, and every feature it declares, filtering and relationships included, is code you write.

In Provisa you tag a Node or Python function with @table, @command or @stream, with no SDK to import. The command covers what a lambda is for. The table is what a lambda doesn't give you: rows that join, filter and sort with every other table, carry the same grants, masks and row rules, and read the same way over SQL, GraphQL, Cypher and every other way in. The code is pinned to a package version, a Git commit or an upload. It runs in a sandboxed worker while you develop, and Build image packages it to run on a remote host of your own.

How sources are reached

Every DDN connector, the first-party database connectors included, is its own web service. Each connector SDK starts an HTTP server answering the NDC specification's endpoints, and the Postgres connector is built on the Rust one. The connector reads its source over the source's own protocol; the hop from connector to engine is HTTP, with requests and results sent as JSON in the shapes the spec defines. In Provisa a single-source read goes straight to the source over its native driver, with no connector service in between.

A DDN join across two connectors is assembled in the engine from each connector's serialized results: the engine queries the first connector, passes the join-field values to the second as query variables, and joins the two responses itself. In Provisa a cross-source join runs in the chosen federation engine (Trino, DuckDB or Postgres), which reads each source over its native connector.

Self-hosting DDN's engine and connectors on Docker comes without a control plane. Private DDN Self-Hosted, which brings the control plane onto your infrastructure, needs an enterprise license and a Kubernetes cluster. Provisa installs the same product on a laptop, a single VM, a VM cluster or Kubernetes.

On staying put

Provisa is a handful of primitives (domains, tables, relationships, masking, views) compiled deterministically. Your model is portable declarative config and the SQL it compiles is yours to read and export, so the next migration, whenever it comes and wherever it goes, starts from a file you already own.
