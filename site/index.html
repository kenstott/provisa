psql -h localhost -p 5439 -U analyst

# One SQL query, joined across Postgres, Mongo, and Elasticsearch
SELECT c.name, o.total, t.trace_id
FROM customers c
JOIN orders o   ON o.customer_id = c.id
JOIN queries t  ON t.actor = c.email
WHERE o.total > 1000;
# The per-role schema, over plain HTTP
POST https://provisa.internal/graphql

# The same question — relationships are fields, not joins
query BigOrders {
  orders(where: { total: { gt: 1000 } }) {
    total
    customers { name email }
    queries   { trace_id }
  }
}
# Neo4j Browser and the official drivers, over Bolt
bolt://localhost:7687   # database: provisa_analyst

# The same question — sources are labels, relationships are edges
MATCH (c:Customer)-[:PLACED]->(o:Order)
MATCH (c)-[:RAN]->(t:Query)
WHERE o.total > 1000
RETURN c.name, o.total, t.trace_id
# No new language. The endpoints are generated from the model.
curl -G https://provisa.internal/data/jsonapi/orders \
  -H "Authorization: Bearer $TOKEN" \
  -d 'filter[total][gt]=1000' -d 'include=customers'

# The same question — JSON back, related rows sideloaded
{ "data": [ { "type": "orders", "attributes": { "total": 1420 } } ],
  "included": [ { "type": "customers", "attributes": { "name": "Acme" } } ] }

# The spec is generated too — point a client generator at it
curl https://provisa.internal/data/jsonapi/openapi.json
# A .proto generated from your schema — typed RPCs per table
grpcurl -d '{"total_gt": 1000}' provisa.internal:443 \
  provisa.orders.OrdersService/Query

# The same question — a typed response, no schema drift possible
message Order {
  string id = 1;
  double total = 2;
  Customer customer = 3;
  repeated Query queries = 4;
}

Those are usually four tools, each holding its own description of the same data: a query engine, a metrics layer, a catalog, a policy service. When one changes, the others are wrong until someone catches it. The descriptions drift, and there is no mechanism to keep them in step.

One model: sources, metrics, ontology and governance.

You describe your data once: sources, tables, relationships, who may see what. Everything else is generated from that one description — the APIs, the legal join paths, the governance, and the audit trail. Keep the catalog and lineage tools you have; Provisa publishes to them. Data catalogs that provide a context layer tell an agent what it should do; Provisa enforces what it can do.

One model — what each part covers Every change is versioned, and promoted through environments

Any language, one governed IR

GraphQL, Cypher, and SQL all query the same model and retarget to any source dialect. Domains carve it into namespaces (a domain is the schema a SQL client sees), and governance applies identically across all of them. Add a protocol and the governance follows automatically.

Read and write

Analytical and transactional flows through the same governed API: cross-source reads fan out through the engine; writes and single-source reads route direct to the driver, sub-100ms.

Smart routing

Single-source queries bypass the engine entirely. Materialized views record the transform that built them, so queries rewrite transparently onto a fresh MV.

Query interfaces & wire protocols

Each language and protocol you add is another headache.

Each language-transport stack needs its own governance integration and its own programmers. Data leaks and exfiltration paths appear at every new surface. A change to the access model now touches every interface point, which becomes its own lock-in: you can't change one thing without changing several.

Each stack also kicks off another endless round of tool selection, vendor selection and standards processes, then procurement, contracts, invoices, renewals, disputes, and the debates between teams over where business logic, security and capabilities should live, which end in building yet more integrations. Start a GraphQL API team, for example, and it grows along exactly those lines. If the goal is a bigger team, that plan works.

Every language and wire protocol here compiles to one IR. Governance is applied once at that IR — a change happens once, and the same rules reach every combination of language, transport, and tool.

The result: your BI dashboards and your application APIs share the same semantics and the same governance.

Every interface in detail

Access control, compiled in

Access rules in every tool are rules nobody can prove, including audit.

When access control is configured per API, every new interface is another integration to get right, and proving to an auditor that no path was missed means checking each one separately. Here access control is compiled into the query plan on every language and every transport. Add a source, a column, or a relationship and every layer applies to it automatically — there is nothing to re-apply per interface. It's one part of governance; where, when and how work runs, and what the data means, are declared in the same model.

Auto-indexing file crawler

Point it at a location. Get a catalog of the data hiding in it.

One of the 73 connectors behaves unlike the other seventy-two: you register a location, not a table. It walks the tree recursively, finds tabular files and the tables inside documents, and catalogs each table — the shared drive nobody has mapped, the S3 prefix of extracts, the SharePoint site a department has been running on for years.

  1. 1

    Point

    A local or network folder, an S3 bucket, a SharePoint site, an HDFS path, or an HTTP, FTP or SFTP host: one location, not one table.

  2. 2

    Crawl

    It walks the tree to whatever depth you allow and searches every file for tables: a CSV or Parquet file is one; in an Excel workbook it finds the regions of each sheet that look like tables and extracts each; in HTML, Markdown, Word and PowerPoint it extracts the tables the document marks as tables. In documents with links it follows them too, down to the same depth limit.

  3. 3

    Register

    You pick which of the discovered tables to register, and they land under the same six access-control layers as everything else.

Derived data & your existing stack

Pipelines are code. Code breaks. Declare the dataset instead.

A pipeline is a program that ran; to audit one you read code. When the source changes, the pipeline is wrong until someone finds it and fixes it. The only durable record of what happened is the output table and a log line. Declare the dataset instead and the definition is the record.

Declared datasets, not pipelines

A pipeline is a program that ran; to audit one you read code. Declare the dataset instead and the definition is the record: column-level lineage, the data version consumed, the rules that produced it. No orchestration DAG.

Feeds the catalog you bought

One registration publishes to OpenMetadata, DataHub, Collibra, Atlan, Apache Atlas, OpenLineage, BigQuery Dataplex and Snowflake Horizon, with lineage stitched on business identity, so re-platforming doesn't reset it.

Starts from the model you already have

Questions

Frequently asked

Is Provisa a database, or does it replace my warehouse?

Neither. Provisa is a semantic and governance layer that runs on an engine you choose: Trino, DuckDB, ClickHouse, Postgres, Snowflake, Databricks, BigQuery, or the embedded DuckDB engine in the box. Your warehouse becomes a replaceable execution engine, not the place your semantics live.

How it works in depth
How is this different from Starburst or Denodo?

Starburst is a query engine; Provisa sits above one and can use Starburst as its engine. Denodo is the closest comparison, in the same category: Provisa adds GraphQL and Cypher as peers to SQL, nine wire protocols including pgwire and Bolt, engine choice, and a deployment that starts at one pip install.

Provisa and Starburst
Does Provisa support data mesh?

Data mesh was a governance model, in its most complete sense, and never had a runtime. Provisa is that runtime: each domain owns its namespace and its ODPS data products over the systems it already runs, and where, when, how, for whom and with what meaning data is processed is declared once and compiled into every query, on the engine you already have.

Data mesh, with a runtime
I'm on Hasura v2. Can I migrate?

Yes. Point the converter at your Hasura v2 metadata directory and it emits a Provisa config: sources, tables, per-role permissions as row-level security, relationships, remote schemas, actions, event triggers, and cron triggers. Anything it can't map cleanly is reported as a warning rather than dropped.

The migration path
Can AI agents query my data safely?

An MCP server, over stdio or remote Streamable HTTP, exposes governed tables as tools. The OAuth token maps to a role, so every agent call passes the same six access-control layers as a human query, and traversals are limited to registered relationships. Agents get no bypass and there's no second policy to keep in sync.

Governed data for AI
Does it work in an airgap?

The embedded profile ships the entire runnable system, precompiled UI included, as a single Python wheel. Regulated orgs already trust Artifactory-as-PyPI, so there's no Docker registry to mirror, no JVM, and no root required. Its dependencies are locked with hashes in the repository.

What happens to my model if I stop using Provisa?

You keep it. Provisa is a handful of primitives (domains, tables, relationships, masking, views) compiled deterministically. The model is portable declarative config held in git, and the SQL it compiles is yours to read and export. The semantics you write don't die with the tool.
