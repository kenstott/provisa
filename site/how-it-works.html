Provisa / How it works

Connect your data. Query in 5 minutes.

Governed from the first query.

The claim

Connect Postgres, Snowflake and Salesforce. Query with SQL, GraphQL or your AI agent. In 5 minutes.

The claim is literal. Point Provisa at your sources, describe how they fit together, and you have a governed API across every source. The five minutes are real: the Start here demo walks through it on a sample dataset, start to finish.

The mechanism

Provisa is a data kernel: a compiler and runtime for building your data control plane.

The primitives are sources, tables, relationships, terms, roles, capabilities, grants, scope, products, and contracts. Declare them and the whole governed API follows: the query endpoints, the legal join paths, the access rules, and the audit trail.

Every language compiles to one IR. Governance is applied there and pushed down into the native query your engine runs. A GraphQL query, a SQL statement and a Cypher traversal all pass through the same governance point before anything reaches your data.

Provisa compiles each request and hands it to your engine. Results stream back. It scales horizontally and vertically to support your workloads, and the heavy compute is offloaded to your engine.

It is built the way an operating system is built — the same philosophy as an OS kernel and its drivers. Source drivers, engine drivers and secrets drivers plug in and swap without reinstalling. Command bindings are the compatibility layer that answers other tools’ calls: APOC for Neo4j tools, catalog functions for SQL clients, fields in GraphQL, tools in MCP. BI tools, notebooks, agents and apps are clients connecting over standard protocols. Provisa drives your systems; it does not run on them and never becomes their engine.

Three tools it borrows from, one idea each. From Unix: a few small primitives that compose, so a new need is a combination rather than a new subsystem. From Terraform: you declare the state you want, review the diff, and promote it from one environment to the next. From Kubernetes: a controller keeps what is running reconciled to that declaration, so the APIs, the governance and every published copy follow the model instead of drifting from it.

Why one compiler can speak every language

Languages are ways of expressing logic, and the logic of data is bounded: select, join, aggregate, traverse. Transports are bounded too: whatever the protocol, data leaves through a socket as rows, nested documents, graphs, columnar batches or streams. Programming languages have shared one compiler infrastructure for twenty years; Provisa does the same for data.

Building a compiler front end has also become cheap: parser generators like ANTLR and mature open-source parsers for SQL, GraphQL and SPARQL do most of the work, so a new language is a translation into the IR, not a new system. Each request is compiled when it arrives into one IR, governed there, handed to your engine as native SQL, and shaped on the way out for the transport that asked.

Where languages or protocols differ at the edges, their public conformance suites settle it: Provisa runs them and publishes the results.

It also means the pace of change isn't a constraint. New query languages, protocols, engines and sources keep arriving; for most stacks each one is a migration. Here, a new language or transport is a front end or a shaper, and a new engine or source is a driver: additions to the edges, with the model and its governance unchanged.

Command bindings

Does Provisa support the library or tool you already use? It can: create its command bindings. A command is written once, and every language can call it, each under the name that language's callers expect. That's apoc.meta.data for a Cypher tool, a catalog function for a SQL client, a field in GraphQL, a tool in MCP.

Every command is offered in every language by default. Renaming it or leaving it out of a language is an explicit choice, and SQL is always there because everything compiles to it. Where a language expects a different result shape, that variant is its own command. Each one runs governed, so a mimicked tool call never sees more than the role may read.

That's how Provisa speaks APOC to Neo4j tools and agent frameworks, and it's how you teach it any other dialect yourself, without waiting for a release.

What you can check today

The generated SQL is visible for any query in the explorer: write a GraphQL query and the Query Language Explorer shows its Semantic SQL and Cypher translations live, beside your query, before it runs.

The live sandbox at sandbox.provisa.dev opens a private environment with data already loaded. Run a query, read the plan, and verify it yourself.

What Provisa is not

Is Provisa a database, or does it replace my warehouse?

Neither. Provisa is a semantic and governance layer that runs on an engine you choose: Trino, DuckDB, ClickHouse, Postgres, Snowflake, Databricks, BigQuery, or the embedded DuckDB engine in the box. Your warehouse becomes a replaceable execution engine, not the place your semantics live.

Why that matters.

How is this different from Starburst or Denodo?

Starburst is a query engine; Provisa sits above one and can use Starburst as its engine. Denodo is the closest comparison, in the same category: Provisa adds GraphQL and Cypher as peers to SQL, nine wire protocols including pgwire and Bolt, engine choice, and a deployment that starts at one pip install.
